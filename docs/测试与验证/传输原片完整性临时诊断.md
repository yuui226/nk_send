# 传输原片完整性临时诊断

当前用于对照普通安卓和鸿蒙的原片损坏问题。入口集中在 `TransferCorruptionDiagnostic`，复用现有传输观察点，不增加另一套安卓传输实现。

## 开关与移除

- `gradle.properties` 中临时设置 `transferCorruptionDiagnostic=true`，现有 Debug / Release 打包脚本均会启用；运行时只对已识别为 Harmony 的设备生效。普通安卓不计算诊断哈希、不做回读，也不生成 TXT。Gradle 开始时会打印 `Transfer corruption diagnostics ON`。
- 测试结束后删除这一行或改为 `false`，重新打包即可关闭诊断哈希、本地回读、队列结束后的相机重读和 TXT 输出。也可用 `-PtransferCorruptionDiagnostic=false` 覆盖一次构建。
- 这是构建期开关，不写用户设置。旧诊断包需要更换成重新构建的普通包才会停止采集。
- 后续完全删除代码时，集中删除 `TransferCorruptionDiagnostic`、构建标志和 `TransferViewModel` 中的可空诊断调用；协议层只移除诊断 trace / reference-read 接口。**保留鸿蒙完整性校验用的 `TransferFingerprint`、接收字节观察器、私有临时源、发布记录及设备判定**，它们属于修复功能，不能随诊断一起删除。

## 测试与日志

1. 选择一个空的传输目录，在 Harmony 设备上测试 JPG / RAW / 视频。普通安卓仍使用原有 SAF 写入、改名或复制路径，以及原有视频续传规则；不会运行这套诊断。鸿蒙诊断只观察，不根据哈希差异额外删除文件、改变任务成功状态或自动重试，完整性修复仍按兼容分支运行。
2. 日志优先写入传输目录根部的 `ZTransfer_corruption_时间戳.txt`。按天 / 按类存放时也在根目录，不在日期 / 类型子目录。若传输目录的 DocumentsProvider 拒绝创建或打开日志，会自动写入公共 `Download/ZTransfer/` 目录，用户可以直接在系统文件管理器中找到。应用私有目录 `files/transfer-diagnostics` 只作为开发侧副本，不再作为用户唯一的兜底。启动、每 8 个文件和队列结束时都会重试；报告开头会记录 `reportUri=...`、`location=transfer-directory|public-downloads` 和 `reportError=...`。
3. 已有原图会按原规则跳过，报告中写 `FILE_SKIP ... coverage=not-checked`，不算本次诊断样本。不要把“已存在跳过”当作“重新下载并通过校验”。
4. 卡片完成后先保持相机连接，等 TXT 最后出现 `END` 再复制发出。诊断还会回读最终文件并向相机重读原片进行对照，因此比正常传输耗时更多；诊断包不适合测正式版吞吐量。

## 读懂结果

| 标记 | 检查位置 |
|---|---|
| R | 接收后、写入目标流之前的字节。安卓视频续传时前缀来自本地，`receivedOrigin=local-prefix+camera-suffix` 会明确标记 |
| T | 关闭输出流后回读临时源；安卓为 SAF 临时文件，鸿蒙为应用私有临时文件 |
| F | 改名 / 复制完成后回读正式文件 |
| L | 本轮队列结束时再次回读正式文件，与 F 比较 |
| C | 队列结束后向相机重读原片（只计算哈希，不生成第二份图片），与 R 比较 |

`MATCH` 表示对应两次字节观察一致；`SIZE_MISMATCH` / `CONTENT_MISMATCH` 表示大小 / 内容不一致；`READ_FAILED` / `unavailable` 表示证据不完整，不能当作通过。暂停、断开或退出可能导致末尾的回读未完成，需一起保留相关错误记录。

诊断使用固定缓冲，不保留整张图片 / 视频字节。SHA-256、临时文件和最终文件回读，以及额外一次相机读取都会增加耗时和 I/O；删除构建开关后，普通安卓不再承担这些诊断开销。报告中的 `storageCompatibility harmony=false staging=saf resume=normal` 可用于确认安卓没有误走鸿蒙修复分支。
