# 传输、生成与滤镜／LUT 性能复查

日期：2026-09-29。基线：bb649087，包含本轮尚未提交的修正。

范围：AP、STA、USB 传输到自动生成的调用链；照片滤镜／LUT 配方、处理与资源；监看 LUT 的加载和绘制。代码及 JVM 验证，不包含真机性能测量、GPU 兼容性或实际存储提供方测试。

## 本轮修正

1. **整文件下载补充已知大小校验。** 原先全量路径只核对数据相位声明大小；若相机返回一个自称完整的短数据相位，可能漏报。现在同时核对 ObjectInfo／GetObjectSize 已知的可靠大小。未知大小哨兵不用于比较，64 位视频大小保留。校验仅比较整数，不重新读取文件，不额外访问相机，不改变数据内容。照片错误清理、视频续传仍沿用原有处理。
2. **小图的滤镜像素缓冲按实际区域分配。** 分区边框导出原先总是申请约 16 MiB 像素数组。现在共用渲染器的缓冲计算规则；600×400 图只需 960,000 字节（约 0.92 MiB）。同步修正内存预检，避免小图按整块计算。大图仍使用原来的四百万像素批次，没有增加大图 JNI 读写次数，没有降采样或修改颜色算法。

## 下载与生成的竞争检查

- 下载按数据流写入；不为整张原图创建位图。1 MiB 输出缓冲减少小写入；每 200 ms 更新下载进度，不逐数据包更新整份任务列表。
- JPEG 文件头仅在边框需要拍摄信息时捕获。视频、纯滤镜／LUT 不捕获这些头部。解析与必要补读有独立消费者，补读不会占据像素计算线程。
- 自动生成一张一张执行，专用后台优先级线程；排队只存轻量配方与位置，不提前解码。下载不等待绘制、裁切、JPEG 编码结束。
- 元数据补读仍共享相机通道。新照片文件头完整时无需补读；已有原图、截断头是必要的例外。没有为了“完全无竞争”删除这些功能。
- 已有文件索引、效果目录复用；生成查重先于解码。裁切优先直接使用可重开的文件描述符，无法使用时才复制私有临时文件。
- 时间与速度各自计算。生成等待不算下载耗时或生成处理时间；CPU／存储竞争造成的实际下载变慢不会被统计公式隐藏。
- 共享硬件仍有竞争，无法仅通过线程分离承诺打开 LUT 后下载速度完全不变。照片完整事务期间，其他相机请求可能需要等待。

## 照片滤镜与 LUT

- 两个设置入口保持各自草稿，照片 LUT 目录与监看选择独立。启用 LUT 后滤镜关闭；启用滤镜后 LUT 关闭；生效选择只有一份，不叠加计算两次。
- 入队保存当时的选择与强度。照片 LUT 使用内容寻址的私有快照，外部文件后续修改不改变已入队配方。弱引用跟踪仅用于保护仍有使用者的快照，不把排队 LUT 大表常驻内存。
- 同一生成持有已经取得的 LUT mapper，各区域不会因共享缓存淘汰而重新加载。共享 LUT 资源和文件解析缓存分别有预算，不能把两者误写成合计 8 MiB。
- CPU LUT 使用浮点表、三线性插值、域范围处理及强度混合；不进入普通滤镜 HSL 分支，不分配普通滤镜的精确颜色缓存。
- 普通滤镜使用有界精确 RGB 缓存，冲突重新计算而不近似取色。alpha 和透明像素规则保持不变。
- 非沉浸边框对原照片区域分区处理，再绘制边框，不把 LUT 套到文字、品牌或边框上。无边框／沉浸路径仍需整图解码。最终仍保留完整画布，不宣称恒定小内存。
- 总开关不清空配方；裁切原图与效果输出仍分别保存。效果失败保留原图，生成重试不重新下载。
- 本地照片工作台批量导出仍是独立的最多两工作者逻辑，自动传输后生成是一工作者；本文不宣称整个 App 只能同时处理一张照片。本地工作台使用本地照片元数据是原有用途，不等于相机自动生成改回本地 EXIF 兜底。

## 监看 LUT

- 文件扫描／解析通过受控 IO 队列；快速切换使用请求代次与取消标记，旧结果不能覆盖新选择。
- GPU 每帧只上传画面，不重新上传 LUT；同尺寸画面复用纹理存储。待绘制帧只保留最新一帧，没有逐帧无限排队。
- 新 LUT 真正显示后才提交选择并关闭伪色；开启伪色会关闭 LUT。加载或 GPU 失败保留既定降级处理，不让旧回调重新开启已经关闭的功能。
- 监看是 GPU 半精度纹理，照片是 CPU 浮点处理；算法方向一致不代表输出逐像素相同。显卡精度、设备显示和照片 LUT 强度仍会影响观感。没有擅自合并两套用途不同的渲染器。
