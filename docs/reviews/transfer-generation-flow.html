下载继续走，生成独立做

这份说明描述代码现在怎样工作，不是下一版设想。每个环节有固定编号，后续可以直接讨论“D05”或“G08”。

基线：8e1c9c65 + ab99323a；包含取消边界、LUT 资源生命周期、整文件大小校验及小图缓冲修正。范围：相机传输后的自动照片生成，不代表本地滤镜工作台的全部流程。

独立的是调度和状态，不是手机硬件。下载下一张时可以生成上一张，但两条线仍共享 CPU、内存、磁盘和相机通道。不能承诺打开 LUT 后绝对零速度影响。真机验证由你负责。
下载线入队 → 查原图 → 请求相机 → 流式写盘 → 校验 → 发布原图 → 交接 → 下一张
生成线登记 → 准备字段／地址 → 等就绪 → 裁切（可选） → 效果 → 保存 → 下一张

中间的元数据准备是辅助通道：它不占用重生成名额。文件头积压时的小型暂存写盘仍可能让交接短暂等待。

下载线

把相机文件可靠地保存到手机
D01

入队时记住设置

每次操作创建独立任务，记住这次的滤镜或 LUT、边框、水印、裁切范围和按日期保存规则。以后修改设置不会改写这张任务的配方。

边界与用途

同一次批量操作按文件编号去重；不同次手动操作可以建立不同任务。照片效果自动生成支持 JPG/JPEG/PNG；RAW、视频原样传输。总开关是执行时的门控，不是清空配方。

代码核对：TransferViewModel.createQueueTasks / addToQueue
D02

决定何时开始

立即传输模式继续处理队列；“选完再传”或暂停状态下等待用户开始。正在传的文件不会被“停止”硬切断。

边界与用途

下载顺序保持队列顺序。撤回只影响尚未开始的下载；当前文件自然完成，生成队列独立推进。

代码核对：processQueue / withdrawPending / PendingTransferQueue
D03

找到目标目录并检查原图

复用目录索引查找已经保存的原图。找到后直接引用它，不再向相机下载同一份字节；如有生成需求，则交给生成线。

边界与用途

不是文件内容哈希去重；按目录中的名称、大小等现有规则判断。目录首次扫描会等待，后续复用；同目录扫描请求合并，扫描时不持索引共享锁。

代码核对：getDirectoryIndex / ExistingFileNameIndex.findOriginal
D04

区分照片与视频

照片一律从零下载，不使用旧半成品。只有 MOV、MP4、NEV、AVI 保留分块和断点恢复。

边界与用途

照片旧半成品会删除。视频检查身份令牌；半成品已完整时尝试发布，否则从 4 MiB 边界续传。视频大小未知时不能仅凭半成品大小认定完整。

代码核对：supportsVideoResume / processQueue
D05

向相机请求数据

照片在 AP／USB 使用整文件请求；已验证的 STA 直读路径保留尼康局部读取命令，但一次请求完整范围。视频沿用原分块策略。

边界与用途

STA 单次照片请求要求已知大小且范围不超过 Int 最大值；不支持局部命令时仍有原来的整文件回退。视频普通 Wi-Fi 块为 4 MiB，大于 512 MiB 的文件用 32 MiB；USB／高吞吐使用 64 MiB 块，符合条件的小视频也可整文件请求。

代码核对：NikonCamera.downloadToFile / shouldUsePartialObjectDownload / downloadChunkSize
D06

边接收边写盘

数据收到一段就写一段到隐藏临时文件，不主动把整张原图加载成位图。拍摄信息需要用到时，顺便保留 JPG 的前 256 KiB。

边界与用途

保留文件头不额外访问相机。仅开启边框且至少选择一项拍摄信息的 JPEG 才捕获；视频不捕获。底层数据包读写仍存在，它不等同于多次相机分块请求。

代码核对：downloadToFile.writeChunk / pump / captureHeader
D07

检查传输是否完整

必须收到相机响应，核对实际字节数与相机声明／已知大小。照片一次请求短读会失败，不拼接第二次范围请求。

边界与用途

这些是响应及长度校验，不是逐字节校验或端到端哈希，不能宣称能发现所有同长度损坏。异常事务会安全排空或关闭连接，避免下一条命令读到遗留数据。

代码核对：pump / transferTransaction / abortActiveTransaction
D08

发布原图

完成写入后预留文件名，优先把隐藏临时文件改为正式名称。提供方不支持改名时，复制成正式文件并核对大小。

边界与用途

同目录名称在短锁内预留，文件 I/O 在锁外。改名成功立即解除临时 URI 的删除资格，即使提供方不改变 URI。复制回退不是文件系统级原子操作，进程被杀仍有窗口。

代码核对：reserveDisplayName / renameQuietly / copyAsFallback
D09

记下载结果并交接

原图成功后记录下载完成、耗时和速度。如需裁切或效果，就提交轻量任务，然后继续下一张下载。

边界与用途

生成准备／绘制／保存不直接计入下载耗时；但 CPU、磁盘竞争造成的实际变慢仍会体现在真实下载速度中。交接若需溢出暂存文件头，可能等待一小次写盘；并非零成本。

代码核对：handoffPhotoGeneration / launchPhotoFrameExport
D10

失败怎样重试

照片失败删除半成品，重试从头下载；视频在允许时保留半成品续传。生成失败不会要求重新下载已保存原图。

边界与用途

保存目录或相机连接失效会使相关任务失败。运行中的照片不会因用户暂停下一批而取消；退出时的协程取消另按资源清理流程处理。

代码核对：download result / retryTask / dispatchRetryAttempts

生成线

从已保存原图制作裁切图和效果图
G01

先登记轻量任务

排队只保存文件位置、配方和小型元数据快照，不提前解码所有排队照片。队列包含运行项，最多 4096 项。

边界与用途

同一个任务编号重复交接不会重复生成；不同裁切或效果是不同任务。容量用完会明确生成失败，保留下载成功，不让下载等待空名额。

代码核对：PhotoGenerationQueue.submit
G02

准备必要拍摄信息

新 JPG 优先解析下载中保留的文件头；已有原图或生成重试优先复用可靠快照。纯滤镜／LUT、纯装饰边框不为拍摄字段读取相机。

边界与用途

自动生成边框不以可能脱敏的本地 EXIF 作为拍摄字段兜底。PNG 等非 JPEG 不走相机 JPEG 头捕获；尺寸、方向、输出 EXIF 的本地读取仍是独立步骤。

代码核对：needsMetadata / parseCameraFrameMetadata / allowLocalMetadataRead=false
G03

少数情况补读相机

缺少文件头或确认截断时才补读。通常完整 JPG 头不需要额外请求；本来没有 GPS 不会因此反复补读。

边界与用途

缺头从 256 KiB 开始；仍截断时扩大到 1 MiB、2 MiB。补读是独立消费者，慢请求不挡住已捕获文件头的解析。它仍与下载共享相机通道，必须等待安全事务边界，也会占用少量通道时间。

代码核对：PhotoMetadataPreparation.supplement / readExifHeader(background=true)
G04

确认补读没有认错照片

补读要求机身身份一致。无法识别实体机身时使用连接对象专属身份，不能只凭型号认为是同一台相机。

边界与用途

同一已识别机身重连后，必要补读先核对文件编号、文件名、大小、拍摄时间。不能确认则保留已有字段继续，不把其他照片的字段混进来。

代码核对：photoMetadataIdentity / samePhotoMetadataSource
G05

及时释放文件头

头部解析后立即释放原字节，留下短文本和坐标。相同来源合并准备请求，结果缓存最多 256 项。

边界与用途

原始头部队列内存预算 2 MiB，溢出私有暂存 16 MiB；失败允许缺字段继续。预算不包含全部瞬时峰值、位图或所有任务对象。文本字段最多 256 个 UTF-16 单元，正常短字段不复制。

代码核对：PhotoMetadataPreparation / boundedForQueue
G06

按需查城市和地区

仅选择城市／地区、有有效 GPS、非 AP 且联网已验证时，使用地址服务。无网络直接省略，不等网络恢复。

边界与用途

独立地址准备队列，一秒预算包含排队等待；缓存命中可直接用。同语言、经纬度格式化到四位小数作为缓存键，不是行政区边界判断。导出时再检查连接条件，不重复查询。

代码核对：PhotoFrameLocationResolver / photoPlacePreparation
G07

就绪后再占用生成线程

一次实际生成一张。排在前面的照片没准备好时，后面已就绪的可以先生成；列表顺序不变。

边界与用途

没有逐项轮询或每张等待协程。准备完成用事件唤醒。纯效果在总开关关闭时可直接跳过，不必等元数据；重新开启后尚未开始的任务使用原配方。

代码核对：PhotoGenerationQueue / execute
G08

如需裁切，先保存裁切原图

保留下载原图。读取原图真实尺寸、方向，解析用户确认的裁切区域，执行 JPEG 系数域裁切，另存 _crop.jpg。

边界与用途

普通文件描述符可直接读取时不复制整图；不支持才临时复制一份，结束清理。已保存的本任务裁切结果在重试时复用。裁切是独立需求，总开关关闭仍执行。

代码核对：generateCrop / withCropSource / LosslessJpeg.crop
G09

检查效果开关与已有成片

裁切之后以裁切图作为效果输入。正式开始效果处理时检查总开关；关闭则跳过效果，不清空配方。相同生效配方已有成片时跳过重复生成。

边界与用途

已开始的效果不会被中途关开关强行打断。裁切期间重新开启而元数据未就绪，会保留裁切图、暂停计时、让出处理名额。实际生成时重查授权，水印规则可能因此调整。

代码核对：execute / destination.hasFrameFor / effectivePhotoFrameWatermark
G10

解码、处理颜色和绘制

非沉浸边框通常分区解码、逐块处理，但最后仍有完整输出画布。仅滤镜／LUT或沉浸边框走整图解码路径，再合成。

边界与用途

解码与输出前做保守内存预检，不暗中缩图。分区滤镜的像素缓冲按实际区域分配，小图不再固定占用约 16 MiB。内存不足或提供方不支持区域解码仍可能生成失败；原图保留。Java 堆估算不能保证所有 native 分配成功。

代码核对：PhotoFrameExporter.renderSource / renderOriginalFrameByRegions / ensurePhotoAllocation
G11

限制计算和 LUT 占用

导出像素计算留在一个后台线程；应用预览另有最多两线程。LUT 按入队时私有快照加载，外部文件修改不应改变已入队效果。

边界与用途

同一张生成期间持有 LUT，后续区域不因缓存淘汰而重复加载；排队配方不持有大表。LUT 原生像素循环仍在同一生成线程同步运行，不增加线程；不可用时回退原 Kotlin。LUT 运行资源缓存 8 MiB／16 项，预算包含原生表副本；另有独立文件解析缓存。内置滤镜精确颜色缓存最多 8 MiB，只算实际颜色，冲突重新算，不近似取色。预算是各缓存上限，不是全进程总上限。

代码核对：PhotoFilterRenderer / PhotoCubeResourceCache / PhotoLutStore
G12

保存效果图并收尾

编码到临时输出，复制适用 EXIF，再发布正式效果图；失败清理临时文件，释放位图及处理计数。下一张就绪任务接着运行。

边界与用途

效果图仍按既定 JPEG 质量编码，不能把“JPEG 裁切不重新量化”误解为整个效果生成无损。生成失败独立显示，重试使用已保存原图／裁切图和原配方。

代码核对：PhotoFrameExporter.export / saveRendered / complete / newAttempt

计时怎样分开

下载时间／速度

从本次协议下载开始，算到原图保存、改名或必要复制结束。视频续传只用这一次实际传输的字节计算速度，不拿此前已下载量充数。生成不直接参与公式，但资源竞争的真实耗时不会扣除。

生成时间／等待时钟

排队、元数据和地址准备期间显示时钟。取得生成执行机会后才计时，包含查重、目录准备、裁切、绘制与保存。若裁切后让出名额等准备，暂停计时并累加实际处理片段。跳过不显示虚假的生成耗时。

遇到这些情况，会怎样

总开关关闭

纯效果到执行点时跳过；裁切仍保存。之后开启只影响尚未开始的任务，不自动重做已跳过项。

原图已在手机中

跳过下载并引用原图。有元数据快照就复用；没有时可能补读相机，不假设本地 EXIF 完整。

缺少拍摄字段

使用已可靠取得的字段生成；缺失项省略。不伪造 GPS、城市或曝光，不把解码失败当作缺字段。

相机掉线

原图下载按失败处理；已落盘的生成可继续。确需补读的准备可能等待协议失败收尾，然后允许缺字段生成。

用户暂停／清空

暂停后续下载，当前下载自然完成。正在生成的任务不会被清空或单项删除，生成线继续。

App 退出

取消队列并清理资源，不跨线程回收仍在使用的位图。临时文件下次启动还有清扫；这是进程内队列，不承诺重启后自动恢复所有生成任务。

磁盘不足／内存不足

该阶段失败，不反向删除已成功原图。有限容量不是无限任务保证，系统被直接杀进程也不能靠异常捕获挽救。

重试生成

新尝试有新任务编号，只走生成入口。保留原图位置和配方，目录设置随后变化不会把旧任务重定向。

本轮复查记录

修正：原图改名成功后，在离开后台操作前立即解除临时 URI 的删除资格，防止取消恰好发生在返回边界时误删原图。另外，当前生成持有同一份 LUT，避免分区处理时因缓存淘汰或超预算重复读取。整文件下载同时核对已知文件大小；小图滤镜缓冲按实际区域分配。没有改动图片内容或颜色算法。

明确保留的取舍：照片单次请求减少命令往返，但 FHD／EXIF 不能插入同一个未结束事务，可能要等整张照片传完。已有原图与截断头仍需按需补读，所以没有删除全部元数据辅助通道。

不夸大的结论：分区解码仍需完整输出画布；内存预检不保证不会被系统终止；长度校验不是哈希；复制发布回退不是完全原子。当前不承诺进程重启自动恢复全部生成队列。
