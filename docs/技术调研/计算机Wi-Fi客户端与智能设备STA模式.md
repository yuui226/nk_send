# 计算机 Wi-Fi 客户端与智能设备 STA 模式

> 更新日期：2026-11-04
>
> 原有 Z30“连接到计算机”路径已完成真机配对、照片列表、预览与原文件传输验证。本次新增的首次配对防护及验证边界见第九节。本文也用于区分新机型“连接至智能设备 → Wi-Fi连接（STA mode）”，并作为后续协议研究入口。
>
> 首次配对流程已按文末“精简路线接入正式连接”更新。此前的事件等待规则和独立探测描述保留为研究历史，不代表当前正式行为。

## 一、先说结论

“STA”只描述相机在 Wi-Fi 网络中的角色：相机作为客户端加入手机热点或路由器。它不代表相机上层连接的一定是手机应用。

尼康目前至少存在两条使用相同 Wi-Fi 拓扑、但配对身份和应用协议不同的路径：

```text
相机作为 Wi-Fi 客户端加入热点或路由器
├─ 连接到计算机
│  └─ 计算机配置文件 + PTP/IP（ZTransfer 当前实现）
└─ 连接至智能设备
   └─ Wi-Fi连接（STA mode）+ SnapBridge（尚未实现）
```

因此：

- 当前功能不是仅供老机型使用的临时绕路。新机型同样正式支持“连接到计算机 → Wi-Fi客户端模式”。
- 新机型“连接至智能设备 → Wi-Fi连接（STA mode）”是另一条智能设备连接路径，不能因为网络拓扑相同就视为与当前实现兼容。
- 在真正完成智能设备 STA 的发现、认证、配对和 PTP 能力验证前，不应使用它替换当前计算机配对实现。

## 二、两条路径的准确区别

| 对比项 | 计算机 Wi-Fi 客户端 | 智能设备 STA |
|---|---|---|
| Wi-Fi 拓扑 | 相机加入手机热点或路由器 | 相机加入手机热点或路由器 |
| Z30 菜单 | 设置菜单 → 连接到计算机 → 网络设定 | 不提供此智能设备 STA 入口 |
| 新机型菜单 | 网络菜单 → 连接到计算机 → 网络设定 → 创建配置文件 → 连接至现有网络 | 网络菜单 → 连接至智能设备 → Wi-Fi连接（STA mode） |
| 官方对端 | Wireless Transmitter Utility、NX Tether 等计算机软件 | SnapBridge/尼康影速传等智能设备应用 |
| 配置文件 | 计算机连接配置文件 | 智能设备连接配置文件 |
| 当前 ZTransfer 身份 | `PAIRED_COMPUTER` | 尚未实现和验证 |
| 当前 ZTransfer 支持 | 已支持 | 不支持 |

同一个热点只能解决 IP 层互通，不能消除配对身份、服务发现、会话初始化和操作码权限的差别。两个菜单产生的配置文件也不应假设可以互换。

## 三、ZTransfer 当前实现

代码内部仍使用 `WirelessMode.STA` 表示当前的“计算机 Wi-Fi 客户端”连接分支，这是实现名称，不等于尼康“连接至智能设备”的 STA 菜单。

当前 Z30 真机已经验证：

- 相机可以连接手机个人热点或路由器，并保存计算机网络配置文件。
- 首次连接可完成配对；后续可从相机选择已保存配置，无需重新输入热点密码。
- PTP/IP 命令通道、事件通道与会话可以建立。
- 可以读取存储卡对象句柄、生成照片列表、识别原文件名和拍摄日期。
- JPG、NEF 和视频可以加入队列并传输原文件。
- JPG 可从 MPF 独立预览图生成大图预览；NEF 可读取内嵌 JPEG 预览。
- 缩略图缓存、渐进式列表、断线重连和双卡筛选均有 STA 独立分支。

### Z30 的协议特征

Z30 在计算机配对会话中有一组需要兼容的行为：

- `GetObjectHandles` 可用，但 `GetObjectInfo` 对样本句柄返回 `0x200F`。
- `GetPartialObject`/直接对象读取可用，因此可以绕开 `GetObjectInfo` 完成目录、预览和传输。
- `GetFhdPicture (0x920F)` 与 `GetLargeThumb (0x90C4)` 返回 `0x200F`，不能用原图冒充 FHD。
- JPG 大图预览使用文件 MPF 索引中的独立 JPEG；NEF 使用文件内部 IFD/扫描得到的 JPEG 范围。
- 元数据、文件头、缩略图和预览范围均需缓存，避免复杂网络下重复探测。

这些兼容逻辑只属于 STA/计算机配对分支，不应进入 AP 或 USB 热路径。

## 四、哪个更快、哪个能力更强

### 可以确定的部分

- 两条路径若使用同一台相机、同一频段和同一热点，原文件持续传输的物理上限接近；名称中的“原生 STA”不会自动提高无线带宽。
- 实际速度主要由 2.4/5 GHz、相机无线芯片、热点质量、网络拥塞及相机 PTP 实现决定。
- 当前计算机模式已经能自由选择并传输 JPG、NEF 和视频原文件，这是 ZTransfer 的核心优势。

### 尚待真机确认的推测

- 智能设备 STA 可能提供更适合手机的发现、配对、重连、缩略图和元数据接口，因此首屏速度与连接体验可能更好。
- 它也可能限制 RAW、视频、原始尺寸或部分遥控能力。SnapBridge 官方帮助显示，这些能力会随机型和下载流程变化，不能假设智能设备 STA 一定更开放。
- 智能设备 STA 是否仍暴露标准 PTP/IP、是否复用 AP 模式的操作码、能否同时满足相册浏览与监看，均需抓包和真机验证。

结论：智能设备 STA 更可能“更适合手机”，但目前没有证据证明它在原图吞吐或可访问文件类型上全面强于计算机模式。

## 五、命名约定

为避免与尼康新机型的“Wi-Fi连接（STA mode）”菜单混淆，建议区分内部名称与用户名称：

| 场景 | 建议名称 |
|---|---|
| 代码内部现有分支 | `STA` / `PAIRED_COMPUTER`，暂不做无收益的全量重命名 |
| 当前用户入口 | “共享网络”或“计算机配对” |
| 新机型未来入口 | “智能设备 STA” |
| AP 用户入口 | “相机热点” |

帮助文案必须引导当前用户进入“连接到计算机”，不能引导至“连接至智能设备 → Wi-Fi连接（STA mode）”。

## 六、未来研究智能设备 STA 的验证清单

在取得支持机型后，将智能设备 STA 作为独立后端研究，不直接改写当前 STA、AP 或 USB 实现。

1. 记录机型、固件、菜单路径、热点频段以及是否要求 SnapBridge 先配对。
2. 抓取服务发现信息：mDNS 服务、TCP/UDP 端口、广播内容和相机 IP。
3. 对比 AP、计算机客户端、智能设备 STA 三种模式的初始化身份、GUID、认证数据和事件通道。
4. 记录 `GetDeviceInfo` 广告的操作码，并逐项验证：
   - 存储卡与对象枚举；
   - 文件名、日期、大小和双卡信息；
   - 缩略图、FHD/大图预览；
   - JPG、RAW、视频原文件读取；
   - 实时取景、遥控和事件；
   - 断线恢复及配置文件持久化。
5. 测量冷启动首屏、缓存首屏、100 张缩略图、FHD 预览和 1 GB 文件的耗时与吞吐。
6. 若能力足够，再新增独立连接类型和机型能力探测；不得让失败探测回落并污染 AP/USB 状态。

### 建议的采用标准

只有同时满足以下条件，智能设备 STA 才适合成为 ZTransfer 正式入口：

- 能由 App 主动浏览相机文件，而不是只能从相机端标记上传；
- 支持当前产品需要的 JPG、NEF、视频和原文件传输；
- 支持可靠的缩略图、日期、文件名和大图预览；
- 配对与重连至少不弱于当前计算机配置文件；
- 不降低监看、遥控、队列传输和已传判定的能力；
- 可以按机型安全降级，且完全不影响 AP 与 USB。

## 九、首次配对误进入相册的防护（2026-11-01）

用户反馈：首次创建计算机配置时，App 偶尔已进入相册，相机仍停在等待配对界面，配置不能保存。代码中可确认的缺口是：`0x935A` 返回 OK 后，等待事件超时或断开也继续重连；随后只要照片可读，就写入已验证标记。照片可读并不能证明配对向导已结束。

当前首次配对的顺序：

1. 使用原有持久化 initiator ID 建立命令、事件双通道，取得机身 GUID。
2. 按原顺序初始化并检测存储；无配对标记时，完成 `0x952B → 0x935A` 交换。
3. 发送 `0x935A` 前排除已经排队的旧事件。返回 OK 后，等待完整的 `0x4008` 事件，最多 30 秒；收到即继续，没有固定增加等待时间。
4. 仅在这一步成功后生成内存确认记录。沿用原来的服务重启等待，重连时锁定同一机身 GUID 和计算机身份。
5. 新会话通过存储及照片访问校验后，首次配对还必须实际收到结构完整、尺寸有效的监看 JPEG；只关闭本次启动的监看，恢复成功后才保存已验证标记并进入相册。主身份和备用计算机身份遵循同一流程；已有可信配对和旧标记迁移不新增监看请求。
6. 监看权限校验失败时，沿用原身份、锁定同一机身，最多重新完成一次配对交换并再次取帧；任一步恢复失败即停止本轮发现及已排队的自动重试，不写成功标记、不切相册、不清除旧凭证。

事件缺失、断开、截断或超时均不作为完成，不用备用相册身份绕过；缺少确认时停止本轮发现和自动重试，提示用户检查相机后重试。取消后到达的结果不能提交配对标记。已有可信配对不重新配对；legacy 标记按原逻辑校验迁移，暂时读取失败保留旧记录，只有明确返回配对专用能力集才作失效处理。AP、USB 和照片浏览规则不在本次修改范围内。

**验证边界：**尼康 Z30 USB/MTP 文档将 `0x4008` 定义为设备能力变化，而不是配置存盘凭证。“本轮状态变化 + 同机重连 + 有效监看帧”共同作为新配对门槛，不能据此宣称已实测所有机型的保存行为。缺失该事件的固件会保守失败，需要真实日志核实，不能再次降级为“相册可读即配对成功”。

回归入口：`StaPairingHandshakeInstrumentation` 使用模拟器本机双 socket、真实 `NikonCamera.connectSta` 和隔离偏好记录，覆盖缺失／旧／畸形事件、真实超时、正确重连、错机身、仍待配对、取消和旧凭证复用；`StaPairingStateTest`、`StaConnectionIsolationTest`、`StaCameraProfileSelectionTest`、`PtpIpDiscoveryTest` 保护原有判断和自动重连边界。

### Z30 1.20 监看权限实测（2026-11-01）

来源：用户提供 `Shared-STA-8641172054054667043.txt`，Debug 2.02（75）。配对前后 `D1A2=00`、`D1A4=00000000`、`D1BB=00` 及 D1A2 描述完全一致；未启动时直接取帧均为 `A00B`。这些值不能判定配对成功。

首次失败发生在临时探测发送 `9201 StartLiveView` 后，连接 EOF，此时尚未发送真正的 `952B` 配对查询。第二次完成 `952B → 935A → 完整4008 → 同机重连` 后，`9201 / 90C8 / 9203` 均成功，收到有效 `640×424` JPEG，随后 `9202` 成功关闭本次启动的监看。

全部临时探测类、入口、分享按钮和前置探测钩子已移除。正式代码仅在新配对完成交换并重连之后验证一帧；D1A2 仅用于判断是否需要启动，以及避免关闭原本已开启的监看，不作为权限证据。DeviceReady 也不是成功证据，最终以有效 JPEG 为准。异常或半包先关闭连接，不在坏流上继续清理；取消不触发自动恢复、不落配对标记。

这次日志确认了该 Z30 的权限差异。监看失败在产品流程上统一视为“尚未完成验证”，不允许进入相册；不据此诊断所有失败都唯一来自配对，也不删除用户已有凭证。

本次验证：`StaConnectionIsolationTest` 20 项通过；`StaPairingHandshakeInstrumentation` 在模拟器中使用真实双 socket 完成 23 项场景，包括权限失败后完整重新配对成功、旧可信标记被明确否定后不能绕过、取消清理、错误／缺失事件，以及旧配对不新增任何监看指令。Debug 包按仓库脚本生成并成功通过 QQ 发送。实际新流程仍需在用户相机完成首次配对及断开后的重连验证。

### 二次对照审查

- 旧 ALBUM_EXPLORER 身份验证失败后，保留原有 PAIRED_COMPUTER 备用路线；只有计算机身份实际开始配对后，失败才阻止绕过。相册身份的校验失败不污染备用连接的普通网络重试。
- 最终写标记、明确失效标记与用户重置共用短临界区；取消检查位于锁内，避免被重置取消的旧握手在清除之后重新写回可信标记。正常已配对连接不会新增这一段监看或等待。
- 保留旧 v2 可信标记属于兼容策略，不会批量重验历史配对；这次修复对新配对流程生效，不能宣称所有历史错误标记都已自动修复。

二次审查后的验证：20 项连接逻辑测试与 24 项真实双 socket 场景均通过；新增场景在最终提交线程实际等待锁时取消并执行重置，确认可信标记及旧身份均不会复活。新 Debug APK 通过仓库脚本构建并成功发送 QQ。

### 首次配对耗时审查（2026-11-01）

- 原相册验证对三个 ObjectInfo 样本取 AND。任一失败后，剩余样本不能改变结论，也不缓存数据；改为立即进入原有 Size＋Partial 路径。全成功路径仍检查三个样本。
- 移除该回退路径的 GetThumb。其结果从未参与判定或填充缩略图缓存，仅用于诊断。上述 Z30 路径因此减少三次往返；不会减少照片列表的缩略图请求或改变配对确认门槛。
- 成功配对后的 6.6 秒固定重连间隔源自 `fe928b23` 的服务重新就绪实测；失败补救复用了同一间隔，目前没有独立的就绪计时。两者先保留，不用“端口可连接”冒充“配对记录已保存”。
- 30 秒事件等待和 8 秒监看验证都是超时／重试上限，成功立即继续；100／200ms 仅在忙碌或尚无帧时触发。用户日志中的正式验证所需请求合计约 1.17 秒，其中 StartLiveView 的 945ms 是相机响应耗时。
- 新增被动分段计时：发现候选、连接双通道、初始化、配对交换、事件确认、主动等待、同机重连、相册读取、监看验证、清理与进入相册。不发送额外探测请求。`+ms` 是各自记录起点的偏移，`Δms` 是相邻协议记录间隔，包含本地处理；外层 discovery 与每次 attempt 的起点分别标明。
- Debug 在现有照片页“诊断日志”保留最近一次连接，支持分享完整 TXT；不会在进入相册时清掉，不随缩略图日志滚出。会话 token 隔离取消后的旧回调；记录有容量上限，Release 不启用新增收集／分享入口。
