# GPS 配对、重连与位置更新：问题清单与优化方案

> 审查基线：`research/gps` 分支，2026-08-30。  
> 目标：用户只看到一个“开启 GPS”开关；配对、重连、定位和写入尽量自动，状态真实、请求最少、失败可恢复。

## 一、最终结论

当前 GPS 主链路已经具备可用基础，但有三个必须优先守住的边界。以下明确区分“日志已证实”“代码可推导风险”和“尚未验证建议”，避免把推测当成缺陷：

1. **BLE 握手完成不等于 GPS 已就绪**。必须完成 ID 写入回调、启动定位，再以 GEO 的 GATT 写入成功作为当前实现闭环；照片最终是否带有位置仍需导出做端到端验证。
2. **相机息屏后的断链应按可恢复事件处理**。用户已经报告息屏后出现连接状态异常；“一定由息屏导致 GATT 断开”目前仍是推断，需用锁屏日志确认。
3. **位置更新监听和 GEO 写入已经解耦**。当前实际写入策略已简化为“首个有效位置立即写入，之后每 60 秒最多写入一次”，不再按距离触发。

### 证据分级

| 级别 | 本稿采用的证据 | 结论口径 |
| --- | --- | --- |
| 日志/现场直接证实 | `stage4 received` 后出现 GATT `state=0 status=19`，没有 `GPS ready/GEO write success`；日志出现重复 `removeBond/createBond`，用户同时报告系统配对码错误弹窗 | 可列为已发生问题 |
| 当前代码直接证实 | `onReady()` 才启动定位；GEO 成功才进入 READY；定位请求为 5s/15s、无距离过滤；首个位置立即写入，之后最短间隔 60s；前台服务为 START_STICKY + stopWithTask=false | 可列为现状事实 |
| 代码可推导风险 | 4.5s 直连超时、1.5s 固定等待、错误路径 5s 重试 | 记录为风险或待优化，不宣称已在日志中发生 |
| 尚无证据 | 息屏一定导致 GATT 断开、60s 是否满足所有拍摄场景、某个 Android 版本一定能静默确认配对 | 只能列为待验证假设 |

## 二、用户看到的正确流程

### 1. 首次使用

用户操作只有：

1. 相机进入“连接至智能设备 → 配对（Bluetooth）→ 开始配对”。
2. App 点击“开启 GPS”。
3. 相机显示确认时，用户在相机上按 `OK`。

App 状态应严格按下面顺序流转：

```text
正在寻找
  → 正在配对
  → 相机请按 OK
  → 正在连接
  → GPS 写入中
  → 已开启
```

说明：首次配对成功字样可以短暂显示，但不能在相机尚未确认或 GEO 尚未写入成功前显示“已开启”。

### 2. 已配对后的后续连接

用户只需：

1. 相机开启蓝牙。
2. App 点击“开启 GPS”。

App 自动完成：

```text
正在连接
  → ID 写入确认（内部步骤）
  → 已连接（链路可用，等待定位）
  → GPS 写入中
  → 已连接/配对成功（首个 GEO 写入成功后的短暂过渡）
  → 已开启
```

不再重复 Classic 配对，不再展示配对步骤。`ID 写入成功` 后可以显示“已连接”（表示链路可用），但不能单独作为“已开启”的依据。

### 3. 相机息屏或短暂断链

```text
已开启
  → 连接暂时中断
  → 正在重连
  → GPS 写入中
  → 已开启
```

当前实现对此前已达到 READY 的会话在后台重连期间保持“已开启”的稳定视觉；若重连最终失败，才转入错误/重试状态。前台通知显示“连接已断开，正在重连”。这一时序仍需真机锁屏验证。

## 三、问题逐项清单

### P0（已证实并已回退）：把 stage4 当成 GPS 已连接会造成“有状态、无位置”

**现象**

相机显示已连接，App 也显示已连接，但没有地址和更新时间。

**根因**

`stage4` 只证明 BLE 协议握手完成。当前定位监听是在 `onReady()` 中启动，而 `onReady()` 还要求 ID 特征写入回调成功。若提前把 stage4 映射成 `CONNECTED`，定位监听不会启动，GEO 也不会发送。

**修复方案**

- 保持 `stage4 → ID write → onReady → startLocationUpdates → GEO write` 顺序。
- 首次连接和已配对重连都不能跳过 ID 写入确认。
- `READY/已开启` 只由首个 GEO 写入成功触发；已配对重连可暂时保留此前的 READY 视觉，直到重连失败或恢复完成。

**当前应有的样子**

```text
stage4 received
  → ID queued
  → GATT write ID success
  → GPS ready
  → GEO GATT write success
  → 已开启 + 地址 + 更新时间
```

**状态**：这是上一轮改动造成、并已由用户实测确认的回归；当前已恢复安全边界，并增加 ID 入队和 GATT 写入日志。

### P0（代码可推导风险）：直连 4.5 秒超时可能误杀正在进行的握手

**证据状态**

代码原先只判断 `ready=false`；日志确实出现过 `stage3 sent`、`stage4 received` 后 GATT `status=19`，但没有记录直连超时日志，因此不能断言该计时器就是本次断开的直接原因。

**根因（代码风险）**

原实现的直连计时器只看 `ready=false`。握手期间 `ready` 本来就是 false，4.5 秒计时器可能关闭正在写 ID 的 GATT。

**修复方案**

- 只有在尚未发送 stage3 时允许直连超时并 fallback scan。
- 一旦 stage3 已发送，必须让当前握手完成，交给 ID 写入超时或 GATT 断开处理。

**修复后的样子**

如果握手已发送 stage3，不应再出现由直连短超时主动切扫描；只有卡在服务发现/握手开始前才切扫描。

**状态**：已按防御性原则在本地实现；本轮未重新打包。下一次日志需出现 `BLE direct connect timeout; fallback scan` 才能证明它实际触发。

### P0：Classic bond 重复删除/重复 createBond，触发系统配对码弹窗

**现象**

日志出现多次：

```text
Classic stale bond remove=true
Classic createBond after removal=true
Classic stale bond remove=true
Classic createBond after removal=true
```

随后 Android 弹出系统配对窗口，并提示配对码错误。

**根因**

- 日志已确认同一轮流程重复执行了 `removeBond()` 和 `createBond()`。
- `removeBond()` 是异步的；在状态真正变为 `BOND_NONE` 前再次轮询，是重复触发的合理代码路径，但仅凭现有日志不能证明每一次重复都由该竞态产生。
- 日志确认 Android 系统配对窗口出现并提示配对码错误；是否完全由 `ACTION_PAIRING_REQUEST` 竞争造成，还需要 pairing variant 和手机侧确认结果证据。

**修复方案**

- 增加单次 `classicBondAttemptAddress`，同一时间只允许一个 `createBond()`。
- `BOND_NONE` 后对同一 Classic 地址只重试一次，不再由轮询重复触发。
- 处理 SSP `PAIRING_VARIANT_PASSKEY_CONFIRMATION`，手机侧静默确认；相机侧仍由用户按 `OK`。
- 配对请求确认失败时不强行中止系统广播，避免流程卡死。

**当前目标表现**

理想结果是用户不会看到竞争性的系统配对码窗口；但当前仍需真机确认 pairing variant 和 `setPairingConfirmation()` 返回值，不能把该结果写成已保证。

**状态**：重复发起问题有日志证据；系统弹窗抑制逻辑已在本地实现，但不同 Android 版本的 pairing variant 和确认结果仍需真机验证。

### P1（用户已报告，根因待日志确认）：息屏时状态与底层连接可能短暂不一致

**现象**

相机息屏后 App 显示“正在连接”或状态反复跳变。

**已知与推断分开**

- 已知：用户报告息屏后出现“正在连接/已开启”状态异常。
- 推断：息屏可能导致 GATT 短断链；当前日志只有 `status=19`，没有 Android 断开原因与屏幕状态的关联证据。

**修复方案**

- 已配对身份（deviceId、nonce）永不因普通息屏断链清除。
- `onDisconnected()` 只清当前 GATT、定位监听和待发送缓存，随后重连。
- 之前已经 `READY` 的连接会设置保留标记，后台扫描回退期间保持 READY 视觉；通知显示“连接已断开，正在重连”。重连失败后再显示错误或重试状态。
- 恢复后首个有效定位立即重新写入。

**当前可保证的行为（服务仍存活时的代码层面）**

息屏不会主动清除已保存身份，也不会要求用户停留在连接页；相机恢复蓝牙后服务会继续尝试重连。是否自动回到“已开启”取决于 GATT/ID/GEO 是否完整恢复，需真机验证。

**状态**：已增加 READY 视觉保持和身份保留；“息屏是否必然触发短断链”以及重连失败/恢复时序仍需真机验证。

### P1（已简化，仍需验证）：位置更新策略的功耗权衡

**当前实现**

- GPS 回调约 5 秒一次，网络定位约 15 秒一次。
- 不再使用距离阈值；首个有效 fix 立即写入。
- 后续位置最短间隔 60 秒写入一次。

**已完成的简化**

- 去掉距离判断，避免定位精度抖动导致额外分支。
- 将写入间隔统一为 60 秒，降低 BLE 唤醒和 GEO 写入频率。
- 定位监听仍保留 GPS/网络双来源，以保证首个有效 fix 的到达速度。

**后续验证**

- 首个有效 fix：立即写入。
- 正常运行：距离上次成功写入达到 60 秒时写入，不再判断移动距离。
- 当前 `maybeSend()` 在写入进行中直接返回，不会为每次定位回调排队。
- 重连成功后首个 fix 立即写入。
- 连续失败使用 5/15/30 秒退避，不立即高频重试。

**修复后的样子**

用户无感，照片仍能获得足够新鲜的位置；静止拍摄时明显减少 BLE 和定位写入开销。

**状态**：已改为 60 秒固定间隔并移除距离判断；仍需采集功耗、移动轨迹和照片覆盖率确认体验。

### P1：通知正文原来是固定文本

**现象**

无论连接、断开还是写入失败，通知都显示“自动写入相机位置”。

**修复方案**

通知只保留必要信息：

| 场景 | 通知内容 |
| --- | --- |
| 已成功写入 | 位置已更新 · HH:mm |
| 正常运行 | 已连接，自动写入位置 |
| 重连中 | 连接已断开，正在重连 |
| 写入失败 | GPS 写入失败 |
| 寻找/配对/确认 | 正在连接相机 |

配对码、配对成功、内部地址等都不展示。

**状态**：已在本地实现，未推送。

### P1（已排除代码缺陷）：原始下载/导出丢失 GPS EXIF

**核查结论**

- 原始文件下载由 PTP 数据直接写入 SAF 临时文件，随后只做改名或字节复制；AP/STA 使用同一条原始文件保存路径，不会主动删改 EXIF。
- 派生边框/滤镜图会显式复制 GPS 经纬度、海拔、时间等 EXIF 标签；个别不支持可写 seekable FD 的云端 DocumentsProvider 可能无法写入派生图 EXIF，但不会影响原始文件。
- 因此目前没有发现“导出逻辑必然丢失 GPS”的代码缺陷。若原片无 GPS，应优先检查拍摄前是否出现 `GEO GATT write success`，再用 EXIF 工具检查原片。

**状态**：代码审查已排除明确缺陷；仍需真机完成“写入 → 拍摄 → 原片导出 → EXIF 检查”的端到端验证。

### P1：App 被杀、强行停止、ROM 后台限制需要区分

**当前行为**

- 普通退后台、锁屏、移除最近任务：按 Manifest 和前台服务配置，具备继续运行条件。
- 系统回收进程：`START_STICKY` + 已保存开关具备恢复条件，但是否恢复由系统和 ROM 决定。
- 用户强行停止 App：系统不会自动重启服务。
- 部分 ROM 禁止后台或电池限制过严：服务可能被杀。

**修复/产品方案**

- 不要求用户把 Z 传锁在连接页。
- 只在必要时提示“允许后台运行/电池不受限”。
- 强行停止后，用户重新打开 App 或重新开启 GPS。
- 手机蓝牙关闭时暂停 BLE、定位和重试；用户确认系统“打开蓝牙”后自动恢复。

**状态**：前台服务和 START_STICKY 已存在；已增加蓝牙开关监听和暂停/恢复逻辑。Android 新版本只能发起系统确认弹窗，不能无提示强开蓝牙；本文不把“服务一定会存活”写成系统保证。

### P2：AP 模式与 GPS 不兼容

**事实**

AP 模式下相机不能把 BLE GPS 位置用于照片；当前代码没有在 STA/USB 状态主动阻断 GPS，但“STA/USB 与 GPS 必然共存”仍不是协议层结论。

AP 限制依据尼康 SnapBridge 官方说明：[AP 模式限制](https://nikonimglib.com/snbr/onlinehelp/en/direct_wifi_connection_5.html)、[在照片中嵌入位置数据](https://nikonimglib.com/snbr/onlinehelp/en/embedding_location_data_in_pictures_27.html)。STA/USB 共存属于当前代码链路推导，仍需跨机型实测，不把它写成官方保证。

**方案**

- AP 模式：GPS 显示“AP 模式不可用”，停止 BLE 和定位。
- STA/USB：当前按独立服务运行；是否与文件传输链路在所有机型上稳定共存，需做并行传输实测。
- 从 AP 切出后，如果 GPS 开关仍开，自动恢复。

**状态**：已有 AP blocked 分支；需继续做三种连接方式的实机回归。

## 四、当前是否存在无用请求或多余等待

### 必须保留

- MTU 协商：一次；失败后降级发现服务。
- PAIR/NOT1 CCCD：协议必需，串行等待回调。
- stage1~4：协议必需，不能合并猜测。
- ID 写入：是 `onReady` 的必要证据。
- GEO 写入回调：是当前实现收到的 GATT 层成功回执，不等同于已验证照片元数据。

### 可以优化

1. **stage4 后固定 1.5 秒等待**：这是代码中的固定等待，但没有协议或日志证据证明它过长。只能作为 A/B 测试项，不能直接判定为浪费。
2. **Classic 发现 30 秒窗口**：这是兼容性设计，当前没有证据证明它造成明显性能问题；首次配对应先保留，失败后停止当前窗口。
3. **失败重试**：当前错误路径固定约 5 秒重试；蓝牙关闭时已暂停，其他失败是否改为 5/15/30 秒退避，需要结合功耗和恢复时间继续验证。
4. **定位回调与 GEO 写入解耦**：降低定位监听频率不应影响首个 fix 和重连首写。

## 五、推荐的最终状态机

```text
OFF
  → STARTING
  → SEARCHING                 （无完整身份）
  → PAIRING                   （stage1~3）
  → CAMERA_CONFIRM            （等待相机 OK）
  → CONNECTING                （Classic 完成或已配对重连，包含 ID 确认）
  → WRITING                   （GEO 写入中）
  → READY / 已开启            （GEO 成功）

READY --息屏/短断链--> 保持 READY 视觉 + 后台重连（失败则 ERROR/重试）
READY --写入失败------> ERROR/重试
任意连接状态 --AP 模式--> AP_UNAVAILABLE
```

核心原则：

- `CONNECTED` 只表示链路可用。
- `READY` 表示 App 已收到 GEO 的 GATT 层成功回执；照片元数据是否最终落盘，必须通过拍摄和导出验证。
- 不允许用 Classic bond、stage4 或 ID 入队替代 GEO 成功。

## 六、验收顺序

1. 已配对重连：确认日志完整出现 `stage4 → ID queued → GATT write → GPS ready → GEO write success`。
2. 相机息屏 5 分钟：不重新配对，恢复后自动写入位置，地址和更新时间继续显示。
3. 相机关闭/打开蓝牙：通知从“正在重连”恢复到“已连接，自动写入位置”。
4. 首次配对：系统不弹竞争性配对码窗口，相机按 OK 后完成配对。
5. 写入失败：通知显示失败，不能显示“已开启”，重试有退避。
6. 对 60 秒固定间隔做功耗、位置新鲜度和照片覆盖率回归，必要时再调整。

## 七、本轮变更边界

- 已完成：为活动握手增加 4.5 秒直连超时保护；通知状态动态化；恢复 `onReady` 后才启动定位；增加关键 GATT/ID 日志。
- 未完成：蓝牙关闭/恢复的完整真机回归、完整真机息屏回归，以及 60 秒位置策略的数据验证。
- 本轮文档审查未重新打包；代码改动是否通过真机回归，以后续带有完整诊断日志的测试为准。
