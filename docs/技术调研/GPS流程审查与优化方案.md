# GPS 配对、重连与位置更新：问题清单与优化方案

> 审查基线：`research/gps` 分支，2026-08-30。  
> 目标：用户只看到一个“开启 GPS”开关；配对、重连、定位和写入尽量自动，状态真实、请求最少、失败可恢复。

## 一、最终结论

当前 GPS 主链路已经具备可用基础，但有三个必须优先守住的边界：

1. **BLE 握手完成不等于 GPS 已就绪**。必须完成 ID 写入回调，启动定位，再以 GEO 写入成功作为最终闭环。
2. **相机息屏是可恢复的短断链，不应当被当成配对失败**。保留已配对身份，停止当前 GATT 和待写缓存，按退避策略重连。
3. **位置更新不应按每次定位回调写入**。当前“移动 3 米或 20 秒”偏频繁，建议下一轮改成“移动 10 米或 60 秒”，重连后的首个 fix 立即写入。

## 二、用户看到的正确流程

### 1. 首次使用

用户操作只有：

1. 相机进入“连接至智能设备 → 配对（Bluetooth）→ 开始配对”。
2. App 点击“开启 GPS”。
3. 相机显示确认时，用户在相机上按 `OK`。

App 状态应严格按下面顺序流转：

```text
正在寻找
  → 正在配对
  → 相机请按 OK
  → 正在连接
  → GPS 写入中
  → 已开启
```

说明：首次配对成功字样可以短暂显示，但不能在相机尚未确认或 GEO 尚未写入成功前显示“已开启”。

### 2. 已配对后的后续连接

用户只需：

1. 相机开启蓝牙。
2. App 点击“开启 GPS”。

App 自动完成：

```text
正在连接
  → ID 写入确认
  → GPS 写入中
  → 已开启
```

不再重复 Classic 配对，不再展示配对步骤。

### 3. 相机息屏或短暂断链

```text
已开启
  → 连接暂时中断
  → 正在重连
  → GPS 写入中
  → 已开启
```

页面可以保持“已开启”的稳定视觉，避免相机息屏时按钮闪成错误状态；前台通知显示“连接已断开，正在重连”。恢复后重新写入一次位置。

## 三、问题逐项清单

### P0：把 stage4 当成 GPS 已连接会造成“有状态、无位置”

**现象**

相机显示已连接，App 也显示已连接，但没有地址和更新时间。

**根因**

`stage4` 只证明 BLE 协议握手完成。当前定位监听是在 `onReady()` 中启动，而 `onReady()` 还要求 ID 特征写入回调成功。若提前把 stage4 映射成 `CONNECTED`，定位监听不会启动，GEO 也不会发送。

**修复方案**

- 保持 `stage4 → ID write → onReady → startLocationUpdates → GEO write` 顺序。
- 首次连接和已配对重连都不能跳过 ID 写入确认。
- `READY/已开启` 只由首个 GEO 写入成功触发。

**修复后的样子**

```text
stage4 received
  → ID queued
  → GATT write ID success
  → GPS ready
  → GEO write success
  → 已开启 + 地址 + 更新时间
```

**状态**：已恢复安全边界；已增加 ID 入队和 GATT 写入日志。

### P0：直连 4.5 秒超时会误杀正在进行的握手

**现象**

日志已经出现 `stage3 sent`、`stage4 received`，随后仍然 GATT `status=19`，App 一直“正在连接”。

**根因**

直连计时器只看 `ready=false`。握手期间 `ready` 本来就是 false，4.5 秒计时器可能关闭正在写 ID 的 GATT。

**修复方案**

- 只有在尚未发送 stage3 时允许直连超时并 fallback scan。
- 一旦 stage3 已发送，必须让当前握手完成，交给 ID 写入超时或 GATT 断开处理。

**修复后的样子**

不会再出现“握手已经开始，但被短超时强制关闭”；只有真正卡在服务发现/握手开始前才切扫描。

**状态**：已在本地实现并编译通过。

### P0：Classic bond 重复删除/重复 createBond，触发系统配对码弹窗

**现象**

日志出现多次：

```text
Classic stale bond remove=true
Classic createBond after removal=true
Classic stale bond remove=true
Classic createBond after removal=true
```

随后 Android 弹出系统配对窗口，并提示配对码错误。

**根因**

- `removeBond()` 是异步的，轮询可能在 bond 状态真正变为 `BOND_NONE` 前再次认定 bond 过期。
- 同一设备被重复发起 `createBond()`。
- `ACTION_PAIRING_REQUEST` 未被正确处理时，Android 系统 UI 会与相机端确认流程竞争。

**修复方案**

- 增加单次 `classicBondAttemptAddress`，同一时间只允许一个 `createBond()`。
- `BOND_NONE` 后对同一 Classic 地址只重试一次，不再由轮询重复触发。
- 处理 SSP `PAIRING_VARIANT_PASSKEY_CONFIRMATION`，手机侧静默确认；相机侧仍由用户按 `OK`。
- 配对请求确认失败时不强行中止系统广播，避免流程卡死。

**修复后的样子**

用户不会看到竞争性的系统配对码窗口；相机端确认一次即可完成 Classic bond。失败后停止当前尝试，不刷屏、不循环弹窗。

**状态**：已在本地实现；需真机确认不同 Android 版本的 pairing variant。

### P1：息屏时状态与底层连接可能短暂不一致

**现象**

相机息屏后 App 显示“正在连接”或状态反复跳变。

**根因**

息屏可能导致 GATT 短断链。若把短断链直接映射为错误，或在握手中间阶段提前改状态，就会产生错误动画；同时清理时机不当还会丢失重连所需的身份。

**修复方案**

- 已配对身份（deviceId、nonce）永不因普通息屏断链清除。
- `onDisconnected()` 只清当前 GATT、定位监听和待发送缓存，随后重连。
- 之前已经 `READY` 的连接，页面保持稳定的“已开启”；通知显示“连接已断开，正在重连”。
- 恢复后首个有效定位立即重新写入。

**修复后的样子**

息屏不会导致用户重新配对，也不会要求用户停留在连接页；相机恢复蓝牙后自动回到“已开启”。

**状态**：原有保持 READY/自动重连逻辑已保留；需真机锁屏 5 分钟验证。

### P1：位置更新策略偏频繁

**当前实现**

- GPS 回调约 5 秒一次，网络定位约 15 秒一次。
- 移动达到 3 米立即写入。
- 未移动时最长 20 秒写入一次。

**问题**

对照片地理标记来说，20 秒周期和 3 米阈值偏激进，会增加 BLE 唤醒、GEO 写入和功耗；定位回调频繁不代表必须频繁写入。

**修复方案（下一轮，不在本轮改变）**

- 首个有效 fix：立即写入。
- 正常运行：移动 ≥ 10 米，或距离上次成功写入 ≥ 60 秒时写入。
- 写入进行中只保留最新 pending，不排队堆积。
- 重连成功后首个 fix 立即写入。
- 连续失败使用 5/15/30 秒退避，不立即高频重试。

**修复后的样子**

用户无感，照片仍能获得足够新鲜的位置；静止拍摄时明显减少 BLE 和定位写入开销。

**状态**：尚未改动，等待你确认参数后实施。

### P1：通知正文原来是固定文本

**现象**

无论连接、断开还是写入失败，通知都显示“自动写入相机位置”。

**修复方案**

通知只保留必要信息：

| 场景 | 通知内容 |
| --- | --- |
| 已成功写入 | 位置已更新 · HH:mm |
| 正常运行 | 已连接，自动写入位置 |
| 重连中 | 连接已断开，正在重连 |
| 写入失败 | GPS 写入失败 |
| 寻找/配对/确认 | 正在连接相机 |

配对码、配对成功、内部地址等都不展示。

**状态**：已在本地实现，未推送。

### P1：App 被杀、强行停止、ROM 后台限制需要区分

**当前行为**

- 普通退后台、锁屏、移除最近任务：前台服务继续运行。
- 系统回收进程：`START_STICKY` + 已保存开关通常可以恢复。
- 用户强行停止 App：系统不会自动重启服务。
- 部分 ROM 禁止后台或电池限制过严：服务可能被杀。

**修复/产品方案**

- 不要求用户把 Z 传锁在连接页。
- 只在必要时提示“允许后台运行/电池不受限”。
- 强行停止后，用户重新打开 App 或重新开启 GPS。
- 相机关闭蓝牙期间暂停无效高频扫描；蓝牙恢复后再尝试连接。

**状态**：前台服务和 START_STICKY 已存在；蓝牙开关监听与退避扫描可作为下一轮优化。

### P2：AP 模式与 GPS 不兼容

**事实**

AP 模式下相机不能把 BLE GPS 位置用于照片；STA 与 USB 可以和 GPS 并行。

**方案**

- AP 模式：GPS 显示“AP 模式不可用”，停止 BLE 和定位。
- STA/USB：GPS 独立运行，不与文件传输链路抢占资源。
- 从 AP 切出后，如果 GPS 开关仍开，自动恢复。

**状态**：已有 AP blocked 分支；需继续做三种连接方式的实机回归。

## 四、当前是否存在无用请求或多余等待

### 必须保留

- MTU 协商：一次；失败后降级发现服务。
- PAIR/NOT1 CCCD：协议必需，串行等待回调。
- stage1~4：协议必需，不能合并猜测。
- ID 写入：是 `onReady` 的必要证据。
- GEO 写入回调：是“相机真正接受位置”的最终证据。

### 可以优化

1. **stage4 后固定 1.5 秒等待**：当前最可疑。可实测缩短到 100~300ms，或由 NOT1 事件触发 ID 写入。
2. **Classic 发现 30 秒窗口**：首次配对保留兼容性；失败后停止，不要无限循环。
3. **失败重试**：从固定 5 秒改为 5/15/30 秒退避，蓝牙关闭期间不扫描。
4. **定位回调与 GEO 写入解耦**：降低定位监听频率不应影响首个 fix 和重连首写。

## 五、推荐的最终状态机

```text
OFF
  → STARTING
  → SEARCHING                 （无完整身份）
  → PAIRING                   （stage1~3）
  → CAMERA_CONFIRM            （等待相机 OK）
  → CONNECTING                （Classic 完成或已配对重连）
  → WRITING                   （GEO 写入中）
  → READY / 已开启            （GEO 成功）

READY --息屏/短断链--> READY（视觉保持）+ 后台重连
READY --写入失败------> ERROR/重试
任意连接状态 --AP 模式--> AP_UNAVAILABLE
```

核心原则：

- `CONNECTED` 只表示链路可用。
- `READY` 才表示位置已经成功写入相机。
- 不允许用 Classic bond、stage4 或 ID 入队替代 GEO 成功。

## 六、验收顺序

1. 已配对重连：确认日志完整出现 `stage4 → ID queued → GATT write → GPS ready → GEO write success`。
2. 相机息屏 5 分钟：不重新配对，恢复后自动写入位置，地址和更新时间继续显示。
3. 相机关闭/打开蓝牙：通知从“正在重连”恢复到“已连接，自动写入位置”。
4. 首次配对：系统不弹竞争性配对码窗口，相机按 OK 后完成配对。
5. 写入失败：通知显示失败，不能显示“已开启”，重试有退避。
6. 最后再调整 3m/20s 参数，并比较功耗、位置新鲜度和照片覆盖率。

## 七、本轮变更边界

- 已完成：连接握手不被 4.5 秒直连超时误杀；通知状态动态化；恢复 `onReady` 后才启动定位；增加关键 GATT/ID 日志。
- 未完成：位置更新频率调整、蓝牙适配器状态监听、完整真机息屏回归。
- 提交策略：先本地编译和真机验证；确认通过后再一次性推送。
