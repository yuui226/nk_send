## 2. 审查范围

完整链路如下：

```text
连接相机
  -> 获取 StorageID / ObjectHandle / ObjectInfo
  -> 渐进发布照片列表
  -> 日期、类型、连拍、已传状态计算
  -> LazyVerticalGrid 展示
  -> 内存/磁盘/相机缩略图加载
  -> 用户加入传输队列
  -> 检查 SAF 目标目录与断点文件
  -> PTP/IP 或 USB 流式读取
  -> SAF 缓冲写入、进度传播
  -> 原片完成
  -> 可选边框/滤镜派生导出
```

## 3. 当前实现中应保留的设计

以下方向正确，不建议在整改中推翻：

- PTP 命令严格串行，并为交互请求设置优先级。
- 原片直接流式写入目标输出流，不把整个文件装入内存。
- Wi-Fi/USB 会按连接类型和文件大小选择整文件或分块传输。
- 传输进度约每 200ms 上报一次，避免逐数据块刷新 UI。
- 同一缩略图请求会合并，存在内存 LRU、磁盘缓存和无缩略图负缓存。
- 后台缩略图预取只写磁盘，不冲刷前台内存 LRU。
- 传输、遥控和 FHD 操作会暂停部分后台缩略图工作。
- SAF 输出使用较大缓冲区。
- 传输期间使用前台服务、WakeLock 和 WifiLock 保持运行环境。
- 派生图片的输入侧已经使用区域解码，避免整张原图同时解码。

## 5. 详细问题

### PERF-001：传输生命周期与断点续传语义不完整

**优先级：P0｜状态：待讨论**

#### 证据

- 前台服务注释明确说明传输仍由 ViewModel 协程驱动：[`TransferService.kt:19`](../../app/src/main/java/com/ztransfer/service/TransferService.kt#L19)。
- 队列任务运行在 `viewModelScope`：[`TransferViewModel.kt:1115`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L1115)。
- `onCleared()` 会取消任务：[`TransferViewModel.kt:2090`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L2090)。
- 启动时以 `deleteParts=true` 扫描目标目录：[`TransferViewModel.kt:735`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L735)。
- 遗留 `.nkpart_` 会被删除：[`TransferViewModel.kt:1668`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L1668)。

#### 影响

- Activity/ViewModel 真正销毁或进程崩溃后，当前下载及队列无法继续。
- 虽然普通失败会保留半成品，但下次启动会删除它，跨进程断点续传实际上不存在。
- 大文件已经传输的字节可能全部浪费。
- 启动清扫与快速重试可能并发操作同一半成品。

#### 候选方案

1. 将传输 worker 和队列所有权移入前台 Service 或 application 级 repository。
2. 持久化任务、文件 identity、目标 URI、part 名称和已完成 offset。
3. 只按 identity 与 TTL 删除确定的孤儿文件，不在启动时统一删除。

#### 验证要求

- 传输 1GB 文件至约 30%，结束 Activity、划掉任务或杀进程。
- 重启后必须从已有 offset 继续，而不是从 0 开始。
- 不得出现真名残缺文件、重复副本或错误复用其他照片的 part。

- 待讨论。

### PERF-002：渐进扫描触发累计超线性工作

**优先级：P1｜状态：已完成（最小范围）**

#### 原问题

- 扫描每取得 20 张 ObjectInfo 就通过完整前缀列表发布一次；旧实现每批复制此前所有文件引用。
- 页面收到每批更新后的其他全表派生计算继续归入 `PERF-003` / `PERF-009`，本次不改 UI，避免扩大风险面。

10,000 张照片、每批 20 张时，仅完整列表发布就累计复制约 2,505,000 个引用，尚未计算 UI 端排序和临时对象。

#### 已完成方案

1. 保留原有 `allFiles`、双卡去重和批次合并逻辑，只把每批末尾的 `allFiles.toList()` 替换为 `BatchPublishedList`。
2. 列表按 256 项分块；发布下一批时只复制块索引、受影响块和尾块，旧快照保持不可变，不再复制此前全部文件引用。
3. 列表相等判断先比较长度；常见追加批次在 `StateFlow` 发布时无需再遍历整个旧列表。

#### 体验与协议保持不变

- `streamFileInfo` / `streamMergedFileInfo` 仍按每批 20 张释放相机锁并立即发布；没有增加 100～200ms 合并窗口、debounce 或递增批次，因此首批出现速度和后续照片逐批出现的节奏不变。
- StorageID、ObjectHandle、ObjectInfo 的请求次数、顺序、PTP 事务及 `ioMutex` 粒度均未改变；本项只替换收到批次后的内存快照表示。
- 文件顺序、日期分组、筛选、连拍合集、双卡去重、实时新增及缩略图网格的用户语义保持不变。
- `FileListScreen` 没有任何代码改动。

#### 验证结果

- 定向测试 `BatchPublishedListTest` 已通过，覆盖连续 20 项批次、块边界替换、追加、旧快照不可变、内容相等语义和空批次复用。
- 完整 `:app:testDebugUnitTest` 已通过；`:app:lintDebug` 也已通过。
- 仓库规定的 `dist-debug/build-debug.bat` 已成功生成可安装 Debug APK。
- 10,000 项、每批 20 项的确定性复制量核算：旧方案累计复制 2,505,000 个完整列表元素引用；新方案包含新增暂存、尾块重建和块索引复制约 176,024 次引用写入，减少约 93.0%。
- 同一开发机 JVM 微基准（5 次预热、15 次取中位数）中，仅快照构建由 2.812ms 降至 0.230ms，约 12.2 倍；该数据不代表手机端总扫描耗时，PTP IO 与 UI 派生不在测量范围内。
- UI 派生计算没有在本项中宣称完成，后续必须按 `PERF-003` / `PERF-009` 单独评估和修改。

### PERF-003：后台预取争抢相机通道

**优先级：P1｜状态：已完成**

#### 证据

- 全库缩略图填充监听完整 `files` 并使用 `collectLatest`：[`CameraViewModel.kt:888`](../../app/src/main/java/com/ztransfer/viewmodel/CameraViewModel.kt#L888)。
- 每次新增一批文件都会重新排序并从列表头遍历。
- 首批文件出现约 600ms 后，会自动请求一张效果演示用 FHD 和 EXIF：[`CameraViewModel.kt:931`](../../app/src/main/java/com/ztransfer/viewmodel/CameraViewModel.kt#L931)、[`CameraViewModel.kt:970`](../../app/src/main/java/com/ztransfer/viewmodel/CameraViewModel.kt#L970)。
- 该 FHD 预取没有等待 `isLoadingFiles=false` 或完整扫描完成。

#### 影响

- 用户可能永远不打开效果页，但 FHD/EXIF 仍会占用单一 PTP 通道。
- 全库 sweep 会在每个 20 文件批次取消、排序、重启。
- 可见缩略图、ObjectInfo 枚举和后台任务互相增加首屏及完整扫描延迟。
- 全库预取还会增加相机耗电、网络流量和手机闪存写入。

#### 候选方案

1. 文件扫描期间只允许可见缩略图请求。
2. 全库预取延迟到扫描完成且持续空闲后；优先只预取视口前后窗口。
3. 效果预览 FHD 改为用户进入相关页面后才加载。
4. 统一为优先级调度器：可见缩略图 > 用户预览 > 后台缓存。

#### 验证要求

- 统计 1k/10k 文件下 sweep 重启次数、GetThumb 取消次数和重复请求率。
- 对比开启/关闭后台任务时的首屏缩略图时间与完整扫描时间。

### PERF-004：磁盘缩略图缓存策略不完整

**优先级：P1｜状态：已完成**

#### 最终实现

- 移除 64MB 上限和 LRU 淘汰，已成功缓存的缩略图完整保留。
- 按相机稳定物理身份分目录，避免不同相机的同名照片互相命中；旧版扁平缓存命中时懒迁移，不造成升级后全量重下。
- APP 启动时清理超过 90 天未成功连接的相机缓存；近期相机不按空间大小淘汰。
- 当前相机只有在存储卡 handle 和全部 ObjectInfo 都完整成功后，才清理已明确不在卡上的缓存；断连、超时、失败或中断均不删除。
- 缓存写入采用临时文件加同目录原子改名，只有文件真实完整落盘后才更新索引并报告成功。
- 本次连接发生磁盘写入失败后停止后台全库落盘，避免磁盘满时持续重试；可见缩略图仍正常从相机获取和展示，下次连接重新尝试。

#### 验证结果

- 单元测试覆盖相机隔离、90 天清理边界、当前图库同步、旧缓存迁移、失败写入不污染索引和稳定哈希键。
- Debug Kotlin 编译通过；完整单元测试和 Lint 结果见本文“当前验证基线”。

### PERF-005：传输进度导致全队列复制和整页失效

**优先级：P1｜状态：已完成**

#### 最终实现

- 将唯一活动下载的百分比、字节数和速度拆到独立 `StateFlow<ActiveTransferProgress?>`；约 200ms 的协议回调只替换一个常量大小对象，不再复制 `TransferState.tasks`。
- `TransferState` 只在任务开始、完成、失败、取消等低频节点变化，设置、筛选、目录索引和无关页面不会被进度回调连带失效。
- 传输页只有当前任务卡订阅高频进度；照片页只有当前照片的进度环订阅；顶部队列胶囊独立订阅并复用低频任务摘要，高频刷新不扫描完整队列，其余照片格子不重组。
- 增加专用 `PendingTransferQueue`，按插入顺序 O(1) 取得下一任务；已完成历史不再让调度累计退化为 O(Q²)。
- 终态任务仍保存最终进度与已下载字节，完成速度统计、失败续传、取消和重试的用户体验保持不变。

#### 验证结果

- 单元测试覆盖活动进度只合并到匹配任务、待传顺序、队列撤回及预检查期间取消。
- Debug Kotlin 编译通过；完整单元测试和 Lint 结果见本文“当前验证基线”。

### PERF-006：SAF 目录索引重复扫描及 O(Q×D) 查找

**优先级：P1｜状态：待讨论**

#### 证据

- App 初始化、切换目录和每个独立队列启动都可能完整扫描目录：[`TransferViewModel.kt:735`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L735)、[`TransferViewModel.kt:1055`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L1055)、[`TransferViewModel.kt:1162`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L1162)。
- 精确文件名未命中时，每个任务遍历全部目录项查找 `"(n)"` 副本：[`TransferViewModel.kt:1799`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L1799)。
- 每完成一个文件，通过 `existingExportFiles + entry` 复制完整 Map：[`TransferViewModel.kt:1087`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L1087)。

#### 影响

- Q 个任务、D 个目标文件时，副本查找可退化为 O(Q×D)。
- SAF/云端 Provider 的目录 query 可能成为开始下载前的主要等待。
- 用户逐张加入并等待队列清空时，可能为每张照片重新扫描整个目录。

#### 候选方案

1. 按目录 URI 建立单飞、可复用的 DirectoryIndex repository。
2. 扫描时同时构建 exactName 与 normalizedBaseName 两级索引。
3. 传输完成时增量更新索引，只发布 delta 或版本号。
4. 通过显式失效或 ContentObserver 控制重扫，而不是每个队列无条件重扫。

#### 验证要求

- 目标目录放置 10,000 个文件，分别加入 1、100、1,000 个新任务。
- 记录 Provider query 次数、首字节等待时间和文件匹配 CPU。

### PERF-007：双路全分辨率派生导出的内存峰值

**优先级：P1｜状态：待讨论**

#### 证据

- 派生导出固定并发为 2：[`TransferViewModel.kt:86`](../../app/src/main/java/com/ztransfer/viewmodel/TransferViewModel.kt#L86)。
- 每个任务仍创建完整尺寸 ARGB\_8888 输出 Bitmap：[`PhotoFrameExporter.kt:2380`](../../app/src/main/java/com/ztransfer/frame/PhotoFrameExporter.kt#L2380)。
- 区域解码只约束输入 tile，没有消除完整输出画布。

45MP（8256×5504）图片仅一张原尺寸 ARGB 输出约为 173MiB；两个并发输出约 347MiB，尚未计算 tile、JPEG 编码、缩略图缓存和 UI。

#### 影响

- 低/中内存设备可能发生频繁 Full GC、严重吞吐下降甚至 OOM。
- 两个派生任务还会与下一张原片下载争抢内存和存储带宽。
- 捕获 `OutOfMemoryError` 只能兜底，不能避免分配前的 GC 抖动。

#### 候选方案

1. 按 `canvasWidth × canvasHeight × 4` 申请加权内存许可证。
2. 大图强制串行，小图才允许并行。
3. 原片传输活跃或内存压力较高时降为 1 worker。
4. 若编码器能力允许，进一步评估分块/流式输出编码。

#### 验证要求

- 连续导出 10 张 24MP 和 45MP 图片。
- 对比 1/2 worker 的 PSS、GC、OOM、原片 MB/s、总完成时间和温升。

### PERF-009：照片页存在不必要的全表派生计算

**优先级：P2｜状态：待讨论**

#### 现象

- 每完成一张传输，`existingExportFiles` 改变。
- 即使没有开启“只看未传输”，日期分组仍把已传集合放进 `remember` key，触发全表过滤、分组和排序。
- cell 坐标 HashMap 会记录所有浏览过的 handle，滚出后不移除：[`FileListScreen.kt:317`](../../app/src/main/java/com/ztransfer/ui/screen/FileListScreen.kt#L317)。
- 多处使用 `collectAsState()` 而不是生命周期感知收集。
- 照片与连拍集合共用同一 lazy `contentType`，不利于复用正确的组合结构。

#### 候选方案

- 未启用未传过滤时，让展示分组完全不依赖 exported 集合。
- 已传绿勾按 handle 增量更新。
- cell dispose 时删除坐标，或根据 `LazyGridLayoutInfo` 临时计算。
- 改为 `collectAsStateWithLifecycle()`，并订阅最小状态切片。
- 为普通照片和连拍集合设置不同 `contentType`。

### PERF-010：热路径多余分配和内存复制

**优先级：P2｜状态：待讨论**

已确认的小型热点：

- 磁盘缩略图先 `readBytes()` 再解码，多一次压缩数据 ByteArray。
- 缩略图缓存键每次构造 Regex。
- `FileInfo.extension` 每次访问都执行 substring/lowercase。
- 黑边裁切可能短时间保留多张替代前 Bitmap。
- 两个 `PacketReader` 创建时各自立即分配 1MB 缓冲：[`NikonCamera.kt:210`](../../app/src/main/java/com/ztransfer/protocol/NikonCamera.kt#L210)。
- PTP/IP 小图/FHD 路径存在 payload、ByteArrayOutputStream 和 `toByteArray()` 多次复制。
- USB 路径存在 direct buffer 到中间数组再到输出缓冲的复制。

候选方案：预计算文件扩展名和缓存 key、预编译 Regex、延迟创建 PacketReader 缓冲、磁盘直接解码，并用 Allocation Profiler 判断协议复制是否值得进一步重构。

### PERF-011：USB 64KB 请求可能限制吞吐

**优先级：P2｜状态：待讨论｜注意：目前仅为测量假设**

文件传输虽有较大的上层 `ioBuffer`，但 `UsbRequest` 读取请求固定为 64KB：[`UsbPtpConnection.kt:373`](../../app/src/main/java/com/ztransfer/protocol/UsbPtpConnection.kt#L373)。这可能增加 requestWait 频率和复制次数，但不同设备/USB 栈表现差异很大，不能仅凭代码直接修改。

验证要求：同一设备和文件分别测试 64KB、256KB、1MB；同时记录吞吐、CPU、稳定性和取消延迟。只有数据证明有收益后才调整。

### PERF-012：枚举失败可能被伪装成空卡

**优先级：P1｜状态：待讨论**

`getStorageIds()` 和 `getObjectHandles()` 的部分异常路径会返回空列表，上层可能把它当作扫描成功的合法空结果。虽然主要是正确性/可靠性问题，但它会触发错误状态、无意义的恢复操作，并掩盖真实协议性能故障。

候选方案：明确区分合法空卡、PTP 非 OK、传输超时和连接断开；后几类应进入可观测的重试/重连流程。

### PERF-013：缺少性能回归门槛

**优先级：P1｜状态：待讨论**

仓库已有较完整的功能单元测试，但尚未发现以下性能设施：

- Macrobenchmark。
- Baseline Profile。
- JankStats 或稳定的 Compose 重组统计。
- 大图库/大队列基准。
- 分阶段 Trace：相机锁等待、网络读取、SAF 写入、目录 query、图片解码、GC、状态更新时间。

建议建立至少以下门槛：

| 场景       | 规模                 | 核心指标                            |
| -------- | ------------------ | ------------------------------- |
| 冷连接与列表扫描 | 1k / 10k / 30k 文件  | 首批内容、首屏缩略图、完整扫描时间、分配量           |
| 快速滚动     | 10k / 30k 文件       | P50/P95/P99 帧耗时、卡顿帧、重复 GetThumb |
| 传输队列     | 100 / 1k / 10k 任务  | 进度回调耗时、分配量、重组范围                 |
| SAF 目录   | 1k / 10k 文件        | query 次数、首字节等待、匹配 CPU           |
| 大文件交互    | Wi-Fi / USB，1GB 文件 | MB/s、预览请求等待、取消延迟                |
| 派生导出     | 24MP / 45MP        | PSS、GC、OOM、总耗时、温升               |
