## 先读这一页

这套调度器只解决一个问题：多个功能同时需要向相机发送 PTP 命令时，谁能取得唯一的相机命令通道。

手机本地的缩略图缓存命中、图片解码、Compose 绘制、文件写入、照片效果生成可以在不同协程或线程中进行；它们不因为进入本地线程池就自动获得相机通道，也不会与相机命令并行写同一条 PTP 命令流。

因此，“评级和缩略图并行”准确的含义是：两个手机任务可以同时等待、解析或命中本地缓存；需要访问相机时，各自提交一个有明确优先级的短事务，由调度器在完整事务之间切换。相机端仍然一次只处理一个命令事务。

本文分为四类内容：

1. **当前实现事实**：代码现在实际做什么。
2. **让路规则**：每种请求在什么条件下可以入场、会被谁挡住。
3. **生命周期与异常**：取消、断线、关闭和重新连接如何清理。
4. **复刻契约与验证边界**：iOS 必须保持什么，哪些仍需协议或真机验证。

如果本文与旧的“待做”方案描述不一致，以本文和当前源代码为准。本文不把尚未实现的公平调度、时间片抢占或实时星级变更追踪写成现有能力。

## 1. 相机通道模型

### 1.1 唯一的运行期命令入口

`NikonCamera` 持有一个私有 `CameraIoGate`。所有已建立会话后的业务命令通过以下统一入口提交：

```kotlin
suspend fun <T> withCameraTransaction(
    kind: CameraRequestKind,
    owner: String,
    block: suspend () -> T,
): T
```

入口在 `CameraIoGate` 内部完成四件事：

1. 创建带序号的 ticket，记录请求类型和 owner。
2. 把 ticket 放入共享等待队列。
3. 按“当前允许入场的有效优先级 + FIFO 序号”选择下一项。
4. 获得协议 `mutex` 后才执行 `block`，完成、异常或取消后释放并唤醒下一项。

`mutex` 是协议安全阀，不是业务优先级本身。业务代码不能直接取得它；`NikonCamera` 不对外暴露绕过调度器的锁路径。

### 1.2 一个 ticket 是一个不可抢占事务

ticket 被选中后，调度器不会在 `block` 中途把它暂停给另一个 ticket。一个事务可能是一条普通命令，也可能是一段必须保持 PTP 数据边界的组合操作：

- 一条 `GetThumb`。
- 一批已经保持旧行为的 `ObjectInfo`。
- 一个评级文件头的首块加扩展块读取。
- 原片传输的一个完整数据分块，包含数据相位、响应消费和本地写盘。
- 一次 Live View 取帧。
- 录像启动的原子命令序列。

事务结束后才重新选择。调度器没有时间片轮转，也不会把一个正在接收的数据包的事务切开。要获得更细的让路粒度，调用方必须把工作拆成多个安全的事务边界，例如传输按分块拆开、评级按文件拆开。

### 1.3 队列选择算法

选择逻辑只看两个条件：

- `eligibleLocked(ticket)` 是否允许这个 ticket 现在入场。
- `effectivePriority(ticket)` 的数值是否更小；相同数值按 ticket 序号先后执行。

当前没有老化机制、配额机制或强制公平时间片。一个持续不断提交的更高优先级请求可以让低优先级请求继续等待；代码通过把高成本工作拆成短事务、在 UI 任务边界取消，以及在评级阶段阻断低优先级后台请求来控制这种等待。

### 1.4 准入和释放的顺序

`acquire` 会在状态锁内把 ticket 加入队列并尝试泵出下一项；被选中的 ticket 先标记为 active，再恢复等待者，等待者随后取得协议 mutex。

`release` 先释放协议 mutex，再清空 active 状态并泵出下一项。这样下一个事务不会因为调度器已经放行而卡在仍未释放的底层 mutex 上。

等待中的协程被取消时，只删除自己的排队节点。已经 active 的事务被取消时，调度器释放它的 active 状态并让下一项继续；如果该事务处于数据阶段，调用方仍必须先完成 PTP Cancel、排空或关闭连接，不能让迟到数据污染下一项。

## 2. 请求类型和优先级

`CameraRequestKind` 的基础优先级如下。数值越小越优先。

| 基础级别 | 类型 | 当前典型行为 | 事务边界 |
|---|---|---|---|
| P0 | `INTERACTIVE` | 监看取帧、对焦、拍照、录像、参数写入、旋转、遥控、关闭会话 | 一条命令或一个必须连续的控制步骤 |
| P1 | `PREVIEW` | 当前大图 FHD、当前 EXIF、FHD 预览请求 | 当前照片的一次完整预览/EXIF请求 |
| P2 | `TRANSFER` | 原片下载的一个数据分块、未知大小解析、视频续传分块 | 一个完整 PTP 数据相位和响应 |
| P3 | `RATING` | 一个文件的评级读取，或视频评级定位器要求的一个区域读取 | 一个文件头探测，或一个结构区域读取 |
| P4 | `VISIBLE_THUMBNAIL` | 当前可见格子缺失的远程缩略图 | 一张缩略图的一次相机请求 |
| P5 | `BACKGROUND_THUMBNAIL` | 整卡列表、后台缩略图、低频目录/元数据读取 | 一批 ObjectInfo、一个后台缩略图，或一个已定义的后台批次 |
| P6 | `IDLE` | 空闲心跳、低频存储检查 | 一条独立命令 |
| 特殊 | `EVENT_POLL` | 事件轮询；有效级别随评级阶段变化 | 一次 GetEvent/GetEventEx |

### 2.1 `EVENT_POLL` 的有效级别

`EVENT_POLL` 在枚举中保留基础值 0，是为了兼容旧的交互顺序；实际入队时按阶段重映射：

- 评级阶段关闭：有效级别为 P2。传输保持 P2，缩略图仍使用 P4/P5，因此新提交的传输会越过已经排队的远程缩略图；只有当前已经开始的那一笔缩略图事务自然收尾后，传输才会入场。
- 评级阶段开启：`eligibleLocked` 直接阻止后台事件轮询；诊断语义上相当于排在评级之后。
- 监看事件轮询使用 `background=false`，作为 `INTERACTIVE` 进入；它不会因评级后台屏障而消失。

### 2.2 评级阶段的有效级别

评级 ticket 本身仍是 P3。`beginRatingPhase()` 只打开一个阶段屏障和重新泵队列，并不会把整个评级扫描锁进相机通道。

评级阶段开启时，以下请求不能在两次评级事务之间抢先入场：

- `VISIBLE_THUMBNAIL`。
- `BACKGROUND_THUMBNAIL`。
- `IDLE`。
- `EVENT_POLL`（后台模式）。

以下请求仍可以在当前事务结束后插入评级之间（如果已有 `interactiveReservations`，还要服从该兼容预约的准入限制）：

- `INTERACTIVE`，包括监看、对焦、拍摄、录像和监看事件。
- `PREVIEW`，包括当前大图和当前 EXIF。
- `TRANSFER`，包括下一块原片或视频数据。
- 其他 `RATING`。

因此“评级让路”不是“评级永远最高”。准确顺序是：当前事务先完成；下一项从允许入场的请求中按有效级别选择；P0/P1/P2 仍可超过 P3，P4/P5/P6 在评级阶段被挡住。

### 2.3 兼容预约 `interactiveReservations`

旧的大图组合流程通过 `withInteractivePreviewPriority` 使用一个兼容预约。预约只增加计数，不占用相机 mutex；预约存在期间，`eligibleLocked` 会挡住 `CameraRequestKind` 基础 `priority > PREVIEW` 的 ticket。由于 `EVENT_POLL` 在枚举中保留基础值 0，它不受这条预约条件单独阻挡；其是否入场仍由 `EVENT_POLL` 的阶段映射和评级屏障决定。FHD 和 EXIF 的手机本地解码不需要持有相机事务，但它们之间不会让传输的下一块抢先提交。

新的调用方应直接使用 `withCameraTransaction`。预约是为了保持旧有“当前大图组合优先”行为而保留的适配层，不是第二个调度器。

## 3. 请求归属总表

下表列出当前代码中会影响相机通道的主要行为。括号内是代码入口或 owner，便于后续 Android/iOS 对照。

| 行为 | 调度类型 | 是否占用相机通道 | 关键规则 |
|---|---|---:|---|
| Live View 取帧 | P0 `INTERACTIVE` (`LIVE_VIEW_FRAME`) | 是 | 每帧一个事务；相机忙时返回空帧并由上层稍后重试 |
| Live View 开始/结束 | P0 | 是 | 结束路径会把结束追踪与 EndLiveView 组成一个 P0 事务；启动路径的 StartLiveView 与 DeviceReady 轮询是多个 P0 事务，轮询间允许调度器插入其他请求 |
| 对焦模式、参数、AF、主体追踪 | P0 | 是 | `focusMutex` 串行化同一套 AF 生命周期；轮询间隔不持有通道 |
| 拍照、录像开始/结束 | P0 | 是 | 拍照和结束录像是交互命令；USB 远控开录的应用模式、禁止条件和开始命令在一个 P0 事务内，Wi-Fi 直接开录路径使用多个 P0 命令事务 |
| 监看事件轮询 | P0 `EVENT_POLL(background=false)` | 是 | 与 focusMutex 协调，评级阶段仍可用 |
| 照片页后台事件轮询 | `EVENT_POLL(background=true)` | 是 | 评级阶段阻塞；不会持有 focusMutex 等待评级 |
| 当前高清大图 | P1 `PREVIEW` | 是 | 当前照片优先；不会被后台评级或缩略图超过 |
| 当前照片 EXIF | P1（后台 EXIF 则 P5） | 是 | 当前预览 EXIF 用 P1；后台资料用 P5 |
| 可见缩略图 | P4 | 是（缺失时） | 内存/磁盘命中不进队列；评级阶段被挡在评级后 |
| 后台缩略图 | P5 | 是（缺失时） | 低优先级；评级阶段不在两张评级之间抢占 |
| ObjectInfo/目录批次 | P5 | 是 | 维持现有批次边界；批次完成后才发布列表并进入下一批 |
| STA 直接目录头 | P5 | 是 | 已验证的直接读取路径按现有 1→3→批量节奏，以后台批次执行 |
| AP/USB 对象评级 | P3 `RATING` | 是 | `GetObjectPropValue` 读取 Nikon 评级值 |
| STA 照片评级 | P3 `RATING` | 是 | JPEG/RAW 受限文件头，首块 100 KiB，必要时每次追加 8 KiB，最多 256 KiB |
| STA 视频评级 | P3 `RATING` | 是 | MP4 `moov/udta/NCDT/NCTG` 定位器按需读取结构区域 |
| 原片照片下载 | P2 `TRANSFER` | 是 | 照片不续传；GetObject 或一次完整范围流式写盘 |
| 原片视频下载 | P2 `TRANSFER` | 是 | 循环分块；只在分块边界让 P0/P1 等更高请求进入；支持续传 |
| 下载活动标记 | 非 ticket 状态 | 否（本身不发命令） | `activeDownloadCount` 贯穿整个文件，防止 P6 心跳在下载间隙插入 |
| 空闲心跳 | P6 `IDLE` | 是 | `withIdleCommand` 在入队前和获准后都检查活动下载；下载期间直接跳过 |
| 监看存储余量 | P6 `IDLE` | 是 | `monitorFreeBytes` 直接提交 IDLE；调度器在活动下载期间阻止它入场，结束后再执行，不是调用方直接跳过 |
| 连接握手/能力探测 | 运行期队列之外 | 是 | 建立会话前由连接流程串行完成，未发布给业务协程；不与运行期请求并发 |
| 关闭会话 | P0 `INTERACTIVE`，允许 shutdown | 是 | 先关闭提交闸门，再取消排队项，最后等活动事务收尾后发送 CloseSession |
| 本地缓存/解码/绘制/照片生成 | 不进入调度器 | 否 | 不读相机通道，也不计入传输速度或评级读取时间 |

## 4. 各类行为的详细让路规则

### 4.1 监看、遥控和对焦

监看画面每次取帧使用短的 P0 事务。曝光、ISO、快门、白平衡、对焦模式和其他参数写入也使用 P0。拍照和录像的关键状态切换使用 P0。USB 远控录像的准备、应用模式和开始命令在同一个交互事务中完成，避免事件轮询或 Live View 取帧插入半切换状态；Wi-Fi 直接开录路径由多个 P0 命令事务组成，不能描述为同一事务原子完成。

对焦还有一把独立的 `focusMutex`，作用是防止两套 AF 流程互相交错；它不取代 `CameraIoGate`。一次 AF 的命令步骤通过 P0 ticket 执行，`DeviceReady` 的忙轮询在每一条轮询命令之间释放通道，约 150ms 的等待也不占用相机命令通道。这样 Live View 能在 AF 等待期间继续取短帧，但另一个 AF 流程不能同时修改目标。

监看事件使用 `rcPollEvents(background=false)`，在 `focusMutex` 内提交 P0。照片页的后台事件使用 `background=true`，提交低优先级 `EVENT_POLL`，不拿 focusMutex 等评级结束。

### 4.2 大图和 EXIF

当前照片的 FHD、当前 EXIF 使用 P1；后台资料读取使用 P5。大图工作流保留一个兼容预约，保证当前照片的 FHD→EXIF 组合期间传输不会抢先开始下一块，但 FHD 和 EXIF 中间的手机解码不占用相机事务。

预览不打断已经开始的数据事务。若原片正在传一个分块，当前分块先消费完 PTP 数据和响应，随后大图取得 P1。关闭预览会取消仍在等待的预览任务；相机已完成的本地结果可继续被 UI 使用。

### 4.3 原片传输

`downloadToFile` 的整个文件过程进入 `withDownloadActivity`，因此心跳和 P6 空闲命令知道“当前有下载”并会跳过。真正访问相机的数据阶段通过 `withTransferSlice`：

- 一个分块从发送命令开始，到完整消费数据包和 `CMD_RESPONSE` 结束。
- Android 文件写盘和传输头部捕获发生在该数据事务内，不能在 PTP 数据未收完时让下一请求接管流。
- 分块结束后才重新按优先级选择下一 ticket。
- 异常时在仍持有通道时发送 Cancel、限时排空；无法确认流边界就关闭连接。

照片当前不支持续传：照片从偏移 0 开始，一次完整范围流式写盘，不把整张照片装进内存。视频使用循环分块和续传偏移；只要分块能力可用，就在分块之间让 P0/P1 插入。分块能力不可用但请求带续传偏移时直接失败，禁止把全量数据写入已定位的文件。

传输速度使用下载函数从开始到当前的单调时钟和实际收到字节计算，包含本地写盘以及分块之间等待 P0/P1/P3 等请求让路的端到端时间；因此相机通道上的评级、预览或监看插入会反映为速度降低。照片效果生成不属于下载函数，也没有把生成阶段单独计入这条统计；但共享 CPU 负载仍可能影响任何端到端墙钟时间。

### 4.4 缩略图和照片列表

缩略图读取分为三层：

1. 内存 LRU 命中：同步返回，不产生相机请求。
2. 磁盘缓存命中：本地解码返回，不产生相机请求。
3. 缺失时向相机 `GetThumb`：可见格子用 P4，后台预取用 P5。

同一 handle 的可见和后台请求会合并，避免重复 `GetThumb`。后台预取在每个已发布列表批次中依次处理；如果传输、监看、大图或照片效果演示已占用前台工作，当前批次可以提前停止，完整列表结束后再补漏。

`streamFileInfo` 的普通 ObjectInfo 按批次放进一个 P5 事务，批次之间释放通道。STA 直接目录读取也保持现有批次边界；它不是每个字段都变成一个独立 ticket。这个边界是为了兼容原有首屏节奏，意味着评级不会切入一个已经开始的长批次，只能等该批次完整收尾。

非评级阶段，传输 P2 仍高于远程缩略图 P4/P5；这保证用户第一次点击开始传输时，不会被照片列表已经排队的缩略图请求长期挡住。当前已经开始的缩略图事务不能被强制打断，会在自己的完整 PTP 事务结束后释放通道。评级阶段开始后，新的远程 P4/P5 缩略图 ticket 被准入屏障挡住；应用层在调用相机前已经查过内存/磁盘缓存的命中仍然完全本地执行，不会等待评级，也不会与评级竞争。评级结束后，未完成的缩略图恢复原有优先级。需要特别区分两个概念：`prefetchPublishedFileBatch` 的返回值 `allCached` 与 `_recentThumbnailReadyDays` 的更新不是绑定的。当前代码在该批次预取函数返回后就更新最近拍摄日边界，即使预取因前台任务提前返回 `false`，也可能把该批次所覆盖的日期计入就绪。因此 `recentThumbnailReadyDays` 当前表达的是“已发布列表批次跨过日期边界并完成一次预取尝试”，不是“该边界内每一张远程缩略图都已经成功落盘”。如果产品契约要求后者，需要单独修改代码；本文不把它描述成当前已有能力。

### 4.5 星级/评级读取

评级开关关闭时，`PhotoRatingScan` 不创建读取任务，也不调用 `beginRatingPhase`。打开时，它为本次连接建立一个本地扫描代次；关闭再打开会清空本次连接的评级内存并重新读取，目的是让用户在相机上改完评级后可以主动刷新。

#### 两个日期范围与范围确定

照片列表和评级各有一个独立的日期档位，均为 1 日、3 日、5 日和全部（代码中 `0` 表示全部）：

- **照片加载范围 `photoLoadingDays`**：限制照片页实际发布的 `FileInfo` 行、可见列表以及远程缩略图请求。句柄目录仍可一次取得完整的 handle 顺序；超过边界的旧照片不会继续读取 `ObjectInfo`/缩略图，边界尾部保留在当前会话快照中，扩大范围时继续使用该快照。若目录删除事件使快照失效，扩大范围会保留已显示文件并重新枚举句柄，不会丢掉旧日期尾部。范围变窄时，已发布数据不会被删除，只由照片页隐藏到范围外；范围扩大时才恢复尾部读取。连接期间新事件追加的照片不受初始扫描停止边界限制，会追加到当前目录并按正常流程加载缩略图。
- **评级范围 `ratingDays`**：只在用户打开评级筛选时生效，决定本轮 STA 评级要覆盖的拍摄日范围。评级结果是本连接内存快照；关闭再打开或重新连接会清空并重新读取。星级条件本身不持久化，评级日期档位可以持久化。

STA 的实际评级边界是两个范围的交集：`effectiveDays` 取两个非零档位的较小值；一个为 `0`（全部）时取另一个，两个都为 `0` 才表示全部。也就是说，照片范围为 1 日、评级范围为 3 日时，照片列表完成最近 1 个拍摄日后即可启动评级，并只读取这 1 日内当前快照中的评级来源；反过来照片范围为 5 日、评级范围为 3 日时，只读取最近 3 日。这样评级不会等待照片列表已经明确不会发布的更早日期。

STA 扫描满足以下任一条件后才允许启动：

- `recentThumbnailReadyDays >= effectiveDays`；
- 列表已经权威结束，实际拍摄日少于有效范围；
- 两个范围均为“全部”时，列表加载结束且日期范围完整。

`recentThumbnailReadyDays` 在每个列表批次的预取函数返回后更新。批次中的内存/磁盘命中不需要 P4/P5；真正缺失的缩略图才需要相机事务。达到有效日期边界后，评级扫描不会继续等待更早日期的缩略图，但当前代码是否已完成该批次所有远程缩略图还要看 4.4 的边界说明。AP/USB 不使用 STA 的日期就绪等待锚点，也不使用 `ratingDays` 再次收缩读取集合；它读取当前已经发布的评级来源。

用户改变照片加载范围时，`TransferViewModel` 会持久化新档位、关闭评级开关并清除已选星级。这样不会在两个范围变化中间复用旧评级快照；用户重新打开评级后才按新的有效范围建立新代次。评级扫描一旦锁定快照，连接期间新增照片不会加入本轮评级，下一次连接或重新开关才会读取。

一旦评级扫描开始，当前连接的文件快照和日期范围锁定。后续列表、缩略图或目录状态变化不会重新建立同一轮扫描；连接重建或显式关闭/重新打开评级开关才建立新的代次。

#### 来源去重

`photoRatingSources` 对同名 JPG/JPEG 与 NEF/NRW 做唯一配对；当两边都带有存储卡字段时要求有重叠，当两边都带有拍摄日期时要求相等，字段缺失不会单独否决配对。只有唯一且兼容的 JPEG 才作为 RAW 的评级来源。视频保持独立来源。配对不唯一或条件不兼容时，不猜测，文件保持未知。

#### 三种连接的读取

- **STA 照片：** `readPhotoRatingHeader` 先读 100 KiB；未解析到评级时从已读长度继续追加 8 KiB，最多 256 KiB。追加不是重复读取前半段。每个文件的这段受限头读取在一个 P3 `RATING` 事务中完成。
- **STA 视频：** 使用已验证的 Nikon MP4 结构定位器，围绕 `moov/udta/NCDT/NCTG` 读取需要的结构区域，不下载视频媒体数据。定位器每次向相机取区域时进入 P3 事务。
- **AP/USB：** 评级扫描使用 `GetObjectPropValue` 读取 Nikon 评级属性；解析已验证的原始值 `0、1、25、50、75、99` 为 `0、1、2、3、4、5` 星。实际发出的对象属性读取是 P3 事务；同一连接中遇到明确的不支持响应后，后续相同扩展名/能力会短路，不会继续发同样的命令。评级扫描不会为了 AP/USB 额外读取文件头；若其他流程此前已捕获文件头，仍可能被动写入本连接的评级表，但开启评级时会先清空这类旧值。

读取结果只保留轻量的 handle→星级映射和来源。当前 `photoRatings` 星级值表最多保留 8192 项；来源字符串保存在单独的 `photoRatingOrigins` 表中，随代次清空但没有独立淘汰上限（详见边界与风险）。评级代次变化后旧映射立即清空；新建 `NikonCamera` 的新连接也不会继承旧对象。未知、失败、不支持与明确 0 星必须区分，未知不能伪装成 0 星。

#### 评级阶段的让路

扫描调用 `beginRatingPhase()`，按文件调用 `readObjectRating`、`readPhotoRatingHeader` 或 `readVideoRating`；照片/对象读取通常对应一个 P3 ticket，视频读取器会按结构区域提交多个 P3 ticket。每个读取调用完成后才提交下一项。扫描本身不长期持有相机锁，也不一次把全部文件放入队列。

评级阶段下：

- P0 监看/遥控和 P1 当前大图可以在当前事务结束后插入。
- P2 原片/视频传输分块可以在当前事务结束后插入。
- P4/P5 远程缩略图、P6 心跳和后台事件不能在评级文件之间抢占。
- 已经开始的 P4/P5 批次或 P2 数据事务不会被强行打断。

这不是“评级和缩略图交替执行”。评级阶段的实际行为是：评级 ticket 连续提交；只有更高优先级的交互、预览、传输事务能在安全边界插入，低优先级远程缩略图和普通后台请求被挡在评级阶段之后。缓存命中不在这条单车道上。

### 4.6 空闲命令和事件

心跳通过 `withIdleCommand`。它先检查活动下载数，入队取得通道后再次检查，避免在等待期间刚好开始下载而插入心跳。存储余量监看走 `monitorFreeBytes` 的普通 `IDLE` ticket；它不在调用方直接跳过，而是由调度器的 `activeDownloadCount` 准入条件挡住，下载结束后再获得通道。评级阶段也会阻止 P6 空闲命令。

无线事件 socket 的 PING/PONG 在独立事件通道上处理，不走命令 ticket；事件包只被解析并投递到内存 Channel，不在事件线程直接发命令。命令通道上的 GetEvent/GetEventEx 仍按上面的 `EVENT_POLL` 规则执行。

### 4.7 连接握手、能力探测和关闭

连接握手发生在会话业务请求开始前：创建 socket、初始化 PTP/IP 或 USB、OpenSession，以及按连接路径执行的必要 `GetDeviceInfo`、STA 能力验证和配对探测，按连接流程串行完成。此阶段没有其他业务协程能使用该 `NikonCamera`，所以这些原始 `sendCmd/recvResp` 不通过运行期 ticket；它们不是一个可被业务请求绕过的第二调度器。

会话关闭采用相反顺序：

1. `beginShutdown` 打开提交闸门，拒绝新的普通 ticket。
2. 取消所有尚未入场的等待项；已经 active 的事务先按自己的异常/排空规则收尾。
3. 用 `INTERACTIVE + allowDuringShutdown=true` 提交唯一允许在闸门后执行的 CloseSession 事务。
4. 发送 CloseSession（若会话确实已打开）并关闭 socket/USB 资源。

重新连接创建新的 `NikonCamera` 和新的调度器状态，旧队列、旧评级代次、旧 active owner 都不会带入新会话。

## 5. 典型场景的实际顺序

### 场景 A：照片列表第一次打开，评级关闭

1. 连接流程已完成，列表取得 StorageID 和 handles。
2. ObjectInfo/STA 直接目录批次以 P5 运行，发布照片批次。
3. 缩略图先查内存/磁盘；命中直接本地完成，缺失以 P4/P5 进入相机。
4. 心跳和后台事件在没有传输、前台预览或评级屏障时按 P6/P2 规则运行。
5. 因为评级开关关闭，不会创建 P3 评级任务，也不会建立评级阶段屏障。

### 场景 B：列表打开并开启评级筛选

1. 开关进入时清空本次评级映射，开始新的扫描代次。
2. 列表继续发布；每个批次执行一次缩略图预取，当前代码在预取函数返回后更新最近拍摄日边界。本地缓存命中不发相机请求，远程缺失才进入 P4/P5。
3. 达到两个日期档位交集得到的有效范围后，扫描锁定日期和来源集合；有效范围为 1/3/5/全部之一。
4. `beginRatingPhase` 打开低优先级准入屏障；每个评级文件按读取器提交一个或多个 P3 事务。
5. P0/P1/P2 到达时，在当前 PTP 事务结束后优先入场；远程 P4/P5 和 P6 等待。
6. 每个评级文件完成后立即更新内存映射和进度；扫描结束调用 `endRatingPhase`，后台缩略图和心跳恢复。

### 场景 C：评级进行中用户开始传输视频

1. 当前评级事务先完成，不能半截让出 PTP 数据。
2. 视频传输的下一个分块以 P2 入队，优先于排队的 P3 评级。
3. 该分块完整收取、写盘、消费响应后释放通道。
4. 下一项再按队列选择；如果没有更高 P0/P1/P2，下一评级文件继续；评级阶段仍阻止远程缩略图和心跳。
5. 视频的速度统计只读取传输函数自己的字节计数和墙钟时间；评级解析没有作为生成阶段追加进去，但若评级事务在分块边界让路，等待会体现在端到端速度中。

### 场景 D：评级进行中进入监看并点击对焦

1. 监看取帧和对焦命令以 P0 入队。
2. 当前评级事务完整结束后，P0 获得下一通道机会。
3. AF 的 `focusMutex` 防止两次对焦生命周期交叉；`DeviceReady` 轮询之间释放通道，Live View 可以继续取帧。
4. 评级扫描在下一个文件边界继续，不重新计算已经锁定的日期范围。

### 场景 E：用户关闭评级再立即打开

1. 关闭动作取消当前 Compose 扫描任务，清空本次评级映射并增加 generation。
2. `endRatingPhase` 在 `finally` 中执行，解除低优先级屏障。
3. 重新打开时建立新的本地映射和新的待读集合，不使用刚才的结果作为当前快照。
4. 重新等待范围锚点，然后从相机重新读取；这是显式刷新，不是断点续读。

### 场景 F：连接中断

1. 当前事务按异常路径结束；无法确认数据边界时由原事务关闭传输。
2. `beginShutdown` 清空队列等待项，评级/列表/缩略图任务收到取消或连接失败。
3. 新连接创建新的相机对象和调度器，不复用旧连接的评级结果。
4. 磁盘缩略图和本地生成结果可以继续使用，但它们不代表新连接的评级快照。

## 6. 诊断和状态观察

调度器可通过 `cameraSchedulerSnapshot()` 读取轻量快照，不发相机命令：

- `queued`：当前等待中的 ticket 数。
- `activeKind`、`activeOwner`：当前 active 事务。
- `interactiveReservations`：兼容预约计数。
- `activeDownloads`：整文件下载活动计数。

评级诊断只记录关键阶段和受控的单事务计时：扫描开始、缓存来源计数、当前进度、取消/失败原因、最终 confirmed/unknown 和总耗时；评级头读取可额外记录 gate、command、parse、other 耗时。默认不应逐条刷屏打印所有普通缩略图或事件请求。

调度器本身不应为了诊断增加相机往返、复制整包数据或改变队列优先级。需要性能诊断时，只记录已存在事务边界上的时间戳和计数。

## 8. iOS 复刻必须保持的契约

### 必须保持

1. 相机命令通道只能有一个实际的 PTP 事务在读写。
2. ticket 在完整事务边界切换；不得中途抢占数据阶段。
3. P0 监看/遥控、P1 当前预览、P2 传输分块高于 P3 评级。
4. 评级阶段只阻止 P4/P5/P6 的后台准入；不能阻止监看、预览和传输分块。
5. 缓存命中不进入相机队列。
6. 下载活动计数跨越整文件，空闲心跳不能插进文件分块间隙。
7. 评级扫描按两个日期档位交集得到的有效范围锁定范围，按文件逐项提交 P3，不持有整段全局锁；照片加载范围本身还决定照片列表是否继续读取更早的 `ObjectInfo`/缩略图。
8. STA、AP、USB 使用各自已经验证的评级来源，不因连接模式混用错误的读取方式。
9. 连接断开清空等待中的业务请求；新连接使用新的调度器状态和新的评级代次。
10. 传输速度使用下载函数自己的端到端计时，照片生成不向其中追加生成耗时；评级/预览/监看若在分块边界占用相机通道，等待会自然反映在传输速度中。监看帧率和照片生成计时使用各自的计时链路。

### 不要复刻为现有能力

- 不要添加按毫秒时间片抢占 PTP 事务。
- 不要把本地缓存/解码线程纳入相机命令队列。
- 不要把整个评级扫描包装成一个长事务。
- 不要让每个缓存命中都触发相机请求或评级缓存写入。
- 不要在连接期间假设 PTP 事件一定能可靠通知星级变化；当前策略是关闭再打开或重新连接获得新快照。
- 不要把未知、失败或不支持解释成 0 星。

## 9. 当前实现的边界和风险点

以下是代码已经明确的边界，不能在产品说明中隐去：

1. **没有强制公平性。** 如果 P0/P1/P2 连续不断产生，P3 评级可能延后；这是为了保护监看、预览和传输。真机若需要最大等待上限，应先设计新的配额规则并增加测试，不能靠修改数字暗中改变行为。
2. **已入场事务不可打断。** 一个大的 ObjectInfo 批次、FHD 请求或传输分块开始后，评级必须等待它完成。
3. **评级阶段由 UI 扫描生命周期触发。** 调度器只执行 `beginRatingPhase/endRatingPhase`，不自己判断“最近几日是否已准备好”。范围锚点和连接快照仍由 `PhotoRatingScan`/`CameraViewModel` 负责。
4. **评级值表有 8192 项上限，但来源表没有独立淘汰。** `photoRatings` 的轻量星级值最多保留 8192 项；`photoRatingOrigins` 会随代次一起清空，但当前代码没有按同一上限独立移除旧来源字符串。因此“评级值有上限”是事实，“值和来源整体都严格限制在 8192 项”不是事实。它们都不是跨连接持久化缓存。
5. **最近拍摄日就绪不是逐张缩略图完成证明。** `updateRecentThumbnailReady` 在批次预取函数返回后推进边界，而预取函数可能因前台任务提前返回 `false`；当前扫描锚点不能表述为边界内所有远程缩略图都已落盘。
6. **连接握手不是运行期队列。** 这不是漏接调度器，而是因为当时业务协程尚未能使用该相机对象；连接流程自身必须保持串行。
7. **事件 socket 是另一条物理通道。** 它只处理 PING/PONG 和已到达的事件包；任何新的命令仍必须回到命令通道调度器。

## 11. 一句话判断当前是否“完整”

以当前代码口径，连接初始化完成并交给业务层后，调度器覆盖了相机业务命令：监看、遥控、预览、传输分块、缩略图、目录、评级、空闲检查和关闭会话都通过统一的 `CameraIoGate`，或通过明确转发到它的兼容适配器；连接初始化本身是前置的串行会话边界。本地缓存、解码、绘制和生成不应进入调度器。真正需要继续用真机验证的是不同机身在这些边界上的耗时和协议响应，而不是再建立第二套锁或第二个优先级系统。
