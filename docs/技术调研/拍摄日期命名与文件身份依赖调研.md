日期：2026-10-27  
代码基线：`android` 分支，提交 `a90da2eb`。下文行号对应此基线，后续优先按函数名定位。  
状态：**暂缓实施，保留调研结果。** 用户决定先不改功能；下文方案是后续讨论依据，不是已实现行为。

## 结论与范围

设想是在照片传输设置中增加可选项，让保存到手机的照片按拍摄日期和时间命名。实现时必须保留相机原文件名，另设保存名称。相机原名、照片身份、保存后的文件名不能继续混用。

当前最重要的依赖有四类：

1. 原片的已传跳过、对号和筛选，依赖保存目录中的文件名及大小；目前没有独立持久化的相机来源到本地输出的映射。
2. 效果图的去重标识虽然写在 JPEG 内，其计算仍包含来源文件名，候选文件查找也依赖名字。
3. 胶片颗粒用来源文件名计算随机种子，改名可能使预览与生成的颗粒排列不一致。
4. 连拍、JPG 与 RAW 配对、双卡逻辑身份及缓存使用相机原名。只改保存名称可以保留这些机制；直接覆盖 `FileInfo.fileName` 会扩大影响范围。

拍摄时间应按**只能统一依赖秒级信息**来设计。原片可能有亚秒字段，但不同机型、格式和连接路径不能保证提供；有亚秒也必须处理重名。

审查范围为相机文件读取、照片列表与回看、下载发布、已传索引、裁切、照片效果、本地照片效果入口及相关缓存。下列清单将同一逻辑的多个调用合并说明，区分现状与未来改名可能带来的风险。

后续如利用原片亚秒信息，应另设命名用时间字段，保留时间来源和可选时区偏移；不要为了命名直接修改 `FileInfo.captureDate`。该字符串本身也参与缓存和来源身份判断。

### 末尾数字归一化不能复用于日期名

现有规则用于把 `DSC_9049.JPG` 与 `Z30_9049.jpg` 识别为同一编号和格式。在日期命名中会出现以下结果：

```text
20261027_143012.JPG → number:143012.jpg
20261028_143012.JPG → number:143012.jpg
20261027_143012_001.JPG → number:001.jpg
```

两个风险需要区分：

- 只改落盘名、仍按相机原名查询，首先会导致查重失效和重复下载。
- 如果随后也用日期名查询，却保留当前末尾数字算法，不同日期或同秒照片可能归入同一个键；大小也相同时可能误跳过。不能把这个条件性风险写成所有改名都会立即误删或误跳过。

当前鸿蒙完整性校验虽然会比较字节数和 SHA-256，但这个哈希没有用于原片的已传查重。[TransferFingerprint.kt](../../app/src/main/java/com/ztransfer/diagnostics/TransferFingerprint.kt) 与已传索引是不同用途。

## 不依赖保存文件名的机制

- 拍摄日分组、日期范围和评级加载范围读取 `captureDate`，不是从文件名解析日期。见 `FileListScreen.kt` 501 行、`PhotoRatingScan.kt` 95、129、146、286 行。
- 下载调度和生成调度主要使用 taskId，单次批量入队去重使用相机 handle。见 `TransferViewModel.kt` 421—449、888—892 行及 [PhotoGenerationQueue.kt](../../app/src/main/java/com/ztransfer/viewmodel/PhotoGenerationQueue.kt)。
- 工作台选择去重和页身份使用 URI。见 [LocalPhotoBatchViewModel.kt](../../app/src/main/java/com/ztransfer/ui/screen/LocalPhotoBatchViewModel.kt) 52 行、`LocalPhotoPreviewPager.kt` 77 行。
- 鸿蒙完整性校验依据字节数和哈希；待验证发布记录使用 URI 和 UUID，并不按名称恢复或删除。见 [HarmonyPublishedFile.kt](../../app/src/main/java/com/ztransfer/storage/HarmonyPublishedFile.kt)、[PendingPublicationJournal.kt](../../app/src/main/java/com/ztransfer/storage/PendingPublicationJournal.kt)。

新增命名策略不应将这些身份改成显示名称。

## 后续方案的设计边界

### 来源身份与保存名称分离

建议保留相机原始 `fileName` 和 `captureDate`，新增保存命名策略、命名用时间信息及实际输出名称。用稳定来源身份关联保存后的 URI、名称和目录。

来源身份不能只用秒级时间、显示名或单一 handle。设计时需要考虑相机身份、原始拍摄信息、格式、大小、跨连接模式别名和双卡关系；具体组成尚未定稿。

输出名称只负责文件展示。效果去重和颗粒种子应使用稳定来源信息，不能因为用户改变保存名称而改变。适配时同时检查效果候选文件发现、旧标识兼容和本地照片效果入口。

### 可恢复的来源映射

目前已传状态可以通过扫描目录恢复。新方案不能仅在本次内存里给日期文件加一个原名别名。

如果映射只保存在 App 数据库，清数据、重装或换手机后会丢失。若要保留现有恢复能力，需要研究随保存目录保留索引或其他可恢复标识。目录索引的结构、更新方式、外部移动／删除后的校验和损坏恢复尚未决定。

原片内容和 EXIF 应保持不变，不应为了加入来源标识而重新编码原片。是否采用目录索引、如何兼容旧文件，是实施前的主要决策。

### 重名与连拍

- 基础命名应包含日期和时分秒，仅日期会让一天中的所有照片竞争同一个名字。
- 同秒多张可加序号，但同一原片重试、重新入队时必须复用既有映射，不能每次产生新序号。
- JPG 与 RAW 的序号按同一逻辑照片分配，不能按两种扩展名各自独立分配。
- 多台相机、双卡、相机编号循环、错误机内时钟以及亚秒重复都需要防覆盖。
- 名称在目标目录内统一预留，并回读 Provider 的实际结果。名称示例只是讨论用法，未决定最终格式：

```text
20261027_143012_001.jpg
20261027_143012_001.nef
20261027_143012_001_c.jpg
20261027_143012_001_c_f.jpg
```

这些示例不能继续使用现有末尾数字归一算法作为来源身份。

### 时间与性能

- 建议采用照片记录的当地拍摄时间。无时区信息时，不应随手机时区变化反复转换同一照片的名称。
- 时间缺失或无效时回退相机原名，不把传输时间当作拍摄时间。
- 亚秒仅在原片实际提供时使用；不虚构精度，也不将其当作唯一标识。
- 尽量复用已读取的元数据或已下载的文件，避免为命名额外增加相机请求和重复下载。
- 日期格式使用固定格式和 ASCII 数字，避免系统语言变化导致同一照片换名；避开冒号、路径分隔符，保留真实扩展名。

### 开关和输出范围

- 命名策略建议在入队时固定；最终名称在发布前预留，避免传输中途切换设置造成同批行为混乱。
- 开关只影响后续保存，不自动批量改名已有照片。
- 开关来回切换后，同一原片仍应正常去重；旧名字和新映射需要共存。
- 第一版可以限定为相机传入的照片；视频和工作台输出是否沿用，需另行决定。
- 裁切和效果图继承统一保存主干，同时保持原有操作后缀。
- 队列展示相机原名还是最终保存名尚未确定；诊断信息应能关联二者。

## 再次启动实施前的验证清单

以下是未来方案的验收范围，不表示现在开始实施。

| 场景 | 必须满足的结果 |
| --- | --- |
| USB、AP、STA 传同一原片 | 切换连接方式后仍可识别已传，不因来源名前缀差异重复下载。 |
| 同秒连拍、多个相机和双卡 | 不覆盖、不误跳过，序号可稳定复用。 |
| JPG 与 RAW 先后分批传输 | 对应照片保持相同保存主干和编号。 |
| 命名开关切换、重新入队、失败重试 | 原片跳过、已传对号和筛选正确，不不断生成新编号。 |
| 重启、清数据、重装、换手机或保存目录 | 按最终决定的恢复策略重建映射；缺失信息时不得误判已有原片。 |
| 原名照片、旧长效果名、新短效果名与日期名混合 | 旧文件继续可用，原片和派生图不互相误认。 |
| 裁切、边框、滤镜、LUT、水印和颗粒组合 | 预览与生成一致，相同来源和参数的效果去重仍正常。 |
| 时间缺失、无亚秒、带偏移、手机时区改变 | 回退明确，不伪造拍摄时间，同一照片名称稳定。 |
| 不支持重命名的目录、Provider 自动加序号、鸿蒙回退 | 保存校验正常，记录实际 URI 和名称，失败清理不误删其他文件。 |
| 中途退出、任务取消、目录内文件被外部移动或删除 | 无永久占名或陈旧映射误跳过，能够安全重试。 |
| 连拍、回看合并、评级关联、双卡删除、缩略图和 EXIF 缓存 | 相机原始身份保持不变，现有行为不受影响。 |

后续应先确定来源映射和旧数据恢复策略，再确定文件名格式。当前决定仍是暂不修改功能。
