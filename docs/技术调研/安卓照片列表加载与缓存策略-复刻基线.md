# 安卓照片列表加载与缓存策略（iOS 复刻基线）

本文是 iOS 照片列表实现的唯一行为基线。内容按安卓当前 `android` 分支源码整理；实现 iOS 时只允许改变语言和平台 API，不允许改变顺序、状态、取消、重试、缓存命中和清理条件。若 Swift 端暂时缺少某个数据源，应记录为阻塞项并补齐数据源，不得用猜测值替代。

## 2. 一次完整扫描的严格顺序

`loadFiles(preserveExisting, resumeSnapshot, detectNewHandles)` 在没有相机时直接返回。进入扫描后必须依次执行：

1. 捕获当前相机的磁盘缓存引用；STA 直读模式清零本轮磁盘命中/未命中统计。
2. `fileLoadGeneration` 加一，取消旧 `fileLoadJob`，调用 `thumbnailFillQueue.beginScan()`，设置 `fileLoadPending=true`。没有显式恢复快照时先清除旧快照。
3. 新扫描（`preserveExisting=false`）清空相机句柄基线、已索引文件、存储目录检查状态、内存缩略图 LRU、`noThumbHandles` 负缓存和效果预览状态。旧相机的句柄即使数字相同也不能复用。
4. 发布加载状态：`isLoadingFiles = !isFileScanPaused()`、`hasCompletedFileScan=false`；非保留扫描清空 `files`、`storageIds` 和效果预览。保留扫描只保留已经显示的文件和效果预览。
5. 若监看、FHD 大图或其他前台任务使 `isFileScanPaused()` 为真，保持 `fileLoadPending` 并立即返回；不能向相机 I/O 队列排队。
6. 在扫描协程内确认恢复快照属于同一个相机实例。属于则直接复用快照中的 StorageID、每卡最新优先句柄顺序和剩余句柄；不属于则从头枚举。
7. 非恢复扫描先取得 StorageID。STA 走 `getStaStorageIdsWithStatus()`，仅对响应级 `DEVICE_BUSY` 重试，最多 3 次（初次 + 两次，间隔 `STA_FILE_SCAN_RETRY_DELAY_MS=750ms`）；传输异常或最终失败标记需要重连并结束本轮。普通连接走 `getStorageIds()`。
8. 过滤无卡/不可用的 StorageID：STA 过滤 `0/-1`，普通连接过滤低 16 位为 `0` 的槽位并去重排序。发布存储列表；STA 直读在双卡成员分析完成前暂不暴露槽位筛选 ID。无可用存储时：清除快照和 pending；只有存在当前相机的已知句柄基线时才按已知句柄移除缺失项，否则保留此前已发布的部分列表；发布完成状态并结束。
9. 对每个可用 StorageID 查询 ObjectHandles。STA 同样只对 `DEVICE_BUSY` 做 750ms、最多 3 次重试；最终失败需要重连并结束。普通连接保留返回结果，即使某一查询不完整。
10. STA 直读模式使用所有存储的句柄集合分析双卡成员和筛选存储 ID；不能按不透明句柄数值做全局排序。
11. 只有所有句柄查询成功时才更新当前相机的权威 `knownHandles` 基线：计算新增/删除，移除确定消失的文件；`detectNewHandles=true` 时仅把新增句柄报告为新媒体。句柄查询不完整时不删除、不更新权威基线。
12. 每张卡仅反转相机自然顺序得到 newest-first；双卡后续按每卡当前头部的真实拍摄时间归并。所有句柄为空时立即完成扫描，并且只有句柄查询成功才对账磁盘缓存。
13. 保存 `FileScanHandleSnapshot`：相机实例 token、StorageID、各卡 newest-first 句柄、句柄查询成功标记、STA 成员映射、筛选 StorageID。该快照只用于同一会话被 FHD/监看暂停后的恢复。
14. 从句柄顺序中排除已发布的句柄。没有剩余句柄时清除 snapshot/pending，发布完成状态并按成功条件对账，然后结束。
15. 对剩余句柄做渐进式元数据扫描：普通路径批量大小为 `FILE_THUMBNAIL_PIPELINE_BATCH_SIZE=12`；STA 直读沿用首批 1、第二批 3、之后 12 的低延迟预热策略。单卡 `streamFileInfo`，多卡 `streamMergedFileInfo`，STA 直读 `streamStaDirectMergedFileInfo`。
16. 每个批次在 Main 上一次性发布：按句柄去重；STA 双卡用 `logicalIdentity()`（文件名 + 大小 + 拍摄时间）合并同一逻辑照片的存储成员；更新 `files`、`isLoadingFiles = loaded < total`，记录已处理句柄。
17. 接受的批次立即调用 `prefetchPublishedFileBatch`，让缩略图写入和元数据扫描并行但共享相机通道门控。发现比本轮基线更新的媒体时，发出 `_newMediaFiles` 事件。
18. 正常结束时清除 snapshot/pending，发布 `isLoadingFiles=false`、`hasCompletedFileScan=true` 并发送新媒体事件。新媒体事件先按文件扩展名过滤，再由传输层按 `fileName|size|captureDate` 去重；只有开启自动传输且目录有效时入队，是否立即启动由 `deferTransferStart` 决定。仅当句柄查询全部成功且所有元数据流完整成功时调用缓存 `reconcile`；任何不完整都跳过对账，避免误删仍有效的缓存。

## 3. 代际、取消、暂停和错误规则

- 每轮扫描拥有递增 generation。协程在发布存储、句柄和每个批次前都检查 generation 仍是当前值且 `camera === cam`；旧相机回调不得覆盖新会话。
- FHD 预览或监看开始时取消扫描，保留已发布文件和 `FileScanHandleSnapshot`；结束后同一相机复用快照继续，不重复读取 StorageID/Handles。远程模式退出通常重新枚举，以捕获新照片。
- 协程取消不清空已显示文件；若仍是同一缓存/队列代际，把当前缩略图任务放回队首。STA 扫描错误保留部分列表，并调用 `onCameraTransportLost` 进入重连路径。
- 传输、监看、FHD、效果预览对后台缩略图填充拥有更高优先级；后台填充必须停止或让路，不能与前台请求争抢相机通道。

## 4. 内存和请求级缩略图缓存

- `thumbnailCache` 是按 bitmap KB 计量的 LRU，预算约为最大堆的八分之一；新会话 `evictAll()`。命中直接返回，不触发网络。
- `noThumbHandles` 只记录相机明确返回“无缩略图”或确认解码失败的句柄。临时 I/O、超时、取消不能写入负缓存；新扫描清除负缓存。
- `inflightThumbs` 按句柄共享可见缩略图请求；多个等待者共用一次读取/解码。最后一个等待者取消时才取消底层请求。
- `inflightPrefetches` 共享后台磁盘写入。前台请求发现后台任务正在进行时等待，然后重新检查内存、负缓存和磁盘。
- `remoteThumbGate = Semaphore(1)`：远程 GetThumb 同时最多一个，避免效果预览/FHD 被批量缩略图饿死。

`loadThumbnail(file, allowRemote)` 的固定查找顺序是：内存 LRU → 负缓存 → 相机磁盘缓存 → 等待同文件后台预取并重新检查 → 共享/新建可见请求 → `fetchAndDecodeThumb`。远程被禁止时不得发起远程请求。

`prefetchThumbnail(file)` 只负责写磁盘，不解码、不填充内存 LRU。命中磁盘直接成功；STA 直读 RAW/视频懒加载，不做后台预取；可见请求已在进行时复用它。失败返回 false，由队列记录失败。

## 5. 后台缩略图填充队列

`startThumbnailFill` 与页面无关，连接建立后持续运行，但仅在“已连接 + 文件扫描完成 + 没有传输/监看/FHD/效果预览”时工作。队列固定分 priority/regular 两栏：日期筛选范围内的照片进 priority，其余进 regular。

- `beginScan` 清空待处理和失败项，但保留已 settled 句柄（磁盘已有或已确认无缩略图）。`reset` 才清空全部状态。
- `seed` 只加入未 settled、未 pending、未 failed 的文件；同一 revision 只 seed 一次。
- 相机 ObjectAdded 新照片用 `enqueueNew` 放入所属栏队首。
- `poll` 永远优先取 priority；无任务时等待外部 wake，不忙等。
- 成功写入磁盘或确认无缩略图才 `markSettled`；瞬时失败 `markFailed`，不在循环内热重试。
- 日期范围变化只重排未完成项，不重新处理已完成照片；真实状态唤醒时才 `retryFailed`。
- 前台任务抢占时取消当前请求；同一 queue revision 将当前项放回队首，连接/缓存代际变化则丢弃。
- 磁盘写入被阻塞时停止填充并把当前项放回队首，等待下一次连接/状态唤醒。

## 6. 磁盘缓存键、迁移和清理

- 根目录下按相机稳定身份建立 `camera_<SHA-256(identity)>` 子目录；相机身份不能使用临时连接对象地址。
- 普通照片键：`SHA-256(fileName + NUL + size + NUL + captureDate.orEmpty()) + ".jpg"`。
- STA 直读键：`SHA-256("sta" + NUL + unsignedHandle + NUL + size) + ".jpg"`，避免元数据尚未完整时文件名/日期变化；同时尝试迁移旧的同相机标准键，再尝试旧版根目录扁平键。
- `openCamera` 创建目录，写 `.last_connected` 并更新目录 mtime；目录被系统清空后重建内存索引。
- 启动清理窗口固定 90 天（`THUMBNAIL_CAMERA_CACHE_MAX_IDLE_MS`）：删除超过 90 天未连接的相机目录；删除 `.tmp` 和零字节文件；删除旧版根目录扁平 JPG。磁盘缓存无容量上限。
- 写入必须“临时文件完整写入 → 长度校验 → 原子 rename → 再加入索引”；任何失败删除临时文件并返回 false，不能留下索引幽灵项。
- `findCachedFile` 必须验证目标是非空普通文件；命中旧键时迁移，迁移失败仍可读取旧文件但不伪造新索引。
- `reconcile(validNames)` 只在本轮句柄和所有元数据完整成功后调用，仅删除当前相机目录内不在有效键集合中的 JPG。扫描失败、取消、STA 不完整绝不对账。

## 7. FHD、EXIF 和效果预览的让路关系

- `setFhdActive(true)` 先暂停/取消扫描和后台填充并保留快照；`false` 后同一相机从快照恢复。`loadFhdPreview` 读取 FHD/LargeThumb，最长边 1920、RGB_565，不做黑边裁剪，失败返回 null。
- 效果预览请求只记录 demand；`startEffectPreviewPrefetch` 等待传输、监看和 FHD 都空闲后，读取最新静态 FHD（最长边 1920、ARGB_8888）及 EXIF，再原子发布结果。
- EXIF 缓存键为 `fileName_size_captureDate`；null 结果也负缓存。非图片扩展名立即负缓存；JPEG 读头部 128 KiB，RAW/TIFF 最多 2 MiB，解析失败静默返回 null。

## 8. 列表顺序、筛选和顶栏对照

- 日期分组先按拍摄日期前 8 位（无日期使用 `UNKNOWN_DATE_KEY`），组内按完整拍摄时间降序，分组日期降序。
- 筛选必须作用于原始已发布列表；连拍计算也基于原始列表，避免筛选后改变连拍归属。连拍按扩展名、文件名末尾编号连续且相邻间隔 0–1 秒，连续长度至少 3；RAW/JPG 分轨。
- 照片列表顶栏由双 Z 设置、信号胶囊（可展开详情）、类型筛选和宿主持有的传输执行按钮/队列胶囊组成；预览期间整组按 `previewIndex == null` 隐藏。传输按钮只有 PAUSE（传输中）或 START（有等待任务）状态，队列胶囊在文件页或队列非空时显示。

## 9. iOS 复刻实施顺序

1. 先建立独立的扫描状态模型：generation、camera identity、pending、snapshot、known handles、12 项批次发布和取消恢复。
2. 再实现 per-camera 磁盘缓存、内存 LRU、in-flight 合并和 `ThumbnailFillQueue`，先用可控 `CameraSession` 测试所有命中/失败/取消分支。
3. 将 STA/USB 的现有媒体读取接入上述扫描管线；不在 UI 层另写一套加载逻辑。
4. 接入日期分组、筛选、连拍和预览的同一份文件状态，再实现安卓顶栏和队列宿主控制。
5. 最后接入 FHD、EXIF、效果预览让路规则和真机性能检查。每一步都在本文件和 iOS 任务清单记录代码位置、测试证据及尚未验证的分支。

## 10. 2026-09-13 iOS 批次预取对账修正

`ios/ZTransfer/Domain/PhotoListViewModel.swift` 的 `acceptBatch` 现在与安卓
`CameraViewModel.prefetchPublishedFileBatch` 保持相同边界：元数据批次发布后直接执行本批
磁盘预取，成功项才标记 `settled`；扫描批次不会调用 `enqueueNew`，未命中、暂时失败或前台
任务让路的项不在此处标记 `failed`，等完整扫描结束后的 `seed` 再进入后台填充队列。只有
相机事件新增的对象才走 `enqueueNew`。这样不会把扫描阶段的暂时失败变成永久 `pending`，
也不会改变安卓的“批次预取 → 扫描完成播种 → priority/regular 填充”顺序。
