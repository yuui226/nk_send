iOS STA 模式：行为优先级与加载策略

这份表格按当前 iOS 代码整理，描述“现在会怎样”，不是未来设计。STA 是 Wi‑Fi STA 连接；同一套相机 I/O 门控也用于 USB/AP，差异已在对应行标出。代码证据列给出主要实现文件。

监看复核结果见第五至八节。源码不存在单一全局优先级；入口互斥、interactive reservation、ordinary/transfer FIFO 和后台门控分别决定行为。下表已按实际资源关系重写。

四、需要注意的边界

  • “文件列表每次读取新的”和“缩略图复用缓存”是有意分开的：列表必须以相机当前 handle 为准，缩略图则可以按稳定 key 复用。
  • 每批 12 个是普通扫描和后台填充的稳定窗口；STA 直读首屏的 1/3/12 预热序列是当前 iOS 代码明确写出的低延迟策略，并非所有 STA 批次都固定为 12。
  • 缓存命中不代表一定跳过 UI 重建：路由返回时 SwiftUI 单元可能重新创建，但数据源会先从会话模型和 PhotoThumbnailStore 的内存/磁盘缓存返回，不应重新访问相机。
  • 不要把表格行号理解为全局优先级：监看由入口互斥和 remoteActive 控制，预览使用 interactive reservation，传输、扫描和可见缩略图则在锁中按各自 kind 调度。
