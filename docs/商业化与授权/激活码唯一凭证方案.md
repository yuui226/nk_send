# 激活码唯一凭证方案

## 结论

激活码是授权找回、换机和续费的唯一凭证。设备指纹只回答“这张码当前绑定在哪台设备”，
不得用于搜索、推断或返回该设备历史上出现过的任何激活码、订单或权益。

这条边界保证即使多个手机因为异常 ROM 得到相同设备指纹，也不会互相取得激活码。

## 不变量

1. 未付款的购买请求只能得到待支付订单，不得得到历史激活码或 token。
2. 新购付款确认后生成新激活码，并将该新码绑定到本次订单提交的设备指纹。
3. 找回或换机只能由用户明确输入激活码触发 `/v1/activate`。
4. 年费续原码只能使用客户端明确提交的 `renew_code`；服务端不得按设备指纹猜续费目标。
   客户端没有可用原码时按普通新购发新码，不阻断付款。
5. 待支付订单只按客户端随机 `request_id` 幂等；不得按设备指纹复用其他订单。
6. App 只凭本地保存的随机订单号补完当前付款，不扫描同设备的历史订单。
7. 授权 SharedPreferences 不参加云备份或设备迁移。

## 客户端

### 购买

- 购买页不调用 `/v1/restore`，也不提供“恢复授权”按钮。
- 每次真正创建订单时生成 UUID `request_id`。
- 服务器返回待支付订单后保存 `pending_order`；启动、回前台或网络恢复时只补查这个订单号。
- 普通重试不覆盖仍可支付的 `pending_order`；只在付款落证成功或二维码明确过期时清除。
- 到账后保存服务端返回的新激活码和 token，并在成功页强制展示激活码、提供复制入口。

### 激活与换机

- 重装或换机后由用户输入自己保存的六位激活码。
- `/v1/activate` 成功后，新设备顶替同一码的旧设备；同设备重复输入保持幂等。
- “我要换机”只展示当前本地通行证里的激活码，不查询服务器历史。

### 续费

- 当前年费用户点击续费时，客户端把本地当前激活码作为 `renew_code` 明确提交。
- 订阅到期时同时清除 token、激活码和到期状态，不保留“到期用户”分支。
- 授权到期、被吊销或被换机顶替时只清授权，不删除独立的待付款订单。
- 已到期激活码不能激活或续费；用户再次购买时按新购处理，付款后取得新码。
- 永久版不是续费目标；购买永久版始终生成独立的新永久码。

### 设备身份

- 有效 `ANDROID_ID` 保持旧指纹算法，避免正常存量用户整体重新绑定。
- `0000000000000000`、`9774d56d682e549c`、空值或非法格式不作为设备身份；客户端改用
  `noBackupFilesDir` 内的随机安装 ID。
- 服务端不拒绝旧客户端提交的全零衍生指纹。旧客户端仍能正常付款并获得自己的新码；
  安全性来自“不按指纹猜码”，不是来自拦截购买。

### 备份

`license.xml` 同时从 Android 11 及以下的 `fullBackupContent`、Android 12 及以上的
`cloud-backup` 和 `device-transfer` 中排除。随机安装 ID 位于 `noBackupFilesDir`。

## 服务端

### `/v1/order/create`

- 不查询该 `device_fp` 的 bindings、已付款订单或历史待支付订单来返还权益。
- 新购永远创建当前商品的新订单；付款后新发码。
- 年费订单携带尚未到期且可续的 `renew_code` 时续原码；缺少、已到期、无效或不可续时按普通新购发新码。
- 付款确认时再次检查续费码；若它在建单后、付款前到期，也改为新购发新码，不复活旧码。
- `request_id` 只用于同一次客户端请求的幂等。同一设备指纹、不同 `request_id` 是完全独立的购买者。
- 新订单号使用 120 位加密随机数，总长 32 字符，兼顾支付平台长度限制并避免枚举本地补单凭证。

### 删除的能力

- 删除 `/v1/restore`。
- 删除 `already_pro` 响应。
- 删除按设备指纹查找 `ownedLive`、`paidLive`、永久码或续费码的逻辑。
- 删除按设备指纹复用 creating/pending 订单的唯一索引与查询。
- 删除不再使用的 `idx_orders_fp`，订单只能按订单号或随机 `request_id` 定位。

### 保留的设备指纹用途

- 激活后签发与本机指纹绑定的离线 token。
- 同一码换机时顶替旧绑定。
- 续签时确认这张明确激活码仍绑定当前设备。
- 管理台显示设备与审计激活历史。

## 上线顺序

1. 备份 `license.db`、配置、签名私钥与定价文件。
2. 部署新版服务端；启动迁移会增加 `orders.request_id`、删除旧的
   `idx_orders_creating_fp` 和 `idx_orders_fp`，并创建 `idx_orders_request_id`。
3. 运行服务端付款回归测试，确认旧订单仍可查单和履约。
4. 发布新版 App。旧 App 的“恢复授权”接口已不存在；旧版续费请求没有显式
   `renew_code` 时会按普通新购处理并在付款后发新码，不会按设备指纹猜原码。
5. 对已泄露的激活码单独换码并吊销旧码。代码改造只能阻止再次错误发码，不能让已经被看到的码失忆。

新客户端首次运行在全零 Android ID 设备上时会得到新的随机设备指纹，原 token 因指纹不符自然失效；
真实用户使用自己保存的激活码重新激活即可。此行为只影响异常 ID 设备，正常 ANDROID_ID 继续沿用旧指纹。

## 验收

- 同一 `device_fp` 预置多张有效码，点击新购只能返回新待支付订单。
- 两个请求使用相同 `device_fp`、不同 `request_id` 时，不复用订单、不互相阻塞。
- 同一 `request_id` 并发创建只触达一次支付上游。
- 付款确认后只交付本订单生成或明确续费的激活码。
- 未到期时续费只延长明确提交的 `renew_code`；到期后客户端清码，再购买会获得新码。
- 全零衍生旧指纹可以购买，但不会获得任何旧码。
- 新客户端的两个全零 Android ID 安装生成不同设备指纹。
- `license.xml` 不进入云备份和设备迁移。
