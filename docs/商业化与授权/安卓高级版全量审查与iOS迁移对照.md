## 1. 审查范围与结论

全局检索 `app/src/main` 中 `LicenseManager`、`isPro`、免费常量、高级提示、临期提醒、购买与激活相关引用，直接命中 14 个 Kotlin 文件；继续追踪设备身份、相机网络、录制、批处理、资源文案、备份配置、相关测试，以及服务端授权／订单／管理接口。并对照当前 iOS 的传输、监看和录制实现。

结论：**本次找到的全部高级功能权限均能由 StoreKit 2 的有效权益驱动，没有发现必须因为苹果内购而删除的高级功能。** 但安卓整套商业化流程不能照搬：授权身份、换机、续费、发码、退款吊销与人工改有效期有明确平台差异。当前无自建后台方案能完成主要购买和解锁需求，不能同时承诺保留安卓后台所有控制能力。

“全量”指本次仓库当前代码中找到的完整高级版调用链，不代表动态行为已全部测试，亦未查询线上价格、订单数据库或 App Store Connect 实际配置。

### 1.1 已确认：取消自有激活码，以苹果购买权益为准

- **iOS 不生成、输入、复制或保管我们自己的激活码，也不展示用于绑定授权的设备码。** 安卓的激活、续签、解绑、换机顶替流程不迁移。
- 权益关联购买时使用的 **Apple 账户，即“媒体与购买项目”账户**，不是手机硬件、设备 UUID，也不一定是登录 iCloud 的账户。同一购买账户在支持的设备上恢复权益，不需要重新付费或转移激活码；两种商品均已确认不开家庭共享。
- App 不管理 Apple 账户登录、不要求用户提供苹果邮箱／密码、不另外加入“通过 Apple 登录”作为购买前提。StoreKit 返回的已验证权益才是业务依据，不以设备指纹、iCloud 标识或自建账户替代。
- “恢复购买”通过 `AppStore.sync()` 后重新读取有效权益完成；正常启动先读 `Transaction.currentEntitlements`，无需用户每次手动恢复。恢复入口不等于续费、退款或取消订阅。
- `appAccountToken` 是开发者用于关联**自有服务账户**的可选 UUID，不是苹果账户 ID 或新的激活码；本次无自有账户体系，不为使用 StoreKit 而强行引入它。交易 ID／原始交易 ID 用于识别交易与订阅关系，也不能当成苹果邮箱或全局用户 ID。
- 账户切换后以 StoreKit 刷新结果重新评估，不长期沿用旧账户的本地 `isPro`；App 无法自行读取苹果登录凭据来比对账户，离线时也不能承诺立刻知道账户、续费或退款的最新变化。
- **用户已确认支持苹果优惠码兑换解锁。** 用户兑换的是苹果管理的优惠，兑换后由 StoreKit 交易交付对应权益；不另建发证系统，不接受安卓激活码直接解锁。赠送期限／折扣／优惠后续费规则尚待具体配置。

依据：[购买账户与 iCloud 账户可不同](https://support.apple.com/en-us/117294)、[StoreKit 购买与跨设备恢复](https://developer.apple.com/storekit/)、[主动恢复购买](https://developer.apple.com/documentation/storekit/appstore/sync())、[appAccountToken 的实际用途](https://developer.apple.com/documentation/storekit/transaction/appaccounttoken)。

### 不可混淆的四个区别

1. **两种购买都能解锁功能，不代表能自动互相替换。** 年费改买永久不自动关闭年费，亦不自动退剩余年费；用户已接受通过苹果管理页自行取消的替代流程。
2. **不建数据库，不等于没有授权逻辑。** App 仍需验证、恢复、到期／宽限期处理和各功能门控；苹果不会统计每天传了几张或监看了几分钟。
3. **同一 Apple 账户多设备使用，与家庭共享是两件事。** 即便不开放家庭共享，也不能沿用“换到新手机就使旧手机失效”的安卓承诺。
4. **技术上能退款申请，与开发者能随意吊销不是一回事。** 普通 StoreKit 提供用户退款申请 UI；Advanced Commerce 的取消／撤销接口需要特定资格与服务端调用，不在本次方案中。

苹果依据：[购买与跨设备恢复](https://developer.apple.com/storekit/)、[订阅管理与套餐模型](https://developer.apple.com/app-store/subscriptions/)、[退款申请](https://developer.apple.com/documentation/storekit/transaction/beginrefundrequest(for:in:))、[Advanced Commerce 资格](https://developer.apple.com/in-app-purchase/advanced-commerce-api/)。

## 4. 优惠码兑换及其他运营替代

- **赠送高级版：**用户已确认支持苹果优惠码兑换解锁。苹果优惠码支持非消耗型等内购，也支持年度订阅免费／优惠期。在 App Store Connect 创建并由用户通过苹果兑换，不需要搭建自己的激活库。它不是安卓六位码：有商品审批、兑换资格、次数、有效期和系统版本要求。具体活动和入口布局待定；订阅免费优惠可配置优惠结束不自动续费，但并非所有优惠都默认如此，也不代表兑换新码会自动取消其他既有订阅。
- **补偿延期：**苹果 App Store Server API 有订阅延期能力，但适用于符合条件的服务中断补偿，具有期限和次数限制，需安全的服务端或受控管理工具调用。它不是给任意用户随意加天数的客户端接口；无后台首版不把它列为必做，也不把签名私钥放 App 内。
- **年费送永久：**可考虑让用户兑换永久商品优惠码，之后仍需处理旧年费续订；不能只把本地 `expirationDate` 改成空值假装苹果永久购买。
- **调整售价：**App Store Connect 能改价／配置可售地区，现有订阅者可能保留旧价格；新购展示价不能直接当成所有老用户下一次的实际续费价。涨价同意、保留旧价和优惠是苹果各自的规则，不照搬服务器全员即时替换价格。
- **售后入口：**用户确认退款交给苹果，App 只响应实际权益变化并复用免费规则，不新增自有退款流程或独立申请按钮。保留苹果官方退款渠道说明／反馈；申请处理中不提前降级，明确撤销后重算，仍有其他有效高级权益则继续高级。

苹果依据：[内购优惠码](https://developer.apple.com/help/app-store-connect/manage-in-app-purchases/create-offer-codes-for-in-app-purchases)、[订阅优惠码](https://developer.apple.com/help/app-store-connect/manage-subscriptions/set-up-subscription-offer-codes)、[订阅延期适用范围](https://developer.apple.com/documentation/appstoreserverapi/extending-the-renewal-date-for-auto-renewable-subscriptions)、[定价和老用户价格](https://developer.apple.com/help/app-store-connect/reference/pricing-and-availability/in-app-purchase-and-subscriptions-pricing-and-availability)。

### 4.1 用户提出的“优惠一部分，剩余仍走苹果付款”

**年度订阅与永久非消耗商品均有苹果官方付费优惠码机制，不限于免费赠送。** 非订阅内购在后台选择 `Paid Offer` 并指定优惠后售价；订阅选择支持的付费优惠形式、持续时间及优惠价格。用户兑换后仍由苹果展示实际优惠付款条件并收款，最终凭验证后的交易交付；不是输入码后直接设置高级标记。

- **按优惠后价格配置，不是任意面额代金券。** 例如以暂定人民币目标价举例：年费 ¥39.99 减 ¥10 对应配置优惠价 ¥29.99，永久 ¥99.99 减 ¥20 对应 ¥79.99。以上仅解释机制，金额是否可选须核对苹果价格档位，不能记为活动已确定；App 不自行在 `purchase()` 中传减免金额，也不新建低价“永久版”商品来模拟每张券。
- **年费明确优惠覆盖几期。** 若活动是首年优惠，应配置一年的付费优惠，之后按苹果向用户说明的标准年费续订；不是以后每年都减同样金额。现有订阅用户兑换可能作用于后续续订期，不能承诺对已经支付的订单追溯立减或退款。
- **免费赠送与付费折扣分别配置。** “免费优惠结束不自动续费”的可选规则只适用于苹果支持的免费优惠，不照搬到付费折扣。付费年费仍有自动续订，用户可取消；永久折扣购买仍是一次付清。
- **兑换就是购买流程的一条入口。** 使用苹果兑换界面／链接完成优惠校验和付款。无需自制验码服务器，不把普通 `Product.displayPrice` 当成用户已兑换的最终优惠价格；以苹果确认单为准。兑换成功产生交易后直接交付，不再让用户回到原价按钮重新买一次。
- **统一交易接收。** App 外兑换由 `Transaction.updates`／后续权益刷新接收；如果所选系统 API 直接返回验证后的交易结果，也送入同一处理器。按最低 iOS 16 做 API 可用性分支，永久优惠码的 iOS 16.3 支持要求仍保留；不把新 SDK 示例直接当成最低系统可调用接口。
- **活动参数按需配置。** 指定商品、地区、资格、优惠价／期限、兑换次数及截止时间；定向发放优先考虑一次性码。停用未兑换码不等于撤回已兑换权益，仍以苹果交易状态为准。

依据：[非订阅内购付费／免费优惠及优惠价格配置](https://developer.apple.com/help/app-store-connect/manage-in-app-purchases/create-offer-codes-for-in-app-purchases)、[订阅付费优惠及自动续期规则](https://developer.apple.com/help/app-store-connect/manage-subscriptions/set-up-subscription-offer-codes)、[兑换界面与交易交付](https://developer.apple.com/documentation/storekit/supporting-offer-codes-in-your-app)。本轮未登录 App Store Connect、未生成优惠活动／代码或验证实际优惠付款。

## 5. 不能照搬的动态状态缺口

以下为源码推导出的风险，未在安卓或 iOS 实机复现，不写成已确认的运行结果；本轮不改安卓代码。

### 5.1 页内到期和跨日可能沿用旧监看额度

`RemoteScreen.kt:451` 用不带日期或授权 key 的 `remember` 初始化 `trialLeftMs`。高级版进入时初值来自 `Long.MAX_VALUE`；若留在页面期间降级，`if (!isPro)` 会开启计时，但没有重新读取当天免费余额。免费状态跨自然日也没有重新装载页面剩余时间，账本换日不等于页面倒计时自动重置。

iOS 实施要求：在授权变化、日期变化和前后台恢复时协调当前页面计时与账本，避免无限试用或误扣；先定义并测试状态切换，不能复制“只在进页读一次”。

### 5.2 录制权限必须在异步返回后复查

`startRecorder()` 有 `isPro` 检查，但麦克风授权返回直接调用 `startRecorderResolved()`；后者仅检查是否已录制，没有再次验证高级权限。等待系统授权期间若到期／退款，存在绕过起录前门控的窗口。

`RecControlBar` 注释假定“免费用户不会正在录制”，实际停止分支仍允许执行，这是应保留的保护。iOS 需在真正开录前复查，并确定已经录制时降级的结束／保存策略；不能让用户因权限失效无法停止或保存已录内容。

### 5.3 两类效果图任务的权限快照时机不同

- 相机传输后的派生图：`TransferViewModel.kt:2959` 在真正轮到渲染时重新读取 `isPro`；查重与导出共用同一生效水印。
- 本地工作台：`LocalPhotoEffectsOverlay.kt:327` 点击生成时传入效果快照，`LocalPhotoBatchViewModel.kt:50` 后续批次直接使用该快照，没有逐张重新读取授权。

以上是安卓代码事实。**用户随后明确“已加入队列的肯定不改变水印”，iOS 实施以此为准：所有任务在入队时按当前权限计算并固定生效水印，相机派生图也不在执行前重新读取权限换水印。** 本地批次在点击生成建立任务时固定快照；仅选择照片尚未生成不算已入队。

该差异由用户明确授权。已入队快照用于查重、渲染和原任务重试，升级／到期／退款／设置编辑都不回写旧任务；相机下载后创建派生子任务要继承原入队快照。新建任务用当时权限。水印图片素材也保持任务期间可用且不可被覆盖，不能只有结构体不变而其引用图片已经改变。此规则不冻结全局高级权益，传输额度和大小限制仍按各自业务节点执行。

### 5.4 待批准的旧年费稍后到账

安卓支持同时存在不同商品旧订单；苹果可能出现年度购买待批准、用户后来买了永久、旧年度随后获批。即使本机禁用了重复点击，也不能保证账户层面只发生当前选中的一笔交易。

接收任何已验证交易时按商品与实际权益更新，并重新判断是否出现“永久＋年费仍自动续订”。提醒不能只放在刚买永久成功的那一刻。已处理交易 ID 后续撤销也不能被幂等去重丢弃。

待批准年费转为 subscribed 的通知可能先通过 `Product.SubscriptionInfo.Status.updates` 到达。其 `transaction` 和 `renewalInfo` 均验证通过时，将该交易交给既有交付处理器，不能只刷新年费展示、继续等待另一条通知清 pending。重复到达仍按同一交易的新旧签名合并和庆祝去重；其他续订状态沿用刷新流程。苹果 API 依据：[状态更新序列](https://developer.apple.com/documentation/storekit/product/subscriptioninfo/status-swift.struct/updates)、[状态携带的最新交易](https://developer.apple.com/documentation/storekit/product/subscriptioninfo/status-swift.struct/transaction)。这是本项目对两个事件入口的处理策略，不推断苹果保证两路通知同时到达。

购买进行中仍阻止并发重复点击，但 `.pending` 返回后不得用本地标记一直禁用同一商品。苹果 [Ask to Buy 测试说明](https://developer.apple.com/documentation/storekit/testing-ask-to-buy-in-xcode) 明确拒绝请求不会向 App 交付交易；因此没有可靠的拒绝回调可用于解除本地禁用。允许用户主动再次调用苹果购买流程，由苹果决定请求结果，保留晚到交易监听；不加自动重试、拒绝倒计时或自有订单轮询。安卓依据是 `PurchaseDialog.kt`／`PurchaseSafety.kt` 中失效订单可重建、失败后可重试的行为目标，Ask to Buy 是苹果特有状态。

### 5.5 默认状态和临期文案不能沿用安卓假设

安卓年费到期清码，用户回到新购流程；苹果仍有可恢复历史及可能的续订、宽限期。加载中、无权益、暂时离线、价格获取失败、待批准必须分开；正常自动续订不能每到 30／7 天就被提示“授权即将失效，请再买一年”。

## 9. 合理性复核与精简建议

本节是对第 8 节的进一步约束，不能把提出问题等同于功能存在实测故障。**技术表述修正已同步到主方案与台账；涉及体验或权益变化的建议未擅自定案。**

### 9.1 已收紧的技术方案

1. **权益交付不等待价格和无关详情。** 原“全量刷新完成再发布”只适用于一次权益枚举的一致性，不等于把价格、续订详情、当前权益绑成一个全成功事务。永久已确认就开放永久；新购买已验证且有效就及时交付。年度续订详情失败独立显示未知，不能锁住另一份确定有效权益。宽限期仍按苹果有效状态处理，不能先按旧 `expirationDate` 过滤掉再查询宽限期。
2. **不复制苹果的交易存储和发证系统。** StoreKit 负责提供设备端交易资料及验证结果；本方案用统一内存状态、必要显示缓存和本地免费用量。没有必要额外做自签 token、自己的苹果账户表、手写证书链验签、每周联网续证、全量订单数据库。跨启动缓存若确有实测需要再专门设计，不能把“缓存用于离线”理解为永久信任旧 `isPro`。
3. **一个交易处理器，事件驱动刷新。** 保留本机购买返回、应用级更新监听、主动恢复。启动一次未完成交易扫描是合理的恢复措施，苹果示例也采用这一组合；多余的是每个页面、每次前台切换都新增监听或扫描所有历史。合并同时发生的刷新请求、忽略旧结果；`AppStore.sync()` 只在主动恢复时调用，不自动弹认证。
4. **权益幂等和庆祝去重分开。** 年费／永久不是要累计发放的金币，不需要记录所有订单来保证“只加一次”。权益由当前有效交易归并；同一交易后续撤销仍处理。首次见到某个交易可能是历史恢复或自动续费，不能因此放新购烟花；庆祝必须关联实际用户购买流程。`finish()` 在业务交付后完成，不等待动画或用户取消另一项订阅。
5. **监看每秒记账，不能只等退出。** 第 8 节原描述不够稳妥，已修正为沿用安卓每秒累计＋停止收尾。计时按实际经过时间，离开监看／会话停止后不累计；不能把“端侧录制暂停”当成“停止监看”，也不能因单次视频帧间隔就重置计时。降级后不补扣之前的高级时段；跨日重读新日账本，不保留“无限”倒计时。系统中断后的持久化误差要验证，前后台生命周期仍须按主方案待定项验收，不能承诺退出回调总会执行。
6. **不为串行队列预建复杂额度锁。** 当前 `TransferQueue.startWorkerIfAllowed()` 只启动一个 `run()` worker，按任务等待下载；因此原文件额度采用检查→下载→成功记账即可。保留异步重入保护及唯一完成点；效果图后台并行不多占传输次数。以后若真正引入并行原文件下载，再评估额度预占／释放；现在不建通用事务账本。
7. **共用来源不扩大 UI 刷新范围。** 免费余额、监看秒数、商品加载、购买进度与高级权限分别发布。列表和连接动画只观察其需要的权限值；状态未变不重复发布。业务入口的本地布尔／配置判断值得保留，逐帧、逐像素查权益或联网没有必要。模块名是职责提示，不要求为了表格拆成多个相互转发的管理器。

依据：[启动交易监听及未完成交易](https://developer.apple.com/documentation/storekit/transaction/updates)、[苹果包含一次启动恢复扫描的示例](https://developer.apple.com/documentation/storekit/getting-started-with-in-app-purchases-using-storekit-views)、[主动恢复的使用限制](https://developer.apple.com/documentation/storekit/appstore/sync())、[使用设备端资料主动恢复](https://developer.apple.com/videos/play/wwdc2022/110404/)、[StoreKit 验证结果](https://developer.apple.com/documentation/storekit/verificationresult)。本地依据：`RemoteScreen.kt:446–468`、`LicenseManager.consumeRemoteTime()`、`ios/ZTransfer/Domain/TransferQueue.swift` 的 `startWorkerIfAllowed()`／`run()`。
