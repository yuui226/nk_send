ZTransfer 相机任务协作与优先级全景

从连接后的照片枚举，到可见缩略图、后台缩略图填充、FHD 大图、EXIF、原片传输、监看取帧、事件与心跳，统一映射到同一条相机命令通道。本文展示的是当前代码的真实行为，不是理想化设计。

核心瓶颈：单个 ioMutex 锁内任务不可抢占 内存/磁盘命中不占相机 监看入口在传输忙时被阻止
三层模型总架构实际优先级场景切换关键时序影响矩阵边界与结论代码依据
Mental model

先分清三种“优先”

代码没有一个能给任务打 1、2、3 分的全局优先级队列。最终谁先执行，由下面三层叠加决定。

01

入口与状态硬互斥

传输队列存在 WAITING / TRANSFERING 时，照片页直接阻止进入监看。进入监看后又显式取消整卡枚举，并关闭后台缩略图、效果预览和全局事件轮询。

02

任务主动暂停 / 取消

remoteActive、fhdActive、transfersBusy 只影响被代码明确订阅这些状态的任务。没有订阅的任务不会自动停，例如大图预览不会取消整卡文件枚举。

03

ioMutex 不可抢占串行

一项相机事务拿到锁后，后来者只能等待。整文件下载会持锁到当前文件完成；文件枚举最多 20 条为一个锁段，但每条 ObjectInfo 后都有取消检查；FHD、EXIF、缩略图、帧和普通遥控命令按单次事务持锁。

最重要的判断：“监看优先级最高”在正常 UI 路径上成立，是因为传输忙时根本不允许进入监看，而且进入后主动清场；它不是靠 ioMutex 把正在下载的文件强行抢断。
Architecture

所有相机 IO 如何汇入同一通道

缓存命中、位图解码、派生图导出以及下载后的改名/复制不占相机锁；原片接收过程中向输出流写数据属于整文件下载锁段。只有确实需要向相机取数据或发命令的路径才进入通道。

Effective priority

当前代码的实际优先级梯队

同一梯队内部没有稳定的“谁一定先拿锁”承诺。表中的优先级是状态门和持锁粒度共同形成的有效结果。

S
监看页面（正常入口）进入前要求没有 WAITING / TRANSFERING；进入后取消整卡枚举，停后台缩略图、效果 FHD、全局事件轮询。帧、参数、AF、快门和监看自己的事件循环继续共享 ioMutex。
不是抢占：它靠“禁止与传输同时进入 + 主动清场”获得最高有效优先级。监看事件中的 ObjectAdded 仍会临时取一次 ObjectInfo。
A
已拿到锁的当前事务任何任务一旦进入 ioMutex 都不能被后来者抢断。原片传输最重：当前文件（即使分块）全程持锁；整卡枚举最多 20 条为一个锁段。
这是最高的运行时事实。监看取消枚举时，每条 ObjectInfo 后的取消检查可提前结束锁段；未取消它的 FHD / 传输则仍要等当前批结束。
B
已经发起的前台请求原片传输、大图 FHD / EXIF、可见格缺失缩略图和监看控制命令之间没有业务级重排。大图自己的协程固定为：当前 FHD → 当前 EXIF → 左邻 FHD → 右邻 FHD。
请求真正到达锁的时机决定等待关系。FHD 请求发出时，remoteThumbGate 只能保证同时已进入或等待 ioMutex 的远程 GetThumb 至多一条；它不能越过其它任务。
C
渐进列表与事件增量整卡枚举按 handle 降序（通常对应新→旧），最多 20 条一批并在批间释放锁；ObjectAdded 只读取该 handle 的一条 ObjectInfo。
传输或大图打开时，整卡枚举不会被它们显式停止；只会在 ioMutex 上等待。监看是唯一会取消完整枚举的前台状态。
D
后台与维护任务后台缩略图 sweep、设置效果 FHD、全局事件轮询、10 秒心跳。sweep 受三大前台状态和 effectPreviewActive 控制；效果 FHD还会等 files 安静 900ms。
心跳不参与这些暂停门，仍会排 ioMutex；设置效果 FHD 也不会暂停枚举或事件，只在自己实际加载时让 sweep 停下。缓存命中和本地派生不占相机通道。
Interactive scenarios

切换场景，看每项任务此刻在做什么

“等待”表示代码没有主动暂停，但需要等 ioMutex；“暂停”表示状态门明确不再发请求；“按需”表示只有缓存缺失或事件发生时才访问相机。

Timelines

四条最关键的真实时序

这些顺序解释了为什么有些行为看似“停住”，实质是在等待当前锁持有者收尾。

连接成功 → 照片页

建立相机会话

成功态先发布，立即启动 keepalive、loadFiles 和事件轮询。

枚举存储与 handles

读取卡槽和全部对象句柄；新会话清内存缩略图/负缓存与效果预览，磁盘缩略图保留。

ObjectInfo 最多每 20 条发布

照片列表渐进出现；每次 files 更新会重启后台缩略图扫描与效果预览 900ms 静默计时。

连接庆祝后进入照片页

页面出现前列表和后台缩略图已经工作；可见格开始内存/磁盘/远程三级加载。

打开大图预览

固定当前展示模型快照

只复制当时已经加载且经过筛选/合集展开的条目；后续列表新增不会把当前页换掉。

fhdActive = true

暂停后台缩略图、效果 FHD、全局事件轮询；不暂停整卡枚举、传输或底层仍在组合的可见格。

先完成展开动画

动画结束才开始高清图与 EXIF，避免大位图上传影响动画。

当前 FHD → 当前 EXIF → 邻页 FHD

同一协程严格串行。视频跳过 FHD；当前页变化会取消旧序列并按新页重启。

关闭 overlay

fhdActive = false，后台缩略图和全局事件恢复；大图会话内缓存随 overlay 释放。

加入传输队列

任务先成为 WAITING

transfersBusy 立即为 true：停后台缩略图、效果 FHD、全局事件，并阻止进入监看。

先做本地目录与已存在检查

命中本地原片可直接完成或生成派生图，不访问相机；这段短时间仍因 WAITING 而触发 busy 门。

下载拿到 ioMutex

当前整文件的数据接收与输出流写入都在锁段内；大文件的 PartialObject 分块也不在块间释放。其它远程请求等待。

数据阶段结束后释放相机

输出流关闭/冲刷、改名/复制以及边框/滤镜不再占相机锁。派生图在低优先级线程进行，任务已 COMPLETED，不再算 transfersBusy。

处理下一 WAITING

队列清空后 busy 门解除，后台工作恢复。失败任务当前需要用户手动重试。

进入 / 退出监看

入口先检查传输忙

只要有 WAITING / TRANSFERING 就不给进入，因此正常路径下不会与原片下载并行。

remoteActive = true

取消 fileLoadJob 并保留 pending；若正在读 ObjectInfo，最多让当前一条事务收尾。后台缩略图、效果 FHD、全局事件停止，照片页离开组合。

参数优先，随后启动 Live View

先读取模式与参数，再 StartLiveView；帧获取和解码并行，帧通道只保留最新一帧。

监看自己的事件循环接管

全局 GetEvent 已停。监看约 600ms 轮询；ObjectAdded 会转交 VM 单独读取该对象信息并插入列表。

退出后恢复未完成枚举

页面销毁会取消 LV 会话并令 remoteActive = false；两项清理没有额外业务顺序，仍由 ioMutex 串行。若 fileLoadPending，则保留已发布条目、重新取 handles、跳过已有 handle 后继续。

Decision & caveats

判断“下一项是谁”的最短路径

先判断是否需要相机，再看硬门，最后才看 ioMutex。这样比背一张静态优先级表更准确。

STEP 1
内存 / 磁盘已经命中？

是：立即完成，不参与相机优先级。

→
STEP 2
任务被当前状态门暂停？

remote / busy / FHD 只暂停各自订阅者。

→
STEP 3
是否是 GetThumb？

是：先过 1 许可门，避免堆满锁队列。

必须知道的边界

  • ioMutex 不是优先队列。代码没有保证 FHD、下载、ObjectInfo 谁在锁释放后的下一拍必定先拿到。
  • 下载不可被监看抢断。正常 UI 在下载开始前就阻止进入监看，因此用不到抢断。
  • 大图不是全局最高优先。它只暂停后台缩略图、效果预览和全局事件；整卡枚举与传输仍可能挡在前面。
  • 缩略图有两类。后台全量填充会停；可见格按需加载不会因 transfer busy 自动停。
  • 监看不是“列表永远零更新”。完整枚举停止，但监看事件收到 ObjectAdded 后会单独读取新对象信息并插入列表。
  • 页面 ≠ 后台任务。去队列页会销毁可见格加载，但空闲时后台缩略图扫盘仍继续。
  • 筛选/折叠只改变前台组合。被过滤或折叠的格子不会触发可见项加载；后台仍扫描全部 files，只有日期范围会改变其先后顺序。
  • “停止传输”不打断当前文件。它只把尚未开始的 WAITING 改为 CANCELLED；TRANSFERING 会自然完成，因此监看入口继续被挡到该文件结束。
  • 断点续传只保证当前 App 会话内的普通失败。多数失败保留 .nkpart_ 供手动重试；无法续传/保存失败可能删除它，重新启动 App 还会清扫上次遗留的半成品。
  • 监看内部还有两层锁。AF 用 focusMutex 固定整套流程，帧可在 AF 轮询间穿插；USB 录像启动使用 focusMutex + ioMutex 原子序列，期间帧也要等待。

当前实现形成的全貌

  • 监看：最强硬互斥，正常情况下独占“业务流量”，仅保留自身命令、事件、心跳和新增对象的单条信息读取。
  • 传输：对后台任务有硬暂停；对整卡枚举、大图和可见缩略图只有锁层面的等待关系。
  • 大图：前台体验优先于后台扫盘，但没有压过下载或 ObjectInfo 批次。
  • 列表：元数据最多 20 条共用一个锁段、每条后检查取消；缩略图每次一条远程请求，普通竞争者在批间协作，监看取消可在当前 ObjectInfo 后生效。
  • 本地后处理：边框、滤镜、解码、磁盘缓存和 SAF 操作不占相机通道，可与相机任务并行。
