## 调度器结论

本次两个新提交没有改变通用相机调度器。调度器的唯一行为依据仍是
[全局任务调度器权威逻辑](../技术调研/全局任务调度器权威逻辑.md)以及安卓最终
`NikonCamera.CameraIoGate`。其关键契约已经在原台账 N01/N02 记录并接入 iOS：

- P0 交互、P1 预览、P2 传输、P3 评级、P4 可见缩略图、P5 目录/后台缩略图、P6 空闲；同级 FIFO，已入场事务不可抢占。
- 评级阶段以计数屏障挡住 P4/P5/P6 和后台事件；P0/P1/P2 只能在当前事务边界插入。
- 下载活动计数覆盖整文件和分块间隙；心跳提交前与入场后各检查一次，存储余量命令等待活动下载结束。
- shutdown 拒绝新的普通业务事务，只保留显式允许的关闭事务；连接重建产生全新的 gate 和评级代次。
- 本地缓存、解码和绘制不进入相机命令队列；连接握手和事件 socket 的 PING/PONG 是明确的会话边界例外。

因此本轮不新增“调度器任务”，也不以 `DownloadTrace` 的诊断回调替代调度器。若后续 Android
调度器文档或 `CameraIoGate` 再变化，再回到 N01/N02 做逐 hunk 审计。

## 新增提交逐项核对

### `8138e2de`：按文件类型存放的最终目录语义

这是已有“统一/按天/按类”保存功能的最终修正，不是一个只改文案的变更。必须迁移到 iOS 的事实是：

1. 设置项仍有三档：统一存放、按天存放、按类存放；旧的布尔 `organize_transfers_by_date` 只兼容映射到按天，新的状态使用 `TransferStorageMode`。
2. 按类目录由源文件最后一个扩展名生成：去首尾空格、使用大写、加固定 `ZT-` 前缀；例如 `JPG`→`ZT-JPG`、`NEF`→`ZT-NEF`、`MP4`→`ZT-MP4`，没有扩展名为 `ZT-UNKNOWN`。
3. 目录名必须经过提供方安全校验：`[A-Za-z0-9][A-Za-z0-9._-]{0,63}`；不能把旧的只允许 `ZTyyyy-MM-dd` 的日期正则继续用于按类目录。
4. 任务入队时锁定目标目录。设置之后改变保存方式，不能搬移已经排队的原片或其 `ZTFrames` 派生图；效果图仍在该目标目录的独立 `ZTFrames` 子目录。
5. 已传索引、照片列表对号、未传筛选、目录扫描、重名分配和重试续传必须使用同一个目标目录键。按类模式扫描根目录下所有符合条件的类型目录，但不能把 `ZTFrames` 当作原片类型目录。
6. 目录缓存从“日期目录缓存”泛化成“目标目录缓存”，在传输根目录或树失效时一起清除，避免旧 URI 被复用。

安卓依据：`TransferViewModel.kt` 的 `TransferStorageMode`、`storageTypeFolderName`、
`isValidTransferFolderName`、`createQueueTasks`、`refreshExistingExportFiles`、目录索引和设置拨轮；
`NewMediaTransferPolicyTest` 的日期、前缀、非法目录名和任务快照测试。此项归入原台账 N11，不能另写成
“按类型类似支持”。iOS 当前只有日期目录快照和 `destinationFolderName`，尚未有三档设置及 `ZT-` 类型目录闭环。

### `f40f6bbf`：传输损坏取证诊断（诊断构建专用）

这次提交没有新增普通用户入口，也不改变默认传输路径；它通过 Gradle 属性
`-PtransferCorruptionDiagnostic=true` 生成一次性调查版，并由 `BuildConfig.TRANSFER_DIAGNOSTICS`
同时控制协议追踪和完整性取证。正常构建必须保持零额外读取、零哈希、零报告写入。

诊断版在一个传输队列会话中记录五层证据：

- **R**：相机协议交给输出流之前收到的完整字节，整文件 SHA-256、字节数及最多 4096 个 4 MiB 分段哈希；视频续传还先读取已有前缀再合并。
- **T**：临时 provider 文档关闭后读回；**F**：改名/复制后的发布文档读回；比较 R/T/F 的大小、整文件摘要和首个不同分段。
- **L**：队列排空后再次读回所有发布文件，用于发现 provider 延迟写入或改名后的内容变化。
- **C**：队列未暂停、协程仍活动且相机可用时，从相机重新下载到空输出流，不写用户文件，只比较 C 与 R。
- 私有 app 文件追加日志是会话内权威副本，SAF 文本报告只在开始、每 8 个文件和结束时镜像；日志不保留媒体原始字节。

协议追踪 `DownloadTrace` 只在诊断构建接收回调，按一次下载事务聚合 Wi‑Fi PTP/IP 的 transaction id、
START/DATA/END 顺序和异常计数，或 USB 的容器头/响应头/transaction id、读请求、零包和超时计数；不逐包刷日志，
回调异常不能改变传输、取消或连接语义。`NikonCamera.downloadToFile` 新增被动 trace、收字节观察回调和诊断版
视频 4 MiB 分块参数；`UsbPtpConnection` 只提供统计观察。`TransferFingerprintTest` 有 15 个测试，覆盖哈希
分块独立性、空流/边界/上限、首个差异、非法范围、finish 幂等、输出流失败和不触碰下游等契约。

此项先作为独立 N16 调查任务：必须先核对 iOS `CameraDownload`/`TransferQueue`/PTP-IP/USB 的真实字节边界、
临时文件和发布文件生命周期，再决定等价诊断钩子的位置。不能把普通版永久打开二次读相机，也不能把诊断报告做成
用户界面功能；若实现，必须有与安卓相同的显式诊断编译开关、日志脱敏、取消/暂停跳过 C 阶段和“诊断失败不影响传输”保证。
