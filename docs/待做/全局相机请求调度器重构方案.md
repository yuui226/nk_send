# 全局相机请求调度器重构方案

## 目标

将当前分散在 `CameraIoGate`、`NikonCamera` 各个读取函数和页面状态中的相机让路逻辑，整理为一个统一的事务调度器。

目标不是改变原有产品优先级，而是让每一次相机请求都明确声明类型、优先级、取消规则和诊断信息，避免评级、缩略图、传输和监看之间互相套锁、重复判断或形成自我等待。

星级读取也必须接入同一调度器。评级扫描只决定文件范围和解析结果，不再自己决定相机通道何时可用。

## 重构前基线（留档）

重构前代码已有 `CameraIoGate`，但它是“互斥锁 + 交互等待计数 + 传输切片”的组合：

- `withInteractive` / `withInteractiveTagged`：交互命令取得通道。
- `withInteractivePriority`：登记交互优先等待者，影响传输切片是否能够进入。
- `withTransferSlice`：传输、缩略图和部分后台读取使用，每次事务结束释放。
- `withDownloadActivity`：标记完整下载活动，供心跳和低优先级检查跳过。
- `withIdleCommand`：没有完整下载时才执行普通命令。
- `ioMutex`：仍被部分旧入口直接使用。

当前风险：

- 请求类型没有统一枚举，优先级由调用方隐式决定。
- 一个外层优先级预约包住整段业务时，内部再次申请通道可能自我等待。
- 直接使用 `ioMutex` 的旧入口可能绕过让路规则。
- 评级、视频评级、缩略图和传输对“一个事务”的边界定义不一致。
- 取消、断线和残留 PTP 响应的处理分散在各个函数。

### 重构前评级实现的事实边界（留档）

这里记录的是重构前的代码事实，不能作为当前工作区的实现说明：评级扫描外层曾通过 `withPhotoRatingPriority` 登记交互优先等待者；每次 JPG/NEF、视频或对象读取内部再调用 `withInteractiveTagged("RATING")`。前一次把评级读取改成普通传输切片的临时实验已经回滚。

当前 STA 还存在一个独立的产品边界：`recentThumbnailReady` 主要在已发布批次确认达到三个拍摄日时置位；少于三个实际拍摄日的相机内容，可能要等权威列表结束才满足条件。调度器只负责相机通道排队，不改变这个范围判定。

## 当前工作区实现状态

本轮代码已经落地统一调度器，以下内容以代码为准：

- `CameraIoGate` 内部使用一个按优先级和到达顺序选择的事务队列；业务层不再直接持有 `ioMutex`。
- 监看/遥控为 `INTERACTIVE`，大图和当前 EXIF 为 `PREVIEW`，传输分块为 `TRANSFER`，评级文件头或视频结构小范围读取为 `RATING`，可见缩略图为 `VISIBLE_THUMBNAIL`，目录与后台缩略图为 `BACKGROUND_THUMBNAIL`，心跳和存储检查为 `IDLE`。
- 评级扫描不再持有整段优先预约；每个文件或结构区域独立提交一个 `RATING` 事务，因此在事务边界可以让给监看、遥控和传输。
- 本次连接的评级快照不会被对象变更事件反复失效或重扫；事件线程只投递事件，星级值在下一次连接重新读取。
- 目录与 STA 直读路径保留重构前的批次事务边界；每批列表仍按原顺序发布，批间释放相机通道，避免改变首屏和分页行为。
- 缩略图在内存或磁盘命中时不会进入调度器；评级未运行时，传输和缩略图继续沿用重构前的同级 FIFO；评级阶段只有远程缩略图排在评级事务之后。
- 传输仍由 `withDownloadActivity` 记录整文件活动，并以每个完整分块提交 `TRANSFER` 事务；现有取消时的 Cancel/排空逻辑仍在下载事务内部执行。
- 会话关闭会先进入 shutdown 闸门：拒绝新的业务 ticket，清空尚未入场的等待项；已经入场的当前事务仍由自身的协议收尾逻辑完成，只有关闭事务可以在闸门关闭后入队并取得下一个槽位。

少于三个实际拍摄日时，权威列表的最后一批缩略图完成后即可把现有日期范围视为完整；调度器不猜日期边界，只接收照片列表发出的 ready 信号。

## 当前运行方式（按代码逐步对照）

调度器只负责“已经建立会话后的相机命令通道”。手机本地的解码、Compose 绘制、文件复制、效果图生成和缓存查询不进入队列；连接握手仍按原来的顺序完成，事件线程只投递事件，不直接在相机命令通道发业务命令。

每个运行期相机请求都经过下面这条固定链路：

1. 调用方在发出第一条 `sendCmd` 或读取响应前选择一个 `CameraRequestKind`，并给出可诊断的 `owner`。
2. 调度器创建一个带到达序号的 ticket 放入统一队列。ticket 一旦排队，不会再被业务层改成另一种优先级；需要改变意图时取消原请求并重新提交。
3. 调度器从当前可执行的 ticket 中选择优先级最高者；同一优先级按到达顺序执行。正在执行的完整 PTP 命令/数据阶段不会被打断。
4. ticket 获准后取得底层互斥通道，执行 block 内的完整协议事务。block 内禁止再次申请调度器事务，避免嵌套自等待。
5. block 正常返回、异常或取消后都释放通道，再唤醒下一项。等待中的取消只移除自己的 ticket；已入场事务的取消必须由调用方完成已有的 Cancel、排空和关闭协议收尾。

可以把优先级理解为“下一项谁先获得相机通道”，不是线程优先级，也不会让两个 PTP 数据阶段并行：

| 级别 | 当前交给调度器的行为 | 事务边界 | 何时让路/何时恢复 |
|---|---|---|---|
| P0 `INTERACTIVE` | 监看取帧、拍摄、录像开始/停止、对焦、参数写入、旋转、遥控实验命令、会话关闭 | 一条命令或一个不能拆开的遥控步骤 | 永远优先于排队的后台工作；多步对焦只保证每一步串行，步骤之间可重新选出更高优先级请求 |
| P1 `PREVIEW` | 当前高清图、FHD、当前照片 EXIF | 当前照片的一次完整远程读取 | 等当前已入场传输分块结束后取得通道；邻页预取不享受当前页待遇，传输繁忙时不启动或延后 |
| P2 `TRANSFER` | 原片下载的每个分块 | 一个完整数据分块；完整下载另有活动标记 | 分块中不可抢占；分块结束后重新排队，P0/P1 可以在下一块前进入。下载活动只让 P6 空闲探测跳过，不阻止正常分块继续 |
| P3 `RATING` | STA 最近三个拍摄日的照片头、视频结构区域；可用时的对象评级命令 | 一张照片头或一个视频结构区域；不是整场扫描 | 评级开关关闭或三日缩略图锚点未到达时不提交；开始后不占整场预约，P0/P1/P2 在下一个评级事务边界优先，评级完成后远程缩略图才继续 |
| P4 `VISIBLE_THUMBNAIL` | 首屏/当前可见的缺失缩略图 | 一张缩略图的一次请求 | 评级启动前可先执行；评级启动后排在 P3 后。内存或磁盘命中不提交 ticket，直接在本地返回 |
| P5 `BACKGROUND_THUMBNAIL` | 旧照片预加载、目录 `StorageIds/ObjectHandles/ObjectInfo`、STA 元数据刷新 | 一条命令或一张后台缩略图 | 让给 P0–P4；照片页离开时取消尚未入场的后台任务，已完成缓存保留 |
| P6 `IDLE` | 心跳、存储检查和其他低频能力检查 | 一条独立命令 | 有完整下载活动时直接跳过；无下载时仍须排在所有其他请求之后 |

代码入口与调度类型的对应关系如下，后续新增相机命令也应先落到这一层，而不是直接访问底层 socket：

| 代码入口 | 负责的行为 | 使用的调度类型 |
|---|---|---|
| `NikonCamera.getThumbnail`、`getFhdPicture`、`getStaFhdPicture`、`readExifHeader` | 缩略图、当前大图/FHD、当前 EXIF | `VISIBLE_THUMBNAIL` / `BACKGROUND_THUMBNAIL` / `PREVIEW` |
| `NikonCamera.downloadToFile` | 原片或视频传输 | `withDownloadActivity` + 每个分块 `TRANSFER` |
| `NikonCamera.readObjectRating`、`readPhotoRatingHeader`、`readVideoRating` | JPG/NEF/MOV/MP4 评级读取 | 每个对象/文件头/结构区 `RATING` |
| `NikonCamera.getStorageIds`、`getObjectHandlesWithStatus`、`streamFileInfo` | 存储卡、句柄和按现有边界读取的 `ObjectInfo` 批次 | `BACKGROUND_THUMBNAIL` |
| `RemoteLab` | 监看取帧、对焦、拍摄、录像、参数写入 | `INTERACTIVE` |
| `MonitorStorage`、`NikonCamera.keepalive` | 存储检查、心跳和低频探测 | `IDLE` |
| `NikonCamera.close` | 取消旧排队项并关闭会话 | 清队列后 `INTERACTIVE` |

`PhotoRatingScan` 和 `CameraViewModel` 只负责决定评级范围、生命周期和何时提交请求；它们不再持有相机锁。`PhotoPreview` 只把当前页和邻页分成不同调用，具体让路由调度器决定。

优先级不是运行中动态修改的字段，而是由“下一次提交的行为”决定。会发生的状态切换只有这些：

- 缩略图从可见变为后台时，下一次请求由 `VISIBLE_THUMBNAIL` 改为 `BACKGROUND_THUMBNAIL`；已经在通道内的请求不变。
- 列表在评级开关打开、最近三个拍摄日的首批缩略图阶段完成后，才创建 `RATING` 请求；列表仍在确定范围时不会先启动一轮又取消一轮。
- 评级开始后，新的远程缩略图仍可提交，但调度器临时把它们排在排队的 P3 之后；评级结束立即恢复传输与缩略图的原 FIFO；缓存命中完全不参与这个竞争。
- 大图只把当前页提交为 P1。当前页的 FHD 与 EXIF 之间允许手机本地解码和调度器重新选择，但兼容适配层会阻止传输抢先开始下一块；邻页没有这个保护。
- 原片下载用 `withDownloadActivity` 标记整文件活动，用 P2 ticket 包住每个分块。它不是把整份文件锁住，也不是把评级改成传输；速度统计只在下载事务内计算。
- 会话关闭先打开 shutdown 闸门，拒绝新的业务 ticket，再取消所有尚未入场的 ticket，并以 P0 提交唯一允许在闸门后执行的关闭事务。已入场的传输或协议操作先执行自己的排空/关闭收尾，关闭事务随后才能获得通道；新连接不会继承旧队列。

因此“评级与缩略图并行”指手机端两个协程可以同时准备和等待：命中缩略图完全本地运行，缺失缩略图与评级各自提交短事务。相机端仍然只有一个命令通道，由上述优先级在完整事务边界有序切换。

## 不变的行为契约

调度器重构不能改变这些已经确定的行为：

1. PTP 命令和数据事务不可被中途打断，只能在完整事务之间切换。
2. 当前已经开始的传输分块必须完成，不能为了评级或缩略图强行截断。
3. 监看取帧、拍摄、录像、对焦、参数写入和大图预览优先于后台工作。
4. 评级启动前，可见区域和首屏远程缩略图优先；评级启动后，新的远程缩略图请求在评级事务完成后再取得通道，缓存命中始终不进入调度器。
5. 内存、磁盘缓存命中不进入相机调度器，不产生相机请求，也不等待评级。
6. 相机断开时取消等待中的后台请求，正在进行的协议事务按现有异常收尾规则结束；不得把旧连接请求带入新连接。
7. 传输速度、监看帧率和照片生成计时不计入评级读取。
8. 调度器只控制相机通道，不控制本地解码、Compose 绘制、文件复制或照片生成线程。

## 统一请求类型与优先级

所有已建立会话后的运行期相机命令必须通过一个事务入口声明 `RequestKind`。连接握手在会话建立阶段按原有顺序串行执行，不进入业务请求队列；会话关闭则通过 `INTERACTIVE` 事务收尾。建议顺序如下：

| 优先级 | 请求类型 | 典型行为 | 事务边界 |
|---|---|---|---|
| P0 | `INTERACTIVE` | 监看取帧、对焦、拍摄、录像、参数写入、旋转等 | 单条命令或一个不可拆协议步骤 |
| P1 | `PREVIEW` | 当前高清大图、当前 EXIF、FHD | 当前照片的一次完整请求 |
| P2 | `TRANSFER` | 原片传输的一个分块、续传分块 | 一个完整数据分块 |
| P3 | `RATING` | 最近三个拍摄日的 JPG/NEF 文件头、MP4 评级结构、AP/USB 对象评级 | 一个文件头或一个评级结构小范围读取 |
| P4 | `VISIBLE_THUMBNAIL` | 评级开始前的首屏和可见区域缺失缩略图；评级开始后在其后执行 | 一张缩略图的一次请求 |
| P5 | `BACKGROUND_THUMBNAIL` | 旧照片缩略图预加载 | 一张缩略图的一次请求 |
| P6 | `IDLE`、`EVENT_POLL` | 心跳、普通事件检查、低优先级能力探测 | 一条独立命令 |

同一优先级内部按先到先执行。高优先级请求只在当前事务完成后取得通道，不能打断当前事务。

兼容旧行为的细节：评级阶段未开启时，`VISIBLE_THUMBNAIL`、`BACKGROUND_THUMBNAIL` 和 `EVENT_POLL` 在队列选择上临时使用 `TRANSFER` 的同级优先级，因此传输、缩略图和普通事件轮询保持重构前的 FIFO；评级阶段开启后，`EVENT_POLL` 与远程缩略图降到 `RATING` 之后，传输仍保持 P2。评级结束立即恢复该 FIFO 规则。

评级阶段还设置低优先级准入屏障：目录、远程缩略图、普通事件轮询和心跳不能在两张评级照片之间的空档抢先开始；已经开始的完整事务不打断，监看、预览和传输仍可在事务边界插入。这样“评级逐张让路”不会因为下一张评级尚未入队而被后台任务反复抢占。

评级不是“整段扫描任务”的优先级；每一次文件读取才是一个 `RATING` 事务。评级扫描本身不得持有通道预约。

## 所有需要迁移的行为

### 监看与遥控

- Live View 取帧和增强取帧：`INTERACTIVE`，保持现有帧率让路规则。
- 自动对焦多步命令：每个不可拆步骤为 `INTERACTIVE`，步骤之间允许取帧或更高优先级操作。
- 拍照、开始/停止录像、参数写入、旋转和显示模式：`INTERACTIVE`。
- 曝光尺、剩余录像时长等低频读取：使用 `IDLE` 或专门的低优先级参数请求；拍摄、对焦和录像关键步骤自动让路。

### 大图预览

- 当前大图请求和当前 EXIF：`PREVIEW`。
- 预览打开时暂停整卡照片信息读取和远程缩略图。
- 退出预览时取消未完成的预览请求，已完成的本地结果保留。

### 传输

- 原片下载的每个 PTP 分块：`TRANSFER`。
- 当前分块不可抢占；分块之间允许 P0/P1 请求进入。
- 完整下载活动继续通过独立状态禁止心跳和低优先级目录探测插入。
- 传输速度只统计实际传输事务，不包含评级、预览和本地生成。

### 缩略图

- 内存/磁盘命中：完全绕过调度器。
- 首屏/可见区域远程缩略图：`VISIBLE_THUMBNAIL`；评级扫描开始后，新远程缩略图请求排在 `RATING` 后。
- 旧照片后台预加载：`BACKGROUND_THUMBNAIL`。
- 每张缩略图请求独立占用一个事务；不能把整批缩略图包进一个长期锁。
- 评级开始前，最近三个拍摄日中仍需访问相机的缩略图完成、失败或确认无图；缓存命中不参与等待。

### 照片列表信息

- 整卡 `ObjectInfo` / 目录批次：低于可见缩略图，高于空闲检查；每批内部保持现有协议事务边界。
- 进入监看或大图时暂停新批次，当前已开始的单条请求自然收尾。
- 连接级列表状态和调度器事务状态分离，不能用页面是否可见直接持有相机锁。

### 星级读取

评级开关关闭时，不创建评级队列，不进入调度器。

开关开启后：

1. 列表按新到旧确定最近三个实际拍摄日。
2. 最近三个拍摄日的远程缩略图阶段完成后启动评级队列。
3. JPG/JPEG、NEF/NRW：读取受限文件头，每个文件头请求是一个 `RATING` 事务。
4. MOV/MP4：使用已经验证的 `moov/udta/NCDT/NCTG` 定位器，只读取定位所需区域；每个区域读取是一个 `RATING` 事务。
5. AP/USB 对象属性读取：每个对象属性命令是一个 `RATING` 事务。
6. JPG 与唯一同名 NEF 的评级投影保持现有规则，不重复读取相同来源。
7. 每个事务完成后立即释放通道；评级扫描不得持有全局优先预约。
8. 监看、拍摄、对焦、大图和传输请求到达时，评级在下一个事务边界让路。
9. 连接断开或页面任务取消时，清理剩余等待项；不自动从头重扫。

评级结果只保存在当前连接的轻量内存代次中。未知、失败、不支持和确认 0 星必须继续区分，未知不能当作 0 星。

## 调度器 API 约束

建议提供单一入口：

```kotlin
suspend fun <T> withCameraTransaction(
    kind: CameraRequestKind,
    owner: String,
    block: suspend () -> T,
): T
```

约束：

- `block` 内不得再次调用 `withCameraTransaction`。
- 调度器通过快照暴露当前队列、活动类型和活动下载状态；评级与传输继续只记录关键诊断，避免把每条普通请求刷进日志窗。若后续需要耗时诊断，应增加受控统计字段，不在默认路径逐条写日志。
- 取消等待中的请求只移除自己的队列节点。
- 会话关闭会拒绝新业务 ticket 并取消所有尚未入场的等待项；重新连接不会继承旧会话队列。
- 调度器不会自动中断协议数据阶段。需要取消正在执行的数据事务的调用方必须在事务内完成已有 Cancel/排空/关闭；调度器只在事务体返回后释放通道，不能让下一请求提前接管。
- `ioMutex` 不再对业务层公开；迁移完成后删除直接使用路径。
- 旧 API 可暂时作为兼容适配层，但内部必须转发到统一入口，不能保留第二套锁逻辑。

## 原定迁移顺序（本轮已执行，兼容适配层暂留）

1. 为现有 `CameraIoGate` 增加 `RequestKind`、统一事务入口和调度诊断。
2. 先迁移测试覆盖最完整的传输分块、缩略图和监看命令。
3. 迁移大图、EXIF、目录批次和空闲检查。
4. 删除评级的整段优先预约，让照片、视频、对象评级都使用单事务 `RATING`。
5. 删除业务层直接 `ioMutex` 访问。
6. 增加嵌套事务、取消、优先级顺序、断线和传输分块不可抢占测试。
7. 最后再删除旧适配 API，避免一次改动同时改变协议行为和页面状态；本轮先保留旧方法作为转发到统一入口的兼容适配层，确认下游稳定后再单独删除。

## 必须验证的闭环

- 评级开关关闭时，调度器中没有评级请求。
- 评级开启后，最近三个拍摄日完成锚点后才开始；缓存命中不等待。
- 47/52 场景中，最后的 MP4 评级事务能够完成，不出现外层预约和内层请求互等。
- 监看、拍摄、传输分块到达时，评级只在事务边界让路。
- 评级不会改变缩略图列表顺序、首屏出现时间、传输速度统计或照片生成计时。
- 断线、页面离开、切换连接和重复打开筛选窗不会重复建立扫描或遗留队列节点。
- 诊断日志只记录关键统计：队列等待、当前请求类型、单事务耗时、扫描进度、取消/失败原因和最终结果。
