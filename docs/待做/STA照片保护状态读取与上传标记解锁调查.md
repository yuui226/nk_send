# STA 照片保护与星级筛选：证据、探索顺序和实验

> 调查日期：2026-09-21  
> 状态：2026-09-21 复核并调整探索顺序；仅完成代码和资料核对，候选方案均未由本项目真机验证。  
> 代码基线：`android`，HEAD `28bc15c021166468f794aad5a84794d5f2fb4843`。调查时工作区已有其他需求的未提交修改，本文未修改协议或筛选代码。  
> 用户要求：先调查和讨论；重点保留“标记待上传后可能解除读取限制”的线索，供后续实验。

> 范围补充（2026-09-21）：新增“读取相机端星级并筛选照片”需求，研究见第 9 节；与保护状态共用会话实验，但分别验证字段来源。本轮仍不实施功能。

## 1. 问题与结论

用户反馈：STA 模式下筛选不出相机中已保护的照片；AP 和有线模式预计正常，尚需用同一组照片做对照确认。

本文的 STA 指 ZTransfer 当前的“连接到计算机 / PAIRED_COMPUTER”路径，不等于尼康新机型的“连接至智能设备 → Wi-Fi连接（STA mode）”。参见[两种 STA 路径的区别](../docs/技术调研/计算机Wi-Fi客户端与智能设备STA模式.md)。

本地事实与外部报告（证据来源分开看）：

1. 正常 `GetObjectInfo` 路径会读取保护状态，界面也确实按该状态筛选。
2. STA 绕过 `GetObjectInfo` 的直接读取分支没有取得保护状态，构造 `FileInfo` 时沿用 `isProtected = false`。因此这条分支会把“尚未读取”当成“未保护”。
3. 仓库已有 Z30 记录：计算机配对会话的 `GetObjectInfo` 返回 `0x200F`，而直接对象读取可用。这解释了为什么需要该回退路径。
4. Z6 II 的一位开发者报告：标记照片待上传并发送 `AdvancedTransfer (0x9010)` 后，`GetObjectInfo` 不再返回拒绝访问；未选择待上传照片时该命令阻塞。这是外部个例，不是本项目实测或跨机型保证。
5. 尚未找到可直接照搬、已验证解决“尼康计算机 STA 下保护筛选”的完整补丁。上述报告没有验证保护状态，也没有明确写出 AP/STA 菜单路径。

**当前判断：本地确实缺少保护状态补全；相机是否允许补全，可能取决于接口和传输会话状态。不能直接推断为 STA 永远不提供保护状态，也不能宣称已有通用解法。**

### 1.1 推荐探索顺序

排序综合已有证据、实验成本和对相机状态的影响，不是成功率统计。**保护和星级不必等待同一条路径成功。**

| 顺序 | 要做什么 | 排在这里的理由 | 第一轮的结束条件 |
|---|---|---|---|
| 1：星级优先 | 对比机内评级前后的原始 JPG/NEF，找实际变化的评级标签；再验证 STA 局部读取 | 尼康官方说明机内评级可被 NX Studio 查看，评级确实可以传递到软件；无需先破解会话权限，是星级最值得先试的方向。但具体存储位置和读取字节数尚不明确 | 先做同一照片 0 → 3 → 0 的副本对照；找到可靠变化再验证 1–5 星及拒绝状态。只做一轮完整元数据检查，找不到就记录结果，不立即盲扫私有字节 |
| 2：保护的首次协议试验，同时探测星级 | 少量样本读取 `0xDC03`、`0xDC8A`；单对象确认后再研究批量 | 现有属性请求结构可借鉴、验证成本低，适合先快速排除；**当前没有目标尼康 STA 成功的证据，不能称为成功可能性最高** | 取得随机内操作变化的值，或记录明确的不支持/拒绝/错误；不展开全卡重试 |
| 3：保护的主要研究线索 | 对照“仅标记上传”和“标记 + 0x9010”，复测 `GetObjectInfo` | **这是保护问题最有直接外部实测依据的线索**；但机型、配对模式、作用范围和阻塞处理未确认，准备成本及副作用高于只读查询 | 先证明未被标记的对象也恢复读取且保护值正确，再研究持续时间；若仅被标记对象可读，不能算普通全库保护筛选已解决 |
| 4：备用逆向 | 比较 `0x9434` 原始记录随保护/星级变化的差异 | 现有索引接口可读取，但没有证据证明载荷包含所需状态；语义确认成本高 | 可以在前面实验顺手保存载荷；若重复切换后无对应变化，暂不深挖未知位 |

星级第 1 项的依据见[Z30 官方评级说明](https://onlinemanual.nikonimglib.com/z30/en/05-04.html)：它证明 NX Studio 能显示评级，**不证明评级一定在 EXIF、XMP 或固定文件头内**。本表是工程判断；拿到真机证据后应更新排序。

最低成本的起步组合：同一 JPG、同一 NEF 分别做星级前后副本对照；同一次 STA 诊断对少量句柄查询保护/评级属性。无需先做全机型、全星级、双卡和所有上传阶段的矩阵。矩阵用于候选路径有结果后的验证。

## 2. 本地代码证据

以下行号以调查时工作区为准，后续以函数名定位。

| 位置 | 已确认行为 | 对问题的影响 |
|---|---|---|
| `NikonCamera.kt`，`FileInfo`，约 2131 行 | `isProtected: Boolean = false` | 未赋值与明确未保护混在一起 |
| `NikonCamera.kt`，`getObjectInfoInternal`，约 3798–3830 行 | 发送 `0x1008`；读取返回数据偏移 6 的 little-endian u16，非零视为保护 | 正常路径已包含保护信息，无需额外查询 |
| `NikonCamera.kt`，`readStaDirectIndexedObjectInternal`，约 2690 行 | 使用索引、日期、大小与文件名构造 `FileInfo`，未传入保护状态 | STA 索引路径默认为未保护 |
| `NikonCamera.kt`，`readStaDirectObjectHeaderInternal`，约 2874 行；构造对象约 3090 行 | 从文件头等信息构造 `FileInfo`，同样未传入保护状态 | STA 文件头路径也默认为未保护 |
| `FileListScreen.kt`，约 970 行 | `.filter { !filterProtected || it.isProtected }` | 筛选消费的是上游字段；不是这里漏写了 STA 条件 |
| `NikonCamera.kt`，`cacheStaDirectObjectHeader`，约 2732 行 | 用新 `FileInfo` 覆盖 `staDirectFiles[handle]` | 未来补全的保护状态可能被后续文件头读取覆盖，实施时需处理 |

代码入口：

- [NikonCamera.kt](../app/src/main/java/com/ztransfer/protocol/NikonCamera.kt)
- [FileListScreen.kt](../app/src/main/java/com/ztransfer/ui/screen/FileListScreen.kt)

范围限定：这不是“所有 STA 机型必然失败”的证据。能正常走 `GetObjectInfo` 的 STA 会话仍可能取得保护状态；问题明确存在于 `staDirectObjectReadValidated` 对应的直接读取分支。

### 已有可借鉴的属性查询代码

`loadStaDirectOriginalFileNamesInternal` 的代码会按广告能力尝试通过 `GetObjectPropList (0x9805)` 批量读取文件名属性 `0xDC07`；`readStaDirectOriginalFileNameInternal` 使用 `GetObjectPropValue (0x9803)` 逐对象读取，并包含能力判断和诊断信息。

这意味着协议层已有对象属性查询的组织方式可借鉴，**不意味着目标相机已成功支持这些查询，更不意味着保护属性必然开放**。后续应记录真实响应码及数据，而不是只看操作码是否被广告支持。

### 索引与缓存的限制

- `parseNikonObjectsMetadataCaptureDates` 当前只解析 `NK_GET_OBJECTS_METADATA (0x9434)` 中的句柄和日期。
- 当前解析器要求 u32 版本 `100`、u32 数量及严格匹配的 16 字节记录；读取记录偏移 0–3 的句柄、偏移 9–15 的日期时间。偏移 4–7 和偏移 8 未用于此解析。代码注释将偏移 8 记作 `0`，但解析器并不校验它；这不是已确认的完整协议布局。
- 尚未解释的 4 字节只是研究候选，**没有证据证明其中包含保护标记**，不能凭单个样本指定某一位。
- `staDirectFiles` 在连接初始化时清空，读取时也会直接复用会话内缓存。保护可能被用户在相机上改变，不能仅在首次扫描时读取后永久复用。
- 不能假设 JPG/NEF 文件内容中的 EXIF 就代表相机当前的保护状态。本轮没有找到这样的可靠映射。

## 3. 最重要的公开案例：标记上传后解除拒绝访问

来源：[libgphoto2 issue #976 — Nikon Z6ii build in wifi - Access Denied](https://github.com/gphoto/libgphoto2/issues/976)。

作者于 2024-04-24 报告使用 Nikon Z6 II 内置 Wi-Fi 时的行为。截至本次调查，页面仍为 Open，没有看到完整修复方案或关联补丁。

### 作者实际报告了什么

1. `PTP_OC_GetObjectInfo (0x1008)` 返回 `PTP_RC_AccessDenied (0x200F)`。
2. 作者报告标记一张照片待上传并发送 `PTP_OC_NIKON_AdvancedTransfer (0x9010)` 后，不再遇到上述拒绝访问。
3. 作者报告在没有照片被选为待上传时，`0x9010` 阻塞；报告没有给出具体超时、事务日志或阻塞阶段。

这是作者的使用报告，缺少可供本项目复核的原始抓包，并非 ZTransfer 已复现的结果。公开报告描述的是“标记 + 命令”的组合，不能拆解为“只要标记就一定解除”。

### 为什么值得跟进

本项目 Z30 的 `GetObjectInfo → 0x200F` 与该报告的底层症状相同。一个值得验证的推断是：计算机传图会话可能在进入某种传输状态前限制普通对象信息读取。

如果进入该状态后能读取任意对象的标准 `ObjectInfo`，就有机会直接取得其中的保护状态；但这仍是推断。也可能只开放被选中的文件，或只在特定传输阶段开放。

### 公开报告没有回答的问题

- 使用的具体网络菜单、配对身份、固件版本是什么？是否与 ZTransfer 的计算机 STA 一致？
- 单独标记待上传是否有效，还是必须再发送 `0x9010`？
- 命令参数、数据阶段、事件顺序和传输完成流程是什么？
- 解除的是一张被选中的照片，还是同卡、跨卡的全部对象？
- 被解除访问的 `ObjectInfo` 是否正确返回保护状态？切换保护后是否更新？
- 权限在传输完成、取消标记、清空队列、重新连接后是否保留？
- 相机屏幕、拍摄、监看、自动上传和手动下载会受到什么影响？
- Z30、Z f、Z fc 等其他机型是否有相同行为？

**不要把“保护照片”和“标记待上传”当成同一个状态。**实验必须分别控制它们；否则可能把上传选择状态误识别为保护状态。

## 5. 后续实验方案（尚未执行）

### 5.1 准备对照样本与基线

建议先用已有可复现限制的机型，再按结果扩展机型。记录机型、固件、App 版本、完整相机菜单路径、配对身份、网络拓扑及会话初始化命令。

准备至少四张容易区分的照片，最好包含 JPG 和 NEF：

| 样本 | 相机保护 | 标记待上传 | 用途 |
|---|---|---|---|
| A | 是 | 否 | 目标保护照片、未被选择上传 |
| B | 否 | 否 | 普通对照照片 |
| C | 是 | 是 | 同时具有两种状态 |
| D | 否 | 是 | 排除把上传标记误当成保护标记 |

在不同实验阶段再设置对应标记，初始基线应先清楚记录实际队列状态。RAW+JPG 配对是否会一起保护或一起标记，也需要记录；不能假设两个文件状态彼此独立。

先通过相机界面确认状态，并在 AP/USB 下读取同一组照片作基线。句柄跨会话可能变化，应结合卡槽、文件名等重新匹配，不能机械复用旧句柄。

### 5.2 实验 A：直接读取保护属性

目标：验证能否不改变传输状态，直接取得保护信息。

1. 在 STA 中记录 `GetObjectInfo` 的响应，确认本次确实复现限制。
2. 记录操作码广告能力。若支持 `GetObjectPropsSupported (0x9801)` / `GetObjectPropDesc (0x9802)`，按对象格式查询属性列表与描述；这些命令不可用不等于属性值必然不可读。
3. 优先在少量样本上测试 `GetObjectPropValue (0x9803)`；若只有 `GetObjectPropList (0x9805)` 可用，先限制到单个样本查询 `ProtectionStatus (0xDC03)`。确认值正确后才尝试批量，区分“属性不存在”与“批量选择参数不支持”，不直接对全卡逐张失败重试。
4. 相机上对同一照片执行未保护 → 保护 → 未保护，每次重新读取，确认值随实际状态变化。
5. 区分明确不支持、拒绝访问、设备忙、超时、空数据和解析失败；不能统一记成未保护。

若此路可用，可优先考虑它，上传状态实验仍可作为独立协议研究继续。

### 5.3 实验 B：拆解“标记待上传后解除限制”

这是保护问题最有直接外部报告支撑的研究方向，实际试验顺序见第 1.1 节。先核实 `0x9010` 的调用参数和完整事务流程，再做显式诊断实验；目前资料不足以在本文给出可直接执行的命令配方。

| 阶段 | 操作 | 需要观察的结果 |
|---|---|---|
| B0 | 新建干净会话、无待上传照片，只读 `GetObjectInfo` | 建立拒绝访问基线，不发送已知可能阻塞的空队列 `0x9010` |
| B1 | 仅在相机上标记一张照片待上传，不发 `0x9010` | 标记本身是否足以解除；读取被标记和未标记的对象 |
| B2 | 在有待上传照片时按已核实的事务流程发送 `0x9010` | 记录响应、数据、事件和耗时；随后复测相同对象 |
| B3 | 仅在已确认完整传输流程并实际发生传输时，观察完成后的状态 | 读取能力是否保留；上传队列和相机标记如何变化。不能假定 0x9010 一条命令就会完成上传 |
| B4 | 按相机正常流程取消剩余上传标记或清空队列，再复测 | 权限是否随队列消失；与“传输完成”分开记录 |
| B5 | 断开重连，再复测；必要时单独测试相机重启 | 记录读取能力是否保持，并同时记录上传队列是否保留；不能仅凭重连后可读就判为永久解锁 |
| B6 | 重新建立基线，轮换被标记样本，重复上述步骤 | 排除某个对象、保护状态或文件格式造成的偶然结果 |

先用被标记对象、同卡未标记对象验证关键差异，有结果后再扩展双卡。实验期间关闭自动上传，记录所有主动和后台 PTP 请求及事件；否则 B1 期间可能已有其他逻辑启动传输，无法判断是否由“仅标记”触发。解除访问后，要实际校验保护值，而不仅检查响应是否为成功。

只有在前面的协议流程、超时和恢复方式明确后，才考虑单独研究空队列行为。公开报告已经提示阻塞，不需要一开始重现它来证明风险。

实验工具应具有有界超时、明确停止入口和连接恢复能力。命令超时后不要立即向可能仍在执行事务的连接追加命令；应按协议状态完成恢复，必要时重新建立连接。记录停止后列表、预览、监看和正常下载是否恢复。

### 5.4 实验 C：对象索引差分（备用方向）

可在前面实验顺手保存 `0x9434` 载荷，但未知字段语义研究排在后面：

1. 同一照片、同一会话，未保护 → 保护 → 未保护，保留各次原始记录。
2. 另做未标记上传 → 标记上传 → 取消标记对照，避免混淆两种状态。
3. 以句柄匹配记录，比较变化字节；排除其他状态和同时新增文件造成的差异。
4. 在多照片、多格式和不同机型/固件上复核，再讨论是否有稳定字段。

本轮未发现公开的保护位映射。没有重复证据前，不应把未知字节用于正式筛选。

- 命令操作码、参数、事务 ID、响应码、载荷长度、耗时、超时/取消/恢复结果。
- 样本句柄、卡槽/StorageID、格式和可核对的文件标识；保护值来源和原始数值。
- 必要的 `ObjectInfo`、对象属性条目、`0x9434` 样本记录，以及上传过程事件顺序。
- 是否命中缓存；验证读取应能区分真实请求与复用旧数据。
- 相机屏幕是否仍正常、能否拍摄、监看/列表/预览是否继续工作，以及是否意外触发传输。

日志应便于完整复制，避免关键响应被截断。分享时不包含配对密钥、网络密码或无关原始照片数据。

## 7. 后续产品改动的约束

如果实验得到可用结果，再讨论实施，当前不直接修改正式行为：

- 保护状态补全只进入需要兼容的 STA 分支，保留 AP/USB 正常 `ObjectInfo` 读取；星级属于三个模式分别验证的新能力，不受此 STA 限定。
- 不默认切换完整 PC 控制模式；用户已有相机屏幕保持可用的需求。
- 不自动给照片加保护、取消保护或修改上传选择来换取权限。
- 不把 `0x9010` 无条件加入每次列表扫描或刷新；必须明确队列要求、阻塞行为与副作用。
- 区分已保护、未保护、未知/读取失败。未知状态的筛选展示方式需另行讨论，不能假装已全部查询成功。
- 优先批量读取，控制单张回退的次数与耗时，保留逐批加载体验。
- 设计状态刷新和缓存合并，避免后续文件头解析覆盖已取得的保护状态；重连后重新评估能力。
- 拒绝访问可能与阶段有关，不能仅凭一次失败永远禁用；也不能遇到永久不支持还对全卡持续重试。

## 9. 扩展研究：相机端星级读取与筛选

### 9.1 需求与保护状态的异同

用户希望按照相机上已设置的星级筛选照片。当前范围是读取和筛选，不包含在 App 中反向给相机照片评级，也不以 App 本地独立星级替代机内值。

本轮检索 `app/src/main/java`，未发现已实现的相机照片星级读取、`FileInfo` 星级字段或星级筛选链路。因此这是三个连接模式都要研究的新能力，不能因为 AP/USB 的保护筛选正常，就认为其星级已经可用。

| 对比 | 保护状态 | 星级 |
|---|---|---|
| 标准 `ObjectInfo` | 有 `ProtectionStatus` | 没有对应的标准星级字段 |
| 对象属性候选 | `ProtectionStatus (0xDC03)` | 通用 MTP `Rating (0xDC8A)`；尚未确认对应尼康机内星级 |
| 原文件元数据 | 本轮未确认可靠的保护状态映射 | 可检查 IFD/XMP 等评级标签，但需证明与目标机型的机内星级同步 |
| `0x9010` 解除限制的意义 | 若恢复完整 `ObjectInfo`，可能直接读到保护 | 仍需另测星级属性、文件内容或其他接口，不能推断同时解决 |
| 状态表达 | 已保护 / 未保护 / 未知 | 未评级、1–5 星、拒绝/待删除候选、未知；实际编码待验证 |

`ObjectInfo` 结构和 `0xDC8A` 定义可参见 [libgphoto2 ptp.h](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.h)。此处仅证明字段定义，不证明尼康特定模式支持。

### 9.2 已确认资料与候选读取途径

1. **Z30 官方说明了评级及软件可见性。**[尼康 Z30 官方评级说明](https://onlinemanual.nikonimglib.com/z30/en/05-04.html)列出 0–5 星及待删除候选，并说明 NX Studio 能显示评级。不能把待删除候选当作未评级，也不能把读取失败默认当作 0 星。
2. **对象属性是低成本候选，不是已确认的尼康星级接口。**与保护状态共用 `GetObjectPropList / GetObjectPropValue` 通道，但查询 `Rating (0xDC8A)`。若支持属性枚举和描述读取，记录属性是否存在、类型和有效范围；没有描述时保留原始值，用相机操作对照。不同协议/元数据评级可能使用不同数值尺度，不能凭名字套用 0–5 或百分比转换。
3. **星级优先验证文件元数据途径。**[ExifTool EXIF 标签表](https://exiftool.org/TagNames/EXIF.html)列出 IFD0 `Rating (0x4746)`、`RatingPercent (0x4749)`；[Adobe XMP 定义](https://developer.adobe.com/xmp/docs/xmp-namespaces/xmp/)规定 `xmp:Rating` 的未评级、评级和拒绝语义。这些是通用候选位置，尚未证明目标尼康机型会写入其中任何一个。
4. **先用原文件确认，再考虑局部读取。**对同一张照片在机内改变星级后，分别取原文件副本作只读解析。优先在相机完成写入、正常关机后用读卡器逐字节复制，避免导入软件添加评级或侧车文件污染证据；USB 原文件传输也可对照，但不以 NX Studio 的显示结果替代字节证据。确认字段变化后，再单独测试在线落盘时机及局部读取范围。内嵌预览 JPEG、缩略图与原文件元数据可能不同，不能从预览中缺少标签推断原文件没有星级。

   当前 `parseStaDirectExif` 只返回日期和缩略图；JPG 使用的 `jpegExifEnvelope` 只保留 EXIF APP1 段，不保留单独的 XMP APP1 段。因此“已在读文件头”不等于“已有解析器能读所有星级标签”。若目标字段在 XMP 或当前读取范围之外，需要增加对应的有界读取/解析；先量出成本再决定是否采用。
5. **未知索引字段仅作备用。**`0x9434` 可加入星级差分，但不得假设未知 4 字节包含星级，更不能将上传标记变化误当成评级变化。

检查本地样本时，可使用只读命令 `exiftool -G1 -a -s -n -Rating -RatingPercent sample.nef`（JPG 同理）。未输出只表示这些标签未被识别，不足以断言相机没有在其他位置保存星级。必要时进一步检查完整元数据；不通过桌面软件重新保存样本，以免把软件写入值误判为相机写入值。

### 9.3 实验样本与步骤

下面是候选路径有效后的完整验证清单，不是第一轮必须全部完成的前置条件。先按第 1.1 节做 0 → 3 → 0 和少量属性读取；有结果后再分别验证 AP/USB/STA：

1. 准备可核对的未评级、1、2、3、4、5 星及待删除候选照片，分别包含 JPG、NEF。先用同一照片进行 `0 → 1 → 2 → 3 → 4 → 5 → 0`，再测试待删除候选，建立真实值映射与刷新行为。
2. 先在 AP/USB 测试属性读取和原文件元数据，再在 STA 的 B0、B1、B2、B3、B4、B5 阶段读取同样信息。分别记录“保护恢复可读”和“星级恢复可读”，不要合并成一个成功标记。
3. 使用相同星级、不同保护/上传状态的样本，以及相同保护/上传状态、不同星级的样本，排除字段混淆；不必一开始穷举全部组合。
4. **评级操作有相机侧限制。**[Z30 官方评级说明](https://onlinemanual.nikonimglib.com/z30/en/05-04.html)说明已保护照片不能评级。因此先设置星级，再保护，并确认星级是否保留。若某机型在待上传状态下也禁止评级，记录真实行为并调整操作顺序，不把菜单不可操作误判为协议读取失败。
5. 对 RAW+JPG、双卡备份分别确认：机内一次评级影响哪些文件、两个文件的返回值是否一致。不能直接按同名文件复制星级；合并展示时若发生冲突，需要保留来源再讨论规则。
6. 测试在线更改后刷新、离线更改后重连、取原文件与局部读取是否一致，记录属性更新和落盘时机。读取时跳过旧文件头/属性缓存，避免旧值掩盖真实变化。
7. 测量请求数、额外字节数和首屏/逐批加载耗时。原文件下载只用于实验比对，不作为正式列表筛选的默认实现；若无法低成本读取，需另行讨论按需查询或能力限制。

### 9.4 日志、缓存与产品语义

- 日志增加 `ratingSource`、原始属性码/标签、数据类型、原始值、转换后状态、读取耗时/字节数和缓存命中；同时记录机内屏幕实际值、保护与上传标记。
- 模型需区别“确认未评级”和“未知/不支持/暂时读取失败”，保留拒绝状态的独立含义；原始值不认识时不要随意截断到 0–5。
- 星级和保护状态都可能在文件名、句柄、大小不变时改变。不能仅靠已有文件缓存身份判断值永远有效；文件头、对象属性和界面筛选结果都需要刷新策略。
- 保护筛选与星级筛选应为独立条件；若同时开启，建议采用交集，例如“已保护且至少 3 星”。这是设计建议，尚未确定交互。
- 星级筛选可讨论“指定星级 / 至少 N 星 / 已评级 / 未评级”，本轮先验证数据来源，不提前固定控件样式。待删除候选仅是评级状态，不执行删除。
- 当前用户需求为照片；视频评级和桌面软件写入后再回传的文件应作为后续独立兼容范围，不能自动宣称支持。

### 9.5 本轮结论与下一步
