# 监看拍照后 FHD 回看

状态：待讨论、待实验，暂不实施。用户尚未决定是否加入此功能。

## 需求与目的

允许用户在监看界面拍照后查看所拍照片的 FHD 预览，放大检查焦点和细节，再回到实时监看。加载 FHD 时允许监看暂停。

本文件记录讨论结果，不代表以下交互已经全部确定；本次只整理文档，不修改功能代码。

## 建议的第一版范围

1. 拍照成功后显示小型回看入口，不自动弹出照片，也不立即请求 FHD，避免打断继续拍摄。
2. 点击入口后暂停监看取帧，保留最后一帧作为加载背景，并明确显示加载状态，避免被误认成实时画面。
3. 在监看区域原地显示刚拍照片，支持双指缩放、拖动及返回监看。
4. 返回后恢复实时监看，保留原来的参数、工具偏好和布局。
5. 连续拍摄时更新最新照片入口。第一版仅回看最新一张，不预取相邻照片，不附带翻页、传输或裁切功能。

以上为建议，不是已确认的最终交互。入口位置、图标和切换动画留待实施前设计。

## 已检查的代码基础

- `app/src/main/java/com/ztransfer/ui/screen/RemoteScreen.kt`：`shoot()` 会等待新对象事件，取得文件 handle，目前仅作为拍摄成功确认，不加载照片。现有监看会话具有断流恢复机制。
- `app/src/main/java/com/ztransfer/viewmodel/CameraViewModel.kt`：`setRemoteActive()` 在监看期间暂停文件扫描，退出后补查；因此不能假定照片列表中的最后一张就是刚拍的照片。
- 同文件的 `loadFhdPreview()` / `loadFhdBitmap()` 已有相机预览获取、解码和尺寸限制流程，可评估复用。当前 STA 路径不以完整原图下载替代 FHD。

这些是代码层面的依据，不代表已验证相机在 Live View 活跃期间允许获取 FHD。后续实施时需重新核对当前代码。

## 核心技术问题

### 监看暂停与恢复

需要区分两种操作：

- 暂停 App 请求监看帧，不主动结束相机 Live View。
- 向相机发送 EndLiveView，取图后重新启动 Live View。

优先实验前者，避免不必要的会话切换。是否必须采用后者，要由机型及 AP／STA／USB 实测决定，不能预先认定所有相机行为一致。

必须有明确的回看状态，防止现有自动恢复任务把主动暂停当成断流，并在 FHD 加载期间重新抢占通道。事件消费保持单一入口；暂停非必要取帧、分析和属性轮询时，不能误停连接或录像状态所需的事件处理。

### 确认照片身份与方向

- 依据拍摄事件定位照片，不按列表位置猜测。
- RAW＋JPG、双卡写入或连续拍摄可能产生多个对象，需确定配对和“最新一张”的选择规则，优先考虑可用 JPG 预览。
- 对象生成事件不等于该对象立即可读取，需处理相机忙与短暂不可读，重试必须有界。
- 仅 RAW 时使用现有相机预览能力；不可用则提示，不回退为下载完整 RAW。
- 正确处理横拍、竖拍和 EXIF 方向，不能直接沿用当前长按预览的手动旋转策略而不检查。
- 相机实体快门拍摄是否也更新入口，尚未确定。

## 场景处理建议

| 场景 | 建议处理 |
| --- | --- |
| 用户继续拍摄 | 不自动打开回看、不后台预取 FHD；更新最新照片标识 |
| 加载慢或失败 | 可退出，失败有简短提示并恢复监看；禁止永久冻结 |
| 加载中退出 | 废弃迟到结果；协议事务需按既有取消与收尾规则结束后再安全恢复 |
| 端侧录制中 | 第一版不允许进入回看，避免录制冻结或中断；不静默停止录制 |
| 相机录像中 | 第一版不提供照片回看，避免影响录像控制 |
| 断线、退后台、模式切换 | 取消当前回看工作，检查连接和页面状态后决定是否恢复；旧结果不能覆盖新会话 |
| LUT、伪色等监看效果 | 回看照片不套监看效果；隐藏不适用于静态照片的水平仪、电平等实时信息，不修改用户工具偏好 |
| 自动传输及文件扫描 | 不因回看意外恢复全列表扫描或触发重复入队；核对退出监看后的新增文件补查 |
| 内存与性能 | 仅持有单张 FHD，不解码本地原图、不预取邻图；退出释放回看持有的资源，避免重复分析 |
