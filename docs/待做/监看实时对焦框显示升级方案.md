# 监看实时对焦框显示升级方案

更新：2026-10-01。状态：已扩展多框显示并加入首次更新默认开启，协议覆盖范围待实机验证。
调研代码基线：617082c3。2026-10-01 已按用户指示实施首版，见第 11 节。

## 1. 结论与范围

可以在现有架构上升级：从已经获取的监看帧头读取相机报告的当前选中对焦框，与同一帧画面一起显示，解除“必须先在 App 点按、半按或开启追踪才能出现”的限制。正常路径无需增加相机请求、图像解码或图像识别。

但目前不能承诺所有机型、固件、连接方式以及照片／录像模式都与机内显示完全一致。已有证据支持 Z 30 增强监看帧中的选中框；录像裁切坐标、不同 AF 模式、眼部／主体类别及其他机型仍需验证。第一版应做到：有可靠数据就准确显示，没有可靠数据就不伪造。

必须区分三个概念：

| 概念 | 本次处理 |
|---|---|
| 相机当前选中区域／目标的位置与大小 | 核心功能，持续同步相机报告的选中框 |
| 当前是否合焦 | 独立状态；只有含义确认且新鲜的状态才改变颜色 |
| 所有人脸、眼睛、动物等候选识别框 | 第一版不实现；不能把未选中的记录直接当成识别结果 |

“实时”是跟随收到并显示的监看帧，受相机输出频率和传输延迟约束，不意味着与机身屏幕零延迟同步。显示对焦框本身不驱动镜头，不启动追踪，也不修改相机控制模式。

## 2. 当前实现为何不满足需求

核对位置：

- `app/src/main/java/com/ztransfer/protocol/LiveViewMetadata.kt`：帧头校验、合焦状态、选中框解析。
- `app/src/main/java/com/ztransfer/protocol/RemoteLab.kt`：增强／普通监看取帧及回退。
- `app/src/main/java/com/ztransfer/ui/screen/RemoteScreen.kt`：取帧解码、触控对焦反馈、框的显示与坐标转换。
- `app/src/test/java/com/ztransfer/protocol/LiveViewMetadataTest.kt`：现有解析单测。
- `docs/技术调研/Nikon PTP操作码清单.md`：既有 Z 30 操作时序与坐标实测记录。

现状：

1. 已解析 `0x9428` 增强监看帧的部分 AF 数据，普通 `0x9203` 帧没有同等解析。现有解析接受特定版本的 512／1024 字节头，但接受格式不等于已验证所有机型。
2. 画面与元数据已通过同一个 `LiveViewPacket`、`RemoteLiveFrame` 传递；取帧通道为 conflated，不积攒旧帧。这条路径适合继续复用。
3. 真实框显示依赖 `confirmedFocusMarker`。普通点按成功后仅显示约 3 秒，追踪另有逻辑；刚进入监看或直接移动机内对焦点，未必产生这个 App 标记。
4. 普通成功标记还要求帧头为 `FOCUSED`，因此“相机选中了哪里”和“已经合焦”被绑定了。
5. 追踪框存在无期限沿用最后有效矩形的风险；缺帧或目标丢失后可能留下旧框。
6. 现有框使用最小显示尺寸和边缘位置钳制，适合点击反馈，却不适合忠实展示很小的眼部框或边缘框。
7. 照片与录像共用解析，但没有充分证明所有录像画幅、裁切和录制状态下坐标都一致。

现有测试主要使用人工构造的数据，能证明解析逻辑符合当前假设，不能替代跨模式实机证据。旧验证清单关于红框、单框限制等文字也不宜直接当成当前实现，应随实现更新。

## 3. 外部调查：哪些结论可信

### 官方功能与交互

尼康 NX Tether 的 Live View 提供“显示对焦点”，支持在画面中移动焦点及启动／结束主体追踪。这说明远程显示当前焦点是实际存在的产品能力，但其支持机型与协议不能直接等同于本 App。[NX Tether 官方说明](https://nikonimglib.com/nx_tether/onlinehelp/en/03_liveview_window_15.html)

Z 30 官方手册区分 AF-S、AF-C 与录像 AF-F，识别目标、选中目标和合焦颜色也有不同语义。因此不能简单规定“有框就是绿色／已经锁焦”。[Z 30 对焦说明](https://onlinemanual.nikonimglib.com/z30/en/05-01.html)

尼康 SDK 的 2020-09-29 更新明确指出，Z 50 从固件 2.00 升至 2.01 时 LiveViewObject 数据集发生变化。应按已验证的帧结构识别能力，不以“都是尼康”作为字段通用的证据。[尼康 SDK 信息](https://sdk.nikonimaging.com/information/en/)

### 开源实现的可借鉴部分

DslrDashboard 的 `PtpLiveViewObject` 按产品型号处理不同头部布局，区分完整画面、显示区域、显示中心及 AF 框，并通过显示区域换算框坐标。这支持“读取元数据并映射到画面”的路线，也提醒我们裁切显示时不能只除以完整图像宽高。该文件针对较早 DSLR，不能照搬其偏移到 Z 系列增强帧。[源码](https://github.com/deas/dslrdashboard/blob/master/DslrDashboard/src/com/dslr/dashboard/PtpLiveViewObject.java)

已找到直接解析 Z 系列增强帧的公开实现（见第 10 节），但未找到足以证明所有 Z 系列照片／录像模式统一框语义的完整验证。本次不引入开源库、不复制整套旧解析器，也不以计算机视觉检测框冒充相机焦点。

## 4. 建议的显示与操作

### 核心呈现

- 自动展示相机当前报告的选中框，不要求用户先点屏幕。
- 首版只画选中框，不同时铺满候选框；不根据 AF 区域名称猜测它是眼睛或人脸。
- 默认细白色四角框，配轻薄深色衬线以适应明暗画面；无填充遮罩。建议主线约 1–1.5dp，作为设计起点。
- 只有已验证的当前合焦状态才显示绿色。未知或过期状态回到中性样式；AF-C 不用绿色表达“焦点已锁定”。
- 红色短暂失败反馈继续属于用户主动对焦的反馈，不因某帧“不合焦”便持续闪红。
- 几何尺寸尊重相机数据，不为了容易看清而放大真实区域或推离画面边缘。小框缩短角线；只裁剪超出可见画面的部分。
- 框随当前帧直接移动，不给每帧位置套弹簧或缓动，以免追踪拖尾。仅显示／隐藏可用短淡入淡出；新目标出现不重复缩放弹出。

### 开关建议（待产品确认）

建议提供独立的“对焦框”小工具，默认开启，复用现有工具显隐、排序和持久化体系。它控制真实框显示，不代替“对焦区域”选择菜单。隐藏工具按现有规则关闭显示，但不关闭相机 AF；点按对焦仍保留必要的短暂操作反馈。

照片／录像的工具配置遵循现有两套规则。没有可用数据时不画居中假框，也不持续弹提示。不支持不等于未合焦，不能显示失败红框。

规划暂按独立工具入口编写，尚未作为用户确认的交互要求。开关偏好与“当前有无有效框”分开：临时没有目标不能自动关闭用户开关，重新收到可靠数据应自动恢复显示。DISP 切档只改变信息层，不额外控制此工具，避免两个开关共同决定显隐。

### 与已有反馈的关系

显示优先级应明确，不能让整个 AF 操作期间的固定触摸框盖住真实追踪框：

1. “对焦框”开启且当前帧有可靠矩形时，位置始终采用该矩形，包括半按保持和追踪期间。点按可以有一次短暂触摸反馈，但不能保留第二个常驻框。
2. 没有可靠矩形或用户关闭真实框时，才沿用已有的短暂触摸／半按反馈；这种反馈表示操作请求位置，不宣称是相机回报位置。
3. 命令成功不能把正在显示的任意矩形直接染绿；帧到达时间晚于命令也不能单独证明关联。合焦颜色以已验证的帧内状态为准，命令失败沿用已有轻量提示。
4. 不等待“新框恰好等于触摸坐标”才恢复显示，因为追踪目标会移动。触摸反馈结束后直接回到当前帧的数据，不建立复杂的请求与框匹配机制。

框绘制在图像效果之上，与图像共用缩放、拖动、旋转、反挤压变换，不参与 LUT／伪色计算，不写入照片和现有端侧录制画面。

## 5. 数据与状态：保持简单但闭环

### 解析与能力边界

复用现有增强帧解析，仅增加一个轻量的对焦观察结果：框、合焦状态、该项是否有效。会话及时间沿用帧自身信息，不再建立独立轮询通道。

现有布局中的 `+42` 状态、`+44/+45` 数量／选中索引、`+48` 起每条 8 字节矩形，属于当前代码所采用的布局。实施前要确认：

- 实际 AF 表的边界与容量。当前按整个头长推算容量，理论上可能读入音频／姿态等区域；不能直接沿用为新增能力保证。
- 索引、矩形大小、坐标范围、字节序、头版本、JPEG 边界分别检查。
- 未知合焦状态只影响合焦解释，不应连带丢弃音频、姿态等已确认的独立字段。
- 结构无效、有效但无目标、旧协议无此数据应区分，不能全部用同一个 null 决定是否保留旧框。
- 1024 字节头或其他机型只有经过结构验证才启用对应解释；保留现有普通取帧回退，不为对焦框强制改取帧模式或进入完整 PC 控制。

不引入庞大的型号规则库：优先复用已确认的结构，只在实际证据显示不同布局时增加对应解析分支。

### 最小状态规则

| 输入／事件 | 处理 |
|---|---|
| 有效框及状态 | 与同一张已显示 JPEG 更新几何与样式 |
| 有效结构明确表示没有选中目标 | 清除旧框，不能长期保留 |
| 新画面有效但对焦字段损坏／缺失 | 不把上一帧矩形叠上新画面；隐藏真实框，下次有效时恢复 |
| 超时或持续不支持 | 隐藏真实框，保留既有点击操作能力 |
| 切换照片／录像、AF 区域、重启监看、断线或换相机 | 清空旧观察状态，等待新帧；不跨会话复用 |
| 框显示开关关闭 | 立即结束真实框显示并清除保留状态 |

第一版取消旧框跨帧保留，避免为减少闪烁而引入位置误导和额外状态机。字段无效、明确无目标、切换模式时直接停止绘制真实框，不给过期位置添加拖尾淡出。用户主动开关可以做短显隐动画；协议失效处理优先保证真实性。

若整张画面没有更新，应与元数据缺失区分：同一冻结帧中的位置仍与画面对应，但不能无限显示成功状态。沿用接收时间和现有监看生命周期；建议超过 500ms 未收到可显示新帧时隐藏框，这是待实机调整的界面参数，不是协议常量。使用单个存续的截止检查任务，到期检查最新帧时间后续期；不能每帧新建／取消任务，也不另加高频轮询。退后台、断线、退出监看立即取消任务并清空状态。

切换模式或区域时需同时防止旧的在途解码帧重新点亮旧框：利用现有会话／变更代次标记丢弃过期结果。物理拨杆状态若晚于帧到达才被发现，发现后清理并等待新帧；未收到相机标识时无法保证识别到切换的精确瞬间。

### 坐标与录像

已有追踪命令与普通 AF 移动命令使用的坐标网格不同，命令侧不因本次显示升级而更改。

显示侧先确定“完整坐标中的哪一块对应当前 JPEG”，再映射到实际图像矩形，最后共用画面变换。如果证实当前模式为完整坐标等比缩放，可沿用归一化；若存在录像裁切／电子防抖／机内放大，需要确认显示区域数据后换算，不凭比例猜偏移。

坐标换算约定：若已证实可见区域为完整坐标中的 `(left, top, width, height)`，则框中心归一化为 `((cx-left)/width, (cy-top)/height)`，框尺寸为 `(fw/width, fh/height)`。然后映射到实际 JPEG 展示矩形，最后应用现有画面变换。仅做可见区域相交裁剪，不平移框使它留在屏幕内；完全在可见区域外则不显示。还需确认传输 JPEG 自身是否含黑边，不能把容器尺寸当成有效影像尺寸。

这里的可见区域必须来自已确认字段或该模式实测映射，不新增猜测字段。相机方向与手机布局方向分开处理，避免重复旋转；画面手势变换后线宽也要检查，不应随高倍缩放变成粗线。覆盖层不得新增触摸拦截。

App 手势放大和机内放大是两件事：前者已知且共用变换，后者可能改变相机输出的可见区域，必须独立验证。未验证裁切映射的模式先不承诺准确显示。

## 6. 拍照、录像与连接方式

| 场景 | 目标与验证重点 |
|---|---|
| 拍照 AF-S | 移动选择框、半按、成功、失败、松手；不靠 App 点击才能出现 |
| 拍照 AF-C／AF-A（若支持） | 连续移动框及状态；不能把一次成功永久保存成锁定 |
| 微点／单点／宽区域 | 矩形位置与尺寸是否就是机内对应选择区域 |
| 自动区域、人／动物识别 | 选中目标是否变化、眼与脸切换是否有可靠尺寸与索引依据 |
| 主体追踪 | 开始、跟随、目标离开、结束、重新选中，无旧框残留 |
| 录像待机与录制中 | 分别确认帧头、裁切及状态；录制后不能仍用拍照坐标假设 |
| 录像 AF-F／其他可选 AF | 以机型实际支持项验证，不强设不存在的模式 |
| MF | 只有相机明确报告的可解释区域才显示；不模拟对焦峰值或合焦确认 |
| AP／STA／USB | 共用解析和绘制；分别确认实际收到的数据与回退行为，不额外探测写入能力 |

还要区分“字段结构有效”和“语义已验证”：只有在未点按的普通监看中也持续回报当前选择，才算满足本次需求。如果某模式只在启动追踪后才回报框，该模式不能算作持续对焦点支持，更不能偷偷启动追踪来补足。

照片与录像必须在同一实现中支持，但支持程度由真实返回数据决定。无法确认的眼部／多主体标记列为后续能力，不能因首版只显示选中框便宣称“完整复刻机内所有框”。

## 7. 性能约束

- 不新增 GetDeviceProp 等高频请求，不发送 AF／追踪指令来让框出现。
- 只读取现有帧头固定数量字段，首版只输出选中矩形，不复制 JPEG、不二次解码、不创建 Bitmap。
- 保留 conflated 取帧及画面／元数据配对，避免独立线程拿最新框覆盖旧画面。
- 用独立轻量 Canvas 绘制，尽量让坐标读取与刷新局限于绘制层，不让整页按钮跟着帧率重组。
- 不为平滑框开第二个高频时钟；坐标更新随画面，只有显隐过渡需要短动画。
- 无数据不反复探测；正式运行不逐帧打印日志，不保存全部帧头。
- 性能结论需在相同相机、同样工具开关下比较取帧／解码／绘制耗时，不能把网络抖动当成新增框开销。目标是无可感知额外掉帧，调研阶段不编造量化保证。

## 8. 一次性验证设计

准备一个覆盖全部步骤的诊断入口，读取现有帧，不再为每个猜测反复打包。用户主动启动后，只收集有上限的帧头摘要和少量有代表性的原始头部；不存 JPEG。报告包含模式、实际操作码、头版本／长度、坐标范围、框数量／索引／矩形、状态及时间。采样限频，异常前后样本使用有界环形缓存。

一次会话完成：中心和四角移动、半按成功／失败、人物移动／出画、结束追踪、切录像待机／录制／停止、相机不同裁切设置。每步标记时间，必要时同时拍摄机内屏幕作为对照。报告中“字段含义推测”与“已对照确认”分开记录。

诊断预算建议：每次最长 60 秒、摘要最多每秒 5 条、原始头部最多 32 份；自动停止并生成可复制报告。保存型号、固件、连接模式和 AF 配置供对照，配置优先取已有状态；缺失则人工标注，不在取帧链路追加读取。预算仅为诊断设计起点。

先验证 Z 30，再根据可获得设备扩展其他机型。用户本次无需连接相机；此节是后续实施验收安排。

验收必须覆盖：

1. 无 App 对焦操作也能看到并跟随相机真实选中框；画面四角无固定偏移。
2. 照片与录像、待机与实际录制均对照机内画面；没有数据时明确降级。
3. 手机横竖屏、反向旋转、反挤压、手势放大和拖动后仍与内容对应。
4. 多框选中索引变化、目标丢失、坏帧和断线不会留下旧绿框。
5. 点按对焦、半按、追踪、已有失败气泡及端侧录制行为无回归。
6. 不增加相机请求数，不积压帧，不改变机身屏幕显示状态。

针对性自动测试覆盖：未知状态不破坏音频／姿态解析；数量为零与坏索引区分；记录不能越过 AF 区域；同帧匹配；在途旧帧隔离；新画面字段缺失不复用旧框；冻结帧到期隐藏及退出后的任务清理；坐标裁切、旋转、反挤压与缩放变换。测试使用固定小样本和纯函数，不用整套模拟器反复验证协议。

发布前记录一张简短的能力表（机型／固件／连接／照片或录像／AF 区域／几何／状态颜色）。已确认几何但未确认合焦状态的组合允许只用中性框；几何未确认的组合不宣称支持。首版多候选不等于多选中框，如果某模式不存在可靠选中索引，不能随意取第一个。此类模式需单列未覆盖范围。

## 10. 追加调查：公开实现与当前把握（2026-10-01）

本轮进一步读取了开源源码，而非仅依据项目介绍。下列“把握”是工程判断，不是统计成功率或支持率。

### A. Z6/Z7 开发者的实际成功反馈

Nikon SDK C# Wrapper 的公开讨论中，Vadim K.Riez 于 2022-03-26 明确反馈：已通过监看帧头解析取得 AF 框坐标，并能改变位置，放大也可用。后续讨论记录了取帧异常的处理与成功反馈。同帖还讨论 Z9 的 1024 字节头。

参考：[开发者原始讨论](https://sourceforge.net/p/nikoncswrapper/discussion/general/thread/ad495d06ad/)。

意义：Z 系列真实框坐标可从监看头获取已有实际案例，不是只在老单反上成立。限制：这是桌面 SDK 路线；帖子中的字节编号不能直接当作我们 PTP payload 的偏移，也未证明所有录像模式、传输方式与眼部框均可用。其 SDK 等待策略不应搬进我们的取帧循环。

### B. darkgrade：直接的增强帧字段参考

核对提交：`4096621cf921d5391a394bcdf5289788f3fbd47d`。

- [增强帧解析源码](https://github.com/darkgrade/darkgrade/blob/4096621cf921d5391a394bcdf5289788f3fbd47d/packages/link/src/ptp/datasets/vendors/nikon/nikon-live-view-dataset.ts)
- [调用 0x9428 的实现](https://github.com/darkgrade/darkgrade/blob/4096621cf921d5391a394bcdf5289788f3fbd47d/packages/link/src/camera/nikon-camera.ts)
- [现有测试](https://github.com/darkgrade/darkgrade/blob/4096621cf921d5391a394bcdf5289788f3fbd47d/packages/link/tests/nikon-live-view-dataset.test.ts)

该实现采用大端解析，前部布局与我们现有字段有较强一致性，以下新增解释可作为验证候选：

| 偏移 | 对方解释 | 对本项目的价值 |
|---|---|---|
| +20/+22 | 显示区域宽高 | 验证录像／机内放大后可见范围 |
| +24/+26 | 显示区域中心 | 验证裁切偏移，避免假定居中 |
| +28/+30 | 监看图像宽高 | 与我们作为命令 AF 网格的用途区分；不能凭命名改变现有命令换算 |
| +40/+41 | AF 驱动可用性／驱动状态 | 区分显示区域与驱动镜头，待实测 |
| +42 | 合焦判断 0/1/2 | 与当前解释一致，但仍不等于物理清晰度保证 |
| +43/+46 | AF 模式状态／追踪状态 | 作为区域和追踪语义的验证线索 |

这些是第三方源码解释，不是已取得官方协议原文的确认。不能据此直接开启颜色或追踪类别显示。

尤其需要保留警惕：对方单独读取首个矩形，把余下区域留作原始数据；对数量的注释写 96 个区域，但 760 字节只够 95 条 8 字节记录。其测试仅验证 512 字节头后的 JPEG 分离，未证明 AF 索引与多框含义；解析后部还按扩展头读取，因此不能直接移植为我们的 512 字节解析器。

对方案的直接修正：诊断增加 +20～+30、+40～+47 与少量原始框记录；优先验证“首个框是否独立主框／索引是否涵盖首框”。在此确认前，`+48 + index*8` 仅是本项目当前实现假设，不能推广为所有模式通则。

### C. digiCamControl：成熟的帧头显示路线，也有不宜照搬的简化

核对提交：`9269e7851e5130f7d2278cc9942eccde0fd5e593`。

[基础解析](https://github.com/dukus/digiCamControl/blob/9269e7851e5130f7d2278cc9942eccde0fd5e593/CameraControl.Devices/Nikon/NikonBase.cs)与[D500 系列解析](https://github.com/dukus/digiCamControl/blob/9269e7851e5130f7d2278cc9942eccde0fd5e593/CameraControl.Devices/Nikon/NikonD500Base.cs)读取焦点坐标、尺寸和录像状态；[Z 系列类](https://github.com/dukus/digiCamControl/blob/9269e7851e5130f7d2278cc9942eccde0fd5e593/CameraControl.Devices/Nikon/NikonZ.cs)继承 D500 路线。项目也提供[显示焦点矩形功能](https://digicamcontrol.com/doc/userguide/interface/liveview)。

价值：普通 `0x9203` 也可能包含可用 AF 信息，“本项目尚未解析”不应写成“协议没有”。未来可按证据增加普通帧解析，首版仍不扩大范围。

限制：这些偏移不同于我们的增强帧。部分状态判断简化为“不等于 1 就算合焦”，不适合我们区分无信息与成功；没有找到足以验证 Z30 录像裁切、眼部及多选中框的完整测试证据。

### D. 其他线索的权重

- DslrDashboard 的显示区域／中心换算仍是几何处理参考，见第 3 节；针对老机型，不能验证增强帧偏移。
- [Nikon Ekrynox SDK for NINA](https://github.com/Ekrynox/Nikon-Ekrynox-SDK-for-NINA)有实时取景与焦点设置功能，但本次未取得可用于证明当前增强帧多框语义的实现依据，不将项目支持声明作为本需求已解决的证据。
- NX Tether 证明官方存在远程焦点显示功能；SDK、桌面 USB 与本 App AP／STA／USB 的具体运行条件不能互相替代。

### 不确定性现在缩小到哪里

| 问题 | 目前结论 |
|---|---|
| 能否从现有监看数据获得真实框 | 有本地基础、Z 系列成功反馈和公开源码，路线把握高 |
| 能否低开销绘制并跟随画面 | 常规少量字段解析与矢量绘制，把握高；仍需做性能回归 |
| 录像／机内放大如何映射 | 已找到显示区域和中心候选字段，不再完全盲探；待对照确认 |
| 单点、宽区域、自动区域是否始终报告 | 尚缺本项目覆盖模式证据，特别要验证不点按时的回报 |
| 多框索引是否就是当前目标 | 两个实现的数据建模不同，必须确认，不能仅靠数量与范围校验 |
| 颜色是否忠实于机内 AF 状态 | 0/1/2 有交叉参考，但不同模式的表现还需验证；中性框可先成立 |
| AP、STA、USB 是否等价 | 数据解析可共用，但实际返回与权限仍需分别核对 |

### 主观工程把握

- **约 85%**：做成有实用价值的首版，先覆盖 Z30 已验证场景，持续显示真实选中框，并安全处理缺数据。
- **约 70%**：首版同时较好覆盖常用照片与录像模式；主要风险已集中到字段语义和裁切映射，而非绘制或性能。
- **不足 50% 的把握作出完整承诺**：一次覆盖全部尼康机型、所有 AF 区域、人眼／动物、多目标及录像规格，并完全复刻机内显示。当前资料不足以支持这种承诺。

推荐保持原架构，不引入 SDK 或新库；优先核对新找到的显示区域、主框与候选表含义。若录像映射确认、自动区域无需点击也持续回报，第二项把握会明显提高。若某模式根本不输出目标，则公开源码也不能补出不存在的数据，应明确列为限制。


## 11. 首版实现与实机操作（2026-10-01）

已实现：

- 新增默认开启的“对焦框”工具，接入现有排序、隐藏和状态持久化；隐藏关闭显示，不写相机 AF 设置。
- 每个显示帧使用随帧元数据绘制选中框，不依赖先点按或启动追踪；有效相机框优先于固定触摸反馈。
- 显示区域宽高／中心有效时换算可见区域；全零沿用已有完整画面映射，非零异常不猜测。当前按既有索引解释选中记录，多框主框语义仍通过诊断确认。
- 未知合焦判断不连带丢弃音频／姿态；AF 表限制在后续录像／音频区域之前。
- 移除旧框永久缓存；新画面缺字段不沿用旧框；整帧停止更新 500ms 后隐藏真实框。模式／区域切换后不使用变更前已收到的帧。镜头半按、点按与追踪命令流程保持原样。
- 细四角框跟随图像变换；手势放大时补偿线宽，避免粗线遮挡。未增加相机读取或图像解码。
- FPS 隐藏日志入口保留，面板改为对焦诊断。原快门探测／PC 控制开关及旧日志缓冲工具已移除；不读取旧报告。

日志使用步骤：

1. 监看中 1.5 秒内连续点击 FPS 四次，点出现的日志按钮。
2. 点“开始采样”，随后可关闭面板继续操作；采样最多 60 秒，不发送额外相机命令。
3. 移动机内焦点／切对焦区域／切照片与录像／开始停止录像；每步可回到面板点“标记步骤”。
4. 点“停止”后复制报告。重新点“开始采样”会开始新报告，旧内容被替换。

报告包含型号、固件、连接模式、当前照片／录像及 AF 模式文字、头长／版本、完整与可见画幅、合焦字段、框数量、选中索引及选中记录原始宽高与中心。v2 最多每秒检查 5 次，但仅状态或几何发生变化时记一条；删除重复帧、归一化坐标和原始十六进制转储。复制上限 6000 字符，保留首个状态、最近 8 个步骤标记及最新变化。报告单独持久化。

实机反馈：Z30 V1.20 STA 拍照 AF-S 半按时，数量字段 23 与机内显示 23 个黄框一致。目前 UI 仍只绘制单个索引记录，尚未实现全部 23 框，不能视为完整复刻机内显示；颜色也仍需与该模式对照。

自动验证已覆盖元数据、原有对焦事务、姿态及诊断边界；未进行真机验证。当前待确认项仍是多框索引语义、不同录像裁切和不主动点按时的回报范围。第 9 节的实机验收项保留，不因编译／单测通过而标记为实机完成。

### 首版复核

- 对焦框绘制还校验当前照片／录像布局的工具可见性，避免切换布局时隐藏项短暂显示。
- 诊断每条摘要均带当前选中记录的原始宽高与中心，不局限于前四条框记录；异常索引不越界读取。
- 诊断描述和步骤文字有长度限制，验证长名称、8 个步骤和完整采样后报告仍不超过 6000 字符。
- 针对性 35 项单元测试通过，覆盖元数据、诊断、姿态与原有对焦事务；未进行模拟器或真机测试。跨机型与模式语义仍按上文实机清单验收。

### 显示链路诊断补充

用户反馈首个实机包未看到框：此前报告仅证明收包及解析成功，无法证明 Canvas 执行。现增加 UI 实际绘制回调与拦截原因（关闭／隐藏／后台／断线、模式切换旧帧、过期、无框、零尺寸）；只记录状态类别变化，重复绘制不刷日志，报告保留最新 UI 状态。尚未根据现有日志确定不显示的根因，不将这项诊断补充描述为已修复实机不显示。

### Z30 多框反馈后的实现更新（覆盖上文首版单框范围）

用户确认 STA／AF-S 半按时，帧头数量 23 与机内 23 个黄框一致。按本轮需求，当前代码已从仅绘制选中记录改成绘制所有通过校验的框；每条记录独立校验、映射到可见画幅，异常记录跳过，完全重复的矩形去重。选中框字段继续保留给原有调用者，无效选中索引不阻止其他有效框显示。表长度上限保持不变，不能越过音频等字段。

多个有效框采用黄色细四角框，不把全局合焦标志解释为每个区域都合焦。单框保留原有中性／合焦配色。所有框复用一个 Canvas 和同帧图像变换，不新增相机读取、Bitmap 或单框动画。

新增一次性偏好初始化：该更新首次进入监看时开启对焦框，并从照片／录像两套隐藏列表移除该工具；其他工具配置不变。初始化标志与设置一次写入，此后尊重用户关闭／隐藏选择。图标为 AF，避免与反挤压混淆。

日志报告 n=相机记录数、valid=去重后有效可见框数、UI drawn boxes=实际绘制列表数。新增 36 框、坏记录／坏索引隔离、重复框去重测试。多个矩形的位置与机内显示是否逐一一致，仍待新包实机对照，不能仅凭数量一致宣称全模式已验证。
