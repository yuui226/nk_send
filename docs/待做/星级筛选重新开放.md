## 重新开放前新增的核心问题：如何保证星级新鲜且可靠

当前真正未闭环的问题不是“能否读取星级”，而是相机端修改星级后，App 如何知道旧值已经失效：

- 同一次连接中，用户可能在相机上修改一张照片的星级；文件名、句柄和大小都可能不变，不能继续永久复用旧缓存。
- 断开期间用户可能修改已有照片、增加新照片或给新照片评级；下一次连接不能把上次缓存直接当作当前值。
- 缩略图缓存或列表缓存命中时，不能因此跳过必要的星级新鲜度确认。
- JPG/NEF 配对、视频容器解析和 AP/USB 属性读取必须分别标记来源和新鲜度，不能把一个文件的旧值无条件复制给另一个文件。
- 未知、暂时读取失败、不支持、确认无星必须保持不同状态；未知不能当作 0 星，否则会错误排除照片。
- 首屏列表和传输不能等待全卡星级扫描；星级核对必须是低优先级、可取消、可让路的后台任务。

### 公开实现调查结果（2026-10-03）

公开的 libgphoto2 PTP 实现确认存在通用的 `ObjectAdded`、`ObjectRemoved`、`ObjectInfoChanged`、`DevicePropChanged` 和 MTP `ObjectPropChanged` 事件，并实现了 Nikon 的 `GetEvent (0x90C7)` 事件通道：

- [libgphoto2 PTP 事件定义](https://sources.debian.org/src/libgphoto2/2.5.31-4/camlibs/ptp2/ptp.c)
- [libgphoto2 Nikon 相机协议记录](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/cameras/nikon-d600.txt)
- [libgphoto2 PTP 头文件与事件常量](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.h)

这些资料证明“事件通知”是可行的通用协议路径，但没有找到公开资料证明 Nikon Z30 会在修改照片星级时稳定发送带目标句柄的 `ObjectPropChanged`，也没有找到能直接替代实机验证的完整星级刷新实现。因此不能把事件通知当成已经确认的方案。

### 推荐的可靠方案

1. **连接期间优先监听事件**：监听 `0x90C7`，记录 `ObjectAdded`、`ObjectInfoChanged`、`ObjectPropChanged` 等事件。若事件带目标句柄，先将该文件标为“待刷新”，合并短时间内的重复通知，等相机空闲后只重新读取该文件星级。
2. **事件不带句柄或相机不发事件时**：不声称实时。提供一次轻量“刷新星级”操作；后台按当前列表分批核对，分批更新界面，过程中不阻塞缩略图、传输和预览。
3. **每次新连接建立新的确认代次**：旧缓存可以用于首屏占位，但只能标记为历史值；筛选结果在相关文件本次连接确认后才算可靠。新文件始终进入当前代次的待核对队列。
4. **缓存按文件身份保存，但按连接代次失效**：身份可使用句柄、文件名、大小、时间和来源组合；星级值还必须带 `connectionGeneration`、`source` 和 `confirmedAt`。不能只用文件名或摘要判断星级未变。
5. **筛选采用三态以上模型**：`CONFIRMED_RATING`、`CONFIRMED_UNRATED`、`UNKNOWN/UNSUPPORTED/RETRYABLE_FAILURE` 分开处理。筛选期间未知项不能被当作无星，完成一轮后再显示“筛选结果已确认”。
6. **JPG/NEF 配对只作为筛选投影**：唯一可靠同名 JPG 的星级可投影给 NEF，但不能覆盖 NEF 自身缓存；配对关系随本次完整列表重算。

### 必须先完成的实机实验

- 在同一次 STA、AP、USB 连接中，对同一文件执行星级变化，记录 `0x90C7` 是否产生事件、事件码、参数是否包含句柄。
- 事件到达后立即读取星级，确认是否已经写入新值；测试相机忙、连续修改和 JPG+NEF。
- 修改星级后关闭 App、重新连接，确认是否存在可用于快速判断“文件可能变化”的批量标记或时间戳。
- 如果事件始终不可靠，采用“首屏先出图 + 后台分批刷新 + 用户主动刷新”的降级方案，不伪装成实时同步。

在上述实验完成前，不把功能宣传为“相机修改后实时同步”；实现仍采用“事件驱动的单文件刷新 + 新连接代次核对 + 无事件时的低优先级分批刷新”作为可靠降级，而不是永久缓存或每次全卡同步扫描。
