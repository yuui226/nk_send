## 1. 已确认的需求与边界

- 下载与照片生成必须同步并行：下载下一张时，可以生成上一张。
- 明确否决“等待整批下载完成后再生成”以及“下载期间一律暂停生成”的方案。
- 移除两条线之间不必要的等待；生成不能阻塞下一张下载。
- 生成不参与下载速度、下载耗时统计；等待生成显示时钟，实际取得处理名额后才计生成耗时。
- 保持原图品质、原图与裁切图保存规则、入队时效果设置快照及照片效果总开关语义。
- AP、STA、USB 共用后处理流程，不能只优化其中一种连接方式。
- 用户反馈：开启 LUT 后传输速度可能下降至少一半，同时传输与生成会让手机卡顿。尚无同条件性能采样，不能断言单一根因。
- 目标是尽可能隔离流程和资源开销。同设备仍共享 CPU、内存、存储与散热，不能承诺并行情况下绝对零性能影响，更不能通过美化速度统计掩盖实际变慢。

## 2. 代码调查结论

以下为重构前的调查记录，不代表当前实现；已实施内容见第 4 节进度。下面列出的 `processCropTask`、`prewarmPhotoFilter` 已在本轮重构中移除。

| 环节 | 已发现的行为 | 待处理问题 |
|---|---|---|
| 普通原图下载后 | 等待生成所需元数据解析；部分续传场景还补读相机文件头 | 将生成准备移出下载循环 |
| 已有原图 | 下载循环通过生成线程池等待效果图查重与目录准备 | 生成线程忙时可阻塞后续下载 |
| 裁切任务 | 下载循环等待裁切、裁切文件保存及效果图生成 | 存在明确的串行阻塞 |
| 普通效果生成 | 独立的双线程后台工作池 | 已异步，但仍存在共享资源竞争 |
| LUT 单任务限制 | LUT 独占照片处理名额 | 只限制同时处理的照片数量，不等于计算单线程 |
| 像素处理 | PhotoFilterRenderer 内部另有最多 6 线程 ForkJoinPool | 单张任务仍可能占用多个核心，外层低优先级不足以说明内部资源已受控 |
| 图像内存 | 分块读取原图，但仍分配完整输出画布 | 不能将“分块解码”理解为全链路恒定小内存；2400 万像素 ARGB 画布本身约 96 MB，未计边框与中间缓冲 |
| 滤镜预热 | 下载开始附近，在额外 IO 协程中准备滤镜 | 会与下载、预览争抢资源，需移交生成调度 |
| 普通下载速度 | 从协议层起点计算到原图保存及改名/必要复制完成 | 不直接包含随后完整生成时间，但包含被资源竞争拖慢的真实时间；两文件间等待也可能只影响整批耗时 |

## 3. 目标流水线

```text
下载线：相机读取 → 原图保存确认 → 提交轻量生成任务 → 立即下载下一张
                                  ↓
准备队列：文件头解析/必要补读 → 元数据就绪
生成线：选择就绪任务 → 取得处理名额 → 查重/裁切（可选） → LUT/滤镜/边框/水印 → 保存
```

下载与生成持续并行，元数据准备是轻量辅助队列。原图完整可读且准备流程结束后，才进入重生成；“准备结束”包括成功、部分字段可用、失败但允许缺字段继续。无元数据需求的任务直接就绪，不能因字段不全无限等待。

### 3.1 下载线职责

- 原图查重、相机读取、续传、保存、改名或必要复制、下载结果和速度更新。
- 保存确认后交接文件 URI、文件标识、效果与裁切快照等轻量信息。
- 不等待效果图查重、生成目录准备、颜色预热、裁切或生成完成。
- 原图落盘后的生成失败，不回滚下载成功，不删除原图。
- 入队交接必须可靠，不能出现原图成功但生成任务丢失或重复提交。

### 3.2 生成线职责

- 独立队列消费，覆盖普通效果、已有原图生成、裁切及重试。
- 排队仅保留轻量任务记录，不提前解码，不为每张排队照片保留位图或大字节数组。
- 不因生成消费较慢而以阻塞式队列回压下载；大量任务的记录存储和生命周期需要有界设计，不能简单改成无限协程/无限内存队列。
- 新下载时保留有限文件头，解析由独立轻量元数据准备队列负责；积压时以受控缓存或私有快照存储保留可靠来源，不改从可能脱敏的本地图片读取。
- 生成模块不直接访问相机。拍摄信息优先使用传输文件头解析的元数据快照；续传、已有原图缺少可靠快照时，由独立元数据准备任务通过统一相机调度补读文件头，再交给生成模块。不得以可能被系统脱敏的本地 EXIF 替代。
- 裁切边框直接接收原图元数据快照，不通过本地裁切图重新获取 GPS 等拍摄信息；尺寸、方向使用裁切结果，防止重复旋转。
- 生成前重新检查照片效果总开关：关闭则跳过效果，保留入队快照；裁切属于独立需求，仍须执行。已开始的效果按既定规则完成。

### 3.3 实际线程和资源预算

- 首版建议一次生成一张，下载始终独立推进；这是生成侧并发策略，不是整个 App 单线程。
- 导出像素计算先使用一个明确受控的后台计算线程，消除单图内部默认扩张到最多 6 线程的行为。
- 避免外层生成线程提交到内部池后同步等待，形成嵌套线程与无意义占用。
- 解码、颜色处理、编码顺序执行；必要异步 I/O 不得破坏任务取消和资源释放。
- 预览使用独立、轻量、可取消的通道，不能排在长时间导出之后；也不能不受限地与导出同时解码多张大图。
- 下载期间不额外启动预热任务；生成按需准备并复用已验证的 LUT/滤镜数据。
- 是否将空闲时生成计算增加至两线程，留待相同条件真机测试决定；不恢复默认高并发。

### 3.4 内存与存储优化

- 复用分块像素缓冲，降低频繁分配与垃圾回收。
- 避免完整输入位图、处理副本、输出画布长期同时存在；每个临时对象明确归属及释放时机。
- LUT 表按内容复用，保持缓存容量和条目限制；不对每张照片重复解析。
- 原图直接从已保存位置读取，兼容回退时才物化临时文件，不在正常路径重复复制整图。
- 效果图只进行必要的编码与写入；原图、裁切图、效果图仍按用户已确定的规则分别保留。
- 生成前估算输出画布和中间缓冲开销；明确大图内存不足时的安全失败处理，不静默缩图。
- 真正的分块编码输出属于后续独立优化，需要评估画布合成、EXIF、画质及安装包成本，本阶段不直接替换。

### 3.5 状态、统计与失败隔离

- 同一卡片可展示两阶段，但底层下载状态与生成状态独立。
- 下载速度/耗时仅由下载和原图保存环节更新；不通过减去资源竞争等待伪造速度提升。
- 生成排队显示时钟；开始实际处理才计时，效果图保存结束后停止。
- 单独重试生成使用已保存原图和可靠快照，不重新下载整张原图；快照缺失时仍按第 7 节执行必要的文件头补读。
- 取消生成不能取消其他下载；删除任务、清空队列、断线重连和总开关切换均需明确规则。
- 不能在下载结束时提前关闭仍被生成使用的前台服务；两个队列都空闲后再结束服务。
- 派生图先写临时结果，成功后发布；失败/取消清理临时文件，不误删用户原片。

- 总开关变化以事件唤醒调度器：关闭时准备中的任务也可跳过，重新开启不批量改变排队快照。选择与执行之间发生状态变化时，任务可退回准备队列，保留原入队顺序；准备完成事件在任务执行中到达也不会丢失。

- 城市/地区查询已进入独立的有界准备队列，不占用生成消费者或文件头解析消费者；一秒网络预算包含该队列等待，过期任务仍可使用地址缓存。导出复用结果，不再次查询；导出时再次检查 AP/联网条件，防止模式变化后展示地址。准备与地址任务均计入服务存续。
- 照片 LUT 配方已改为私有快照引用，不再通过惰性属性永久持有整张色表。运行时加载资源缓存为 8 MiB、最多 16 项，同一快照并发加载合并；缓存淘汰不删除仍被任务引用的快照，也不使正在使用的色表失效。此预算独立于已有文件解析缓存，不能当作全进程 LUT 总内存上限。

## 7. 方案复核：元数据来源与最小开销（2026-09-29）

结论：双线解耦可行，但下述约束必须一起实现；不能把“低优先级线程”当成资源隔离，也不能用“全部从本地读”替代现有快照机制。

### 7.1 边框信息的首选来源

正常新下载 JPG：协议层 `captureHeader` 从正在写入的下载字节中保留前 256 KiB，仅在从零下载时启用，不额外向相机发命令。当前调用条件为存在边框预设、启用边框、至少显示一项拍摄信息且文件名为 JPEG。之后通过 `metadataFromExifHeader` 解析拍摄信息，并把小型 `PhotoFrameMetadata` 快照交给导出器。

- 256 KiB 是上限，不保证每种文件所有元数据均落在范围内，不能将“解析到一个字段”视为“所有字段完整”。
- 仅 LUT/滤镜的颜色计算不需要品牌、镜头、GPS 等边框元数据，不应因此触发额外相机读取。
- EXIF 方向、图片尺寸、输出 EXIF 保留是独立需求，不能因关闭边框信息而跳过必要处理。
- 城市、地区来自 GPS 的地址解析，不是直接存于文件头的城市字符串。继续沿用现有联网条件、超时和缓存策略，不能以此追加相机读取。

### 7.2 目标来源顺序

| 场景 | 优先来源 | 快照缺失时 | 相机额外请求目标 |
|---|---|---|---|
| 新下载 JPG | 传输捕获的有限文件头，解析一次 | 必要字段因捕获不完整而无法解析时，由元数据准备任务补读相机文件头 | 正常为 0，异常补读需受控 |
| 续传 | 此前已保存/已解析的同文件快照 | 由元数据准备任务补读相机文件头 | 缓存命中为 0，缺失时按需补读 |
| 已有原图、生成重试 | 同原图快照 | 相机仍可访问对应原片时，按需补读文件头 | 缓存命中为 0，缺失时按需补读 |
| 裁切加边框 | 未裁切原图的传输文件头/拍摄信息快照 | 依照原图的新下载、续传或已有原图规则准备快照，不读取本地裁切图拍摄信息 | 新下载正常为 0，其余按原图快照情况 |
| 仅 LUT/滤镜 | 不获取边框拍摄字段 | 只读解码、方向和导出所必需信息 | 0 |

裁切后的尺寸、方向以裁切结果为准，拍摄时间、镜头、曝光等信息沿用原图，不能用原图方向重复旋转已归正的裁切结果。

当前 `existing`、`resume` 的相机补读不能直接删除。应从下载循环迁至独立元数据准备任务，并通过统一相机命令调度，在允许的事务边界执行，避免重复请求。生成服务只接收结果，不持有相机接口。

补读与下载仍共用物理相机通道，不能承诺绝对不占用传输时间，也不能在完整 PTP 数据事务中插入命令。优先复用快照、合并同原图请求；缺失元数据只等待该图的生成准备，不阻塞整个下载队列。具体公平调度策略实施时验证，不允许为补读破坏协议事务或让生成无限等待。

### 7.3 修正：不能依赖本地 EXIF 获取可靠拍摄信息

用户确认的约束：手机系统/文件提供方可能对本地图片 EXIF 中的 GPS 等信息脱敏。自动生成的边框必须优先使用相机传输字节形成的快照，不能把本地读取作为等价兜底。

- 原图传输时截取文件头，解析后的 GPS、海拔、时间、品牌、型号、镜头、曝光等信息复用于普通和裁切边框。
- 裁切不改变拍摄信息；裁切结果只提供新尺寸和方向。禁止为了生成裁切边框重新从已保存裁切图读取拍摄元数据。
- 本地解码可能仍需尺寸/方向等数据，本约束针对边框拍摄信息来源，不代表禁止所有本地读图操作。
- 仅 LUT/滤镜不触发无关的边框元数据补读。城市/地区仍由快照 GPS 走既定地址解析规则。
- 256 KiB 不保证覆盖所有元数据；区分原文件本来缺字段、文件头不完整、解析失败，不为本来不存在的字段循环请求。
- 无可靠快照且相机不可访问对应原片时，不静默采用被脱敏的本地值，不伪造 GPS。已确认允许使用可靠的已有字段继续生成，缺失项不显示、不伪造；记录准备失败原因，不影响已保存原图和其他下载。
- 对重启、重试、已有原图场景，可靠小型元数据快照的保存、索引和清理是减少补读的关键，需按现有任务恢复范围设计。

### 7.4 解析、缓存与调度闭环

- 下载线只交接，不 `await` 元数据解析。轻量准备队列解析一次，成功后立即释放头部数组，后续裁切/边框/保存复用小型结果。
- 不能给所有等待任务无限保留 256 KiB。待处理头部设总字节预算；达到预算时采用轻量磁盘记录等可验证策略，不阻塞下载、不创建无限解析协程，且不能直接丢弃唯一可靠 GPS 来源。
- 快照索引不能只用相机 handle：跨连接/相机可能复用。绑定可靠的原图身份、来源会话与文件版本，删除/替换后失效。
- 若需支持进程重启后继续生成，快照与任务记录需共同持久化并设清理规则；仅内存缓存不满足此要求。具体持久化范围应结合现有任务恢复能力确定，不为本轮无端扩大功能。
- LUT/滤镜准备只在生成侧发生，同内容和参数可复用；与照片/监看选择状态独立，不引入新相机请求。
- 单张生成、单计算线程是保守起点，不是已证明最优。验收必须同时看下载吞吐、生成吞吐和端到端完成时间；不能只改善下载而让生成积压失控。
- 预览、导出取消必须传递到像素循环和分块边界，不能仅取消外层协程而让内部线程继续计算。

- [ ] 普通和裁切边框使用同一原图快照，品牌、型号、镜头、曝光、日期、坐标、海拔、城市/地区一致；裁切后的尺寸方向正确。
- [ ] 在本地 EXIF 被脱敏的场景验证：生成仍使用传输快照；头部截断、无 EXIF、权限失败不得误判为完整元数据。

## 8. 已确认：文件头缓存与元数据准备（2026-09-29）

用户已认可本节方案。目标是避免生成积压同时造成原始文件头积压；不改变下载与生成双线并行要求。

### 8.1 按需捕获，尽早解析

- 仅为需要边框拍摄信息的任务捕获原图文件头；视频、仅 LUT/滤镜等任务不为此保留文件头。图片解码、方向及输出 EXIF 保留仍按各自需求处理。
- 从头下载且文件头成功捕获、包含所需 EXIF 的照片，应在生成前准备好结构化元数据；不能据此假设续传、已有原图和异常文件也一定有快照。
- 文件头进入独立、轻量、受控的元数据准备队列，尽早解析，不排在耗时的图片生成任务之后。下载线只交接，不等待解析结束。
- 不为每个文件启动无限并行解析协程；元数据队列同样需要控制 CPU 和内存使用。
- 解析成功后立即释放原始头部数组；生成任务只引用小型不可变快照，例如品牌、型号、镜头、曝光、日期、GPS、海拔等。
- 快照通常远小于原始文件头，但不以固定大小作保证；仍需限制缓存条目、文本长度及生命周期。

### 8.2 原始文件头容量限制与积压兜底

按每张最多 256 KiB 估算，仅原始数组就可能达到：100 张约 25 MiB，1,000 张约 250 MiB，尚未计对象和复制成本。因此禁止把每张原始文件头一直保留到效果图生成完成。

- 对所有待解析文件头设置统一的总字节预算，包含正在解析和等待解析的占用；实现时计入交接复制可能产生的峰值。
- 正常情况下，尽早解析后释放，内存只保留少量正在处理的文件头和轻量任务快照。
- 极端积压超出预算时，允许将尚未解析的原始文件头暂存应用私有目录，解析后立即删除；不得改读可能脱敏的相册图片替代可靠来源。
- 私有临时存储只作兜底：仍有磁盘成本，不能通过无限异步写入把内存积压转移到另一个队列。
- 内存预算、暂存容量、文件命名/任务关联、取消清理和启动清理在实施时统一确定。磁盘满或暂存失败应记录为该任务的元数据准备失败，不拖垮下载、不丢失已完成原图，不伪装成字段不存在。
- 有限内存、有限磁盘与无限输入不能同时保证永不丢任务；超过资源容量时须明确失败状态，不得无限分配或静默丢弃可靠文件头。

### 8.3 状态与生命周期

区分以下状态，不能只以“某个字段为空”判断失败：

1. 待准备：文件头尚未解析或正在按需补读。
2. 准备成功：可靠来源已解析；字段可以合法缺失，例如相机未写 GPS。
3. 准备失败/不完整：读取失败、截取不完整、解析异常或快照无法取得。

原片本来没有 GPS，不应反复向相机补读；头部不完整也不能误标为“原片无 GPS”。生成是否能继续按已有字段输出，仍遵守第 7 节的异常处理边界。

- 生成完成、跳过或取消后，释放任务不再使用的快照引用和头部临时文件；共享快照不可因一个任务结束就被其他任务错误删除。
- 如需支持重试或进程重启恢复，小型快照可按原图身份保留，但须有容量与清理规则，不无限保留原始文件头。
- 下载与元数据准备交接必须记录成功/失败，不能出现生成任务永久等待一个已经丢失的准备结果。

### 8.5 实施时需明确的资源上限

- 无法同时承诺有限内存、有限磁盘、任意数量任务且永不回压。队列或私有暂存达到硬上限时，必须保留下载结果并明确标记对应生成/准备失败，可重试；不得静默丢任务或继续无界增长。
- 原始文件头暂存失败时，按第 10 节允许缺字段继续；生成配方或源文件引用无法可靠交接时属于生成任务失败，不能误当作缺字段成功。
- 图像解码、编码等系统调用可能使用内部线程；“单计算线程”约束应用自身像素处理，不代表整个进程或系统编解码只有一个线程。

## 9. 完整复核修正（2026-09-29）

总体可行，补充以下约束防止实现时产生隐含阻塞、资源积压或数据错误。

### 9.1 准备与重生成分离

- 等待相机补读、文件头解析或地址查询时，不占生成线程和处理名额，不预分配完整画布。第 7 节的“生成侧解析”指独立轻量准备队列，不能放进重生成串行队列。
- 调度器选择已就绪任务；队首缺元数据不能挡住后续就绪照片。就绪任务按入队顺序处理，界面卡片仍保持原顺序。
- 用准备完成事件唤醒，不为每个任务建立轮询定时器。失败、取消、跳过均需终结准备状态，不能永久等待。
- 效果总开关关闭时，纯效果任务不必等元数据就绪才能被调度为跳过；否则暂停准备可能导致任务永远到不了开关检查点。裁切任务则独立满足裁切所需条件后执行，不能被无须执行的边框准备挡住。
- 裁切和效果属于同一处理任务时，不重新获取自身已持有的独占名额，避免自锁。

### 9.2 减少重复准备和无效补读

- 根据输出确实需要的字段决定是否获取边框元数据；核对品牌图标等布局隐含依赖，避免无关字段查询。
- 可靠解析得出的“原片没有 GPS/某字段”应缓存，不反复请求。
- 同一截断文件头反复读取相同的 256 KiB 不会增加信息。只有确认需要更多字节时才受控扩展补读，设置总字节、次数和超时上限；不为边框重新下载整图。
- 当前 `readExifHeader` 使用交互优先级门控，且 STA 缓存可能返回短于扩展请求的旧文件头。后台元数据补读不能直接照搬交互优先级；扩展读取必须校验缓存长度并在不足时绕过短缓存，否则既抢占下载又没有获得更多字节。
- 准备期限到达后可允许任务缺字段就绪，但已发出的 PTP 请求仍须由协议层安全收尾。禁止仅在外层加短 `withTimeout` 后直接启动下一条相机命令，避免遗留响应污染事务；真正的传输异常仍按现有连接恢复规则处理。
- 当前文件头捕获针对 JPEG。PNG 等其他已支持输入需单独验证元数据来源，不能假设所有图片都具有 JPEG 快照；RAW/视频不能误入此解析路径。
- 城市/地区仅在用户选择且允许联网时查询，沿用缓存和超时，结果在该任务内复用，避免绘制和保存各查询一次。地址等待与相机补读不能串行堵住文件头解析消费者；采用有界异步等待，解析完成立即释放原始头部数组。超时按缺地址就绪，不触发相机重读。

### 9.3 开关和计时边界

- 总开关关闭时，可暂停尚未开始任务的非必要准备，但不能立即批量把所有排队任务永久标为跳过。每个任务在即将开始效果处理时检查开关：当时关闭才明确跳过；此前重新开启则继续使用入队快照。裁切仍需执行，共享准备只有没有其他使用者时才能取消，已有可靠元数据不得因此被清空。
- 准备等待不计重生成耗时，显示时钟；取得处理名额后，计时包含必要查重、目标目录准备、裁切、颜色处理、编码和保存。不得取得名额后又长期等待元数据。
- 已有成片而跳过时不显示虚假的生成耗时，内部阶段切换不反复清零。
- 开关重新开启后，后续未开始任务使用各自入队快照，不自动重做已跳过的任务。

### 9.4 交接、共享锁及内存

- 生成交接按任务标识保证幂等。同图不同裁切/效果是不同任务；原图身份只用于源文件和元数据复用，不能误合并生成任务。
- 每次执行/重试增加尝试标识，元数据、地址查询和生成完成回调都核对任务及尝试标识；取消、删除或重试后迟到的结果不得复活旧任务、覆盖新状态或重复发布文件。
- 释放处理名额、减少活动任务数、清理临时文件必须在成功、异常、取消路径上各执行且仅执行一次。等待中的元数据任务也计入服务存续判断，不能只看两个执行线程是否空闲。
- 系统编解码或提供方 I/O 未必可立即取消；取消后先禁止发布与状态提交，在安全返回点清理。不得跨线程回收仍被原生代码使用的位图，也不得通过新建线程无限重试卡住的提供方。
- 文件名预留、发布和目录索引需要短临界区。禁止下载与生成共持一个锁执行整图处理、目录扫描或大文件复制。尽量按目标目录复用扫描结果，目录准备合并同目标的并发请求；不能为每个任务重新遍历文件夹。
- 同目录并行保存必须验证重名预留及最终文件名，防止覆盖、查重误判、读取未写完文件。
- 大量不同 LUT 排队也不能无限保留大色表。按内容摘要共享不可变配方；排队使用轻量引用或现有私有 LUT 快照标识，运行时按需加载并使用有界缓存。外部文件变化不得影响入队设置。私有快照清理必须考虑所有排队、运行和可重试任务的引用，不能只检查编辑器或内存色表，否则按需加载时可能发现文件已被删除。
- 低优先级应落实到真正执行计算的线程，不仅是外层线程；重解析、解码、预热和目录 I/O 不得返回主线程。
- 可靠交接和暂存仍有成本。“不阻塞下载”指不等待耗时准备/生成，不是交接没有任何开销；需测量交接延迟，不能以无限异步写入掩盖问题。

### 9.5 范围与补充验收

- 首版保持固定、可解释的并发和预算，不立即引入复杂自适应线程数、CPU 亲和性、GPU 导出或强制 GC。
- 单计算线程只是保守起点，不是已证明最快。对照测试同时控制预览开关、温度、后台状态、LUT 尺寸，记录两线重叠时间、下载吞吐、生成吞吐和整批完成时间。
- [ ] 队首元数据不可用时，后续就绪照片仍可生成，下载仍继续。
- [ ] 同目录并发保存、同图不同效果、重复重试均无覆盖或重复发布。
- [ ] 大量不同 LUT 入队时，解析色表内存有界，外部修改不影响任务快照。
- [ ] 元数据准备、地址查询无重复工作；主线程无重运算与文件 I/O。
- [ ] 总开关在准备、排队、裁切和效果阶段切换，符合既定规则。
- [ ] 开关关闭后、排队任务实际开始前重新开启，该任务仍按入队快照生成；已明确跳过的任务不自动重做。
- [ ] 地址服务缓慢或相机补读等待期间，文件头仍及时解析释放，其他就绪任务继续生成。
- [ ] 排队 LUT 色表被内存缓存淘汰后，仍能读取受任务引用保护的私有快照，正确生成。
- [ ] 在补读、地址查询、解码及保存各阶段取消后立即重试，旧回调不污染新任务，名额无泄漏、文件无重复发布。
- [ ] 仅剩元数据准备任务时服务仍存续；开关关闭时纯效果任务能结束等待并被正确跳过。

产品规则已于 2026-09-29 确认：可靠元数据确实无法取得时允许缺字段生成，详见第 10 节。资源容量参数待基线测试确定，不影响双线并行总体设计。


## 10. 已确认：元数据缺失时继续生成（2026-09-29）

- 在有界准备与必要补读仍无法取得可靠元数据时，允许继续生成，使用所有已可靠取得的字段，缺失项不显示、不留占位空行，不伪造数据。
- 缺字段不阻断 LUT/滤镜、裁切及边框输出，不改变原图下载成功状态。纯装饰、手动水印等不依赖缺失字段的内容照常处理。
- 准备结果可标记为“部分字段可用/准备失败但允许继续”，并进入就绪队列；排队等待处理名额时仍显示时钟，真正开始处理才切换为计时。不能无限补读或永远等待元数据。
- 用户预期：相机原片本来保存的拍摄信息应能可靠读取。缺字段输出只是异常兜底，不是省略正常获取流程的理由，验收仍以保留原片实际存在的信息为目标。
- 区分原片没有某字段（例如未记录 GPS）与系统未成功取得字段（截断、权限、断连、解析不兼容等）。记录来源及失败类别，不能把后者伪装成“照片无信息”。
- 可靠快照已包含的字段不得被后续空值覆盖；普通与裁切边框共用快照，不以本地脱敏 EXIF 替代。
- 本规则针对边框拍摄信息；原图不可读、解码失败、裁切几何无法确认等实际图像处理错误，不能当作缺字段而忽略。
- [ ] 测试完整、部分、无拍摄字段三种输入，排版无空行/占位异常，已有字段保留正确。
- [ ] 模拟补读失败，任务能进入生成且不影响后续下载，错误原因可追踪，无重复请求循环。
- [ ] 对照相机原片含有的字段验证正常路径，缺字段兜底不能掩盖数据获取回归。

## 12. 照片传输简化落实

- 照片（含 JPG、RAW 等非视频文件）不恢复旧半成品；失败、取消删除半成品，重试从零开始。
- AP/USB 照片整文件请求；STA 保留已使用的尼康读取命令，一次请求完整范围，短读直接失败，不追加第二个范围请求。底层固定缓冲流式写盘不变。
- MOV/MP4/NEV/AVI 保留视频分块及续传；视频不捕获照片 EXIF 头。
- 原图发布成功立即解除临时 URI 的清理所有权，兼容改名不改变 URI 的提供方。
- 不再有“照片续传缺少开头”的元数据补读场景。已存在原图首次生成、异常截断头部仍保留按需补读；因此快速解析与慢速补读的隔离队列仍保留，不能让罕见补读阻塞后续已捕获文件头的释放。
- 最终 JVM 回归：669 项，0 失败；未运行设备或模拟器。实际速度提升不作未测量承诺。
- 当前实现提交完成后供用户进行真机验证；历史章节中的照片续传要求以本节为准。
