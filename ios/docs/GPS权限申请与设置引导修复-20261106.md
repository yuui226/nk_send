- Android 基准 `/Users/orys/code/nk_send-android`，`eafc461d36da`。`SettingsScreen.kt` 的 `enableGps` 先请求未授予的定位/蓝牙权限，再开启 GPS；`toggleGps` 区分蓝牙开关、定位权限和手机定位开关。`NikonGpsService.kt:startLocationUpdates` 同样分别处理定位权限与手机定位未开启。读取了对应代码及 GPS 测试目录；Android 没有可直接验证 iOS TCC 弹框的测试。

- 原有持久化恢复可在 scene 活跃之前申请权限，未有活跃后补续入口；定位 When In Use 回调同时请求 Always 并启动首次 BLE 请求。本轮补足这些边界，但没有真机复现证据能把用户这一次现象唯一归因于某一个分支。

官方依据：[Apple 定位授权说明](https://support.apple.com/zh-cn/102647)、[requestWhenInUseAuthorization](https://developer.apple.com/documentation/corelocation/cllocationmanager/requestwheninuseauthorization())、[Core Bluetooth authorization](https://developer.apple.com/documentation/corebluetooth/cbmanagerauthorization)。[Apple denied 定义](https://developer.apple.com/documentation/corelocation/clauthorizationstatus/denied)明确包含全局关闭；首次 notDetermined 不必额外查询定位总开关。权限由系统请求后管理，尚未申请不能靠 App 设置开关代替申请。

## 用户授权路径

1. 打开手机“设置 → 隐私与安全性 → 定位服务”总开关，并开启手机蓝牙。
2. 返回 Z传，GPS 窗点“开启 GPS”。定位弹框选择“使用 App 时允许”，蓝牙弹框选择“允许”。需要后台持续写入时，再允许后续的“始终”定位请求。
3. 曾经拒绝过时，点 GPS 重试进入“设置 → App → Z传”更改相应权限；也可在“隐私与安全性”的定位服务/蓝牙列表里管理。
4. 若受屏幕使用时间或设备管理限制，应先解除相应限制。没有申请过的权限不要求用户手动寻找不存在的开关。

## 第四轮：冷启动误开启与允许定位后真机闪退

用户明确指出冷启动不应恢复 GPS 开关，并补充点击允许定位后闪退。沿用同一 Android `eafc461d` 基准，独立处理，没有修改 Android。

### 行为依据纠正

- Android `NikonGpsRuntime.state` 初始为 `GpsState()`，即关闭；`GpsViewModel` 不根据旧 preferences 主动启动服务。`NikonGpsService.setApModeBlocked` 还明确阻止连接页首次报告非 AP 时复活旧 GPS。
- Android 确实写入 `KEY_ENABLED`，但用于已经启动的前台服务恢复及禁用守卫。此前把 `START_STICKY` 的恢复规则套到 iOS 普通冷启动，是错误解释。按本次用户明确规则，iOS 开关只保留在进程内，不再读写开启标志；旧 `enabled` 键仅用于删除迁移。
- Android **确实有错误态“重试”**：`SettingsScreen.kt:toggleGps` 的 ERROR 分支执行 retry，`GpsStatusButton` 将 ERROR 映射到 `gps_retry`。本轮保留正常手动开启后失败的重试；关闭态始终显示 `gps_enable`，不把重试错误地删除。

### 闪退证据与修复

只读取得用户 iPhone 15 Plus 的两份实际崩溃报告，时间 2026-11-06 23:16:17、23:16:19，版本 2.05(79)、iOS 27.0.1。两份均为 SIGABRT，异常栈落在 `CBCentralManager initWithDelegate:queue:options:` 的断言路径，经 `NikonGPSBluetoothClient.ensureCentral/start` 和 GPS 授权续接触发。原报告没有异常 reason 正文，不伪造具体异常原文；脱敏栈摘要归档，原始设备报告仅留 `/tmp`。

源码存在真机独有分支：传 `CBCentralManagerOptionRestoreIdentifierKey`，而成品 `UIBackgroundModes` 只有 location、缺少 bluetooth-central；模拟器分支不传恢复参数，因此前三轮真实定位 UI 仍没有覆盖这个真机初始化。依据 [Apple Core Bluetooth 后台及恢复说明](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html)，后台蓝牙与跨进程恢复是不同能力，恢复标识属于主动加入的机制。

- 移除不符合“本次运行开关”规则的蓝牙恢复注册、恢复回调及持久化恢复入口，真机和模拟器共用延迟创建的普通 manager；显式开启时才创建，后续重启连接复用该 manager。
- Info.plist 和 project.yml 同步加入 bluetooth-central，保留已手动开启会话的后台蓝牙能力；不因此开启 GPS、不启动轮询。
- GPSCoordinator 默认关闭，保留配对身份、帮助已读和更新频率。ConnectionViewModel 同样不再用旧磁盘标志暂停 AP 发现。
- 停止时先发布关闭状态再调用蓝牙 stop，防止 stop 同步发出的 disconnected 重建重连/权限查询任务。继续使用任务代次和当前会话守卫拒绝晚到写入。
- 按钮显式提供当前状态的无障碍文案，不修改可见样式或动画。

## 第五轮：补齐系统蓝牙配对与首次 GPS 写入确认（11月6日开始，7日收尾）

用户反馈相机没有显示配对成功，随后明确接受“使用 iOS 系统配对窗口”，并说明以 GPS 实际可用为目标。本轮仍独立执行。遵守 AGENTS.md 第21行的平台差异约定；不是把界面显示成功作为验收。

### 实际遗漏与依据

Android `eafc461d36da712260ebb262f034d7da70450ae6`，`NikonGpsBleClient.kt:onCharacteristicWrite(ID)`：首次 BLE 身份握手和32字节手机名称写入完成后，执行 Classic discovery/createBond 并断开 BLE；只有系统配对成功才通过 `onPairedIdentity` 保存 stage1 的 device/nonce，然后800ms后重新连接 BLE。已有确认身份的再次握手 ID ACK 才能进入 ready。`NikonGpsService.onPairedIdentity/onGeoWritten` 还要求第一次 GEO 写入成功，才走650ms配对成功、700ms已连接的显示过渡。

iOS 原实现在生成 stage1 时就写 preferences，ID ACK 直接 ready，没有任何 Classic 系统配对；阶段3/4还提前显示相机确认。这是本轮确认的逻辑缺口。新增反证 `testFreshHandshakeDoesNotPersistIdentityBeforeSystemPairingConfirmation` 在旧实现出现4条失败断言；只读手机偏好也存在 device/nonce/ble_address，但没有取得手机真实握手日志，因此不将偏好存在当作系统配对证明。

### 已接受的平台差异与实现

- iOS 使用公开 `EAAccessoryManager.showBluetoothAccessoryPicker(withNameFilter:completion:)`。用户在系统“选择配件”里选择相机，核对配对码并在手机、相机两端确认；不使用私有 API、静默代按或 Android 自动删除系统 bond。
- [Apple 接口文档](https://developer.apple.com/documentation/externalaccessory/eaaccessorymanager/showbluetoothaccessorypicker%28withnamefilter%3Acompletion%3A%29)与本机 ExternalAccessory 头文件核对参数和错误；[Nikon 官方 iOS 配对步骤](https://nikonimglib.com/snbr/onlinehelp/en/bluetooth_pairing_4.html)描述选相机后再次在弹出的设备列表选择、两端确认，以及失败后在系统中忽略相机的处理。文档符合此方案，但不能替代这台手机与相机的实测。
- 只在新鲜握手 ID 写入确认后关闭本次 BLE 并打开系统选择器；相机名匹配沿用 Android 等名/至少4字符前缀范围。系统窗口仅前台呈现、在途去重；30秒截止沿用 Android。关闭 GPS、AP 切换、适配器失效或超时使旧回调失效。公开接口没有程序化取消选择器，逻辑取消后不接受结果，也不叠加第二个系统窗口；需由用户关闭仍可见的旧窗口。
- 系统完成后才持久化 identity，并新增 pairing_confirmed 标记；清除配对同时清标记。没有标记或凭证不完整的旧记录会删除，修复旧版误记身份；不改变频率、帮助、其他偏好。不主动删除手机的系统蓝牙设备。
- 系统完成后清除旧 BLE 地址缓存，重新扫描，因为 Nikon 可能变更随机 BLE 地址。`.systemPaired` 事件保留等待首次 GEO ACK 的标志，跨越 disconnected/connecting/ready，不依赖当时界面状态推测是否新配对。
- 系统取消、找不到、失败、已连接均不保存新身份、不报告 ready。已连接错误提示用户先在“设置→蓝牙”忽略旧记录；普通失败提示重新开始配对。提示放在现有 GPS 面板、三语齐全，不新增入口或轮询。手动开启/关闭、定位授权、既有更新频率与动画时长保持。
- 停止时只在实际扫描中调用 stopScan，避免本轮测试发现的未上电 manager 无效停止请求；不改变连接回收边界。
