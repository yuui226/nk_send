## 依据与范围

Android `eafc461d` 的 `CameraViewModel.tryConnectStaCandidate`、`NikonCamera.connectSta/initializeStaBrowsingSession`、`StaConnectionIsolationTest`：收到 Result ACK 后等待剩余 6.6 秒；普通服务就绪失败仅重试一次、间隔 1.2 秒。iOS 原来也是这一限制，并非漏搬已有的长等待。用户本轮明确要求耐心等待重新联网，作为本次 iOS 行为调整依据；未修改 Android。

只读手机最近完成的诊断（12:16:44）显示一次后续尝试在 Query 0x952B 返回 0x201F，未取得 Result ACK。它不能证明用户描述的上一轮 ACK 后失败的精确耗时；没有将这条明确拒绝吞为网络重试。之前 IPv4 冲突是独立已证实问题，本轮用户说明该问题已处理。

## 修复规则

- 原有 ACK 后剩余 6.6 秒等待不变。给已持有确认收据的同一机身一个从 ACK 起算的 60 秒网络重试窗口；清理、socket 连接和重试间隔都计入，失败不会续期。
- 仅对传输层暂时不可达、拒绝连接、超时、断线/重置继续尝试，失败后异步等待至多 1.2 秒；恢复即可继续，不强制等满一分钟。没有新增后台扫描、忙循环或逐帧工作。
- 保留同一 GUID、身份和收据，不重新发 Query/Result、不切其他机身或备用身份。配对前就绪重试不会耗尽配对后的窗口。
- 取消立即停止；明确拒绝、错误机身、无效协议数据和不确定的 Query/Result 结果保持原终止规则。窗口结束不再发起下一次网络重试；在途有效握手仍沿用既有命令预算，不以窗口到期粗暴打断一次正常验证。
- 界面阶段、按钮、文案、动画不变；等待期间不发布临时失败。原始失败仍进入已有 Debug 诊断。

## 配对记录与补救的完整顺序

1. 收到相机 Result ACK：保存 GUID/IP/身份等连接信息，并在本次流程持有待验证收据；不写 `sta_paired_` 或 `sta_pairing_verified_v2_` 成功标记。
2. 等相机重新联网：只尝试恢复连接，不把尚未联网当作配对被撤销。
3. 同机身恢复后，验证相册权限及真实有效监看帧；全部通过，才写入已验证标记并进入照片列表。
4. 设备明确处于仅配对能力状态时，清除该机身的旧成功标记，执行原来的内联补救。已发起监看验证但失败时，丢弃本次未验证收据、保留机身 GUID，执行原来的一次重新配对。两条路径共享一次额度；新 ACK 后仍须重新验证。
5. 第二次仍不能验证则停止；有了有效帧的证据后，收尾故障只走原有收尾恢复，不重新配对。普通掉网不清除已验证配对；不会删除其他机身记录，也不轮换本机 initiator ID。

因此本轮没有新增“先保存成功标记再靠补救删除”的中间状态，延长网络等待不会让成功标记绕过补救。
