# 相册保存与生成原图生命周期修复

2026-11-10。开发验证4/4完成，真机验证0/1，合计4/5。

## 行为依据与根因

按用户要求，生成始终读取完整且传输完成的原图。已阅读 Android TransferViewModel 的原图发布后异步派生流程及 PhotoFrameExporterTest 的原图/派生输出验证。昨天批准的 iOS 相册与自选文件夹差异继续适用。

CameraRepository.downloadResult 校验长度、关闭 writer，再调用 finalizeDownloadedFile 完成重命名，返回完整文件的 result.url。TransferQueue 把此 URL 写入 outputURL，并传给 startFrameGeneration。生成入口没有读取传输中的 nkpart 分片。

原 finishPhotoLibraryPublication 在生成仍排队或运行时将完整原图导入 Photos，随即删除本地完整原图。Photos 中的资产不会使原 file URL 继续有效。后续生成读取同一路径时失败。PhotoAllocationBudget 将 ImageIO 无法打开输入报告为 fileReadCorruptFile，对应用户的“未能打开该文件，因为它的格式不正确”。裁切准备 attributesOfItem 缺文件可抛 Cocoa code 4，transferErrorMessage 把它解释为“传输目录已失效，请重新选择”。后者依据代码路径定位，本轮没有独立真机日志。

## 实现

生成输入仍是下载完成并发布的原图。相册发布等同一 outputURL 的所有生成读者结束后执行，再导入原图、裁切图和效果图。每个源文件串行发布，原图账本和已成功输出记录避免重复导入。异步 Photos 返回后再次检查生成读者及错误，全部成功才清理完整原图和已导入的派生文件。生成或导入失败保留完整原图与成功派生文件，支持既有离线重试。重复跳过已导入原图时不再盲删仍可能被其他任务使用的文件。

文件夹流程继续保存完整原图与派生文件。无 UI、文案、手势或动画变化。原有下载与单生成工作池继续异步运行。

## 同日补充，冷启动后台清理

用户明确断点续传与失败重试仅属于当前进程生命周期，杀进程后重开视为新生命周期。清理必须在App启动时由后台线程执行，不能延迟到传输前，也不能等待清理或展示提示。

ZTransferApp.init 调用 startStartupCleanup，进程级静态 Task.detached(priority: .utility) 执行一次旧文件清理。相册工作目录调整为 ZTransferPhotoStaging/<当前进程UUID>，同一进程始终使用同一个目录。后台只扫描父目录一级，删除上个进程子目录及旧版本平铺文件，保留本进程目录。因此用户立即开始新传输时可直接写入当前进程目录，与旧目录清理并行。清理不会挂在 scenePhase 前台恢复或传输开始入口。

用户选择的文件夹、系统相册资产和相册导入账本继续使用既有独立存储。冷启动会丢弃上次尚未导入相册的私有文件，此行为由本轮用户明确指定。清理遇到文件系统错误时本次静默结束，下次冷启动再次尝试。
