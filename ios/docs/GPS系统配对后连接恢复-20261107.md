## Android与iOS依据

Android `eafc461d36da`，`NikonGpsBleClient.onCharacteristicWrite(ID)/finishClassicPairing` 和 `NikonGpsService.onPairedIdentity/onDisconnected/onGeoWritten`：系统bond完成之后，使用原stage1身份重连；只有首次GEO成功才显示配对成功650ms、已连接700ms。读取对应实现及既有GPS测试。

[Apple配件选择器](https://developer.apple.com/documentation/externalaccessory/eaaccessorymanager/showbluetoothaccessorypicker%28withnamefilter%3Acompletion%3A%29)展示带iAP标识的设备，其完成回调反馈该选择/连接过程的错误。[错误定义](https://developer.apple.com/documentation/externalaccessory/eabluetoothaccessorypickererror/code)中alreadyConnected表示已连接，notFound表示选择的配件未找到，不是Nikon的stage2身份拒绝结果。设备实测与相机反馈构成这一轮改判的依据。

[Apple retrieveConnectedPeripherals](https://developer.apple.com/documentation/corebluetooth/cbcentralmanager/retrieveconnectedperipherals%28withservices%3A%29)返回已被系统连接的匹配服务设备，仍需App调用connect；此类设备可能不再广播，不能只扫描等待。iOS UUID也不等同Android物理/随机地址。

用户先前已接受iOS系统窗口差异，并明确“目的是让gps功能正常使用，只要达成目的就行”。本轮将iOS系统结果与相机GPS验证拆开，保留原成功展示/频率/关闭规则；没有绕过相机协议验证、没有把未知状态显示为已配对。

## 修改

1. 系统返回paired/alreadyConnected/notFound/failed后，保存**待验证**identity与目标相机名，保留已知CoreBluetooth UUID，再进入BLE验证。用户明确取消、当前30秒截止、关闭/AP/适配器失效仍停止当前尝试，迟到结果不能复活。增加原始错误domain/code诊断，不记录密钥/坐标。
2. 新 `pairing_verification_pending` 与 `pairing_confirmed` 含义分开。`hasPairingIdentity`允许重连/清除，`hasSavedPairing`只有实际确认后为true，不能提前显示“已配对”。pending可跨进程保留以免重启后丢掉已经在相机建立的身份，但**GPS开关仍不持久化、不自动开启**。旧版本无任一标记的提前写入记录仍按上一轮迁移规则清理。
3. 明确进入verifyingPairing，800ms后重连；先取回同一相机的系统已连接设备，再尝试已知UUID，失败沿用4.5秒转扫描。按已知UUID、准确名字、唯一前缀匹配选取；不在两个同前缀相机间随意选。新扫描也约束已有目标，避免邻近另一台Nikon被拿来验证身份。
4. pending的扫描/握手超时作为连接确认超时处理，沿用可取消的5秒重连，不立即丢弃身份、要求重新配对。真正stage2拒绝仍清除身份并要求相机操作；没有绕过随机挑战、服务/通知/写入归属。
5. 当前BLE会话收到GEO成功ACK后才提交confirmed并清pending；失败写入、关闭后的旧ACK不提交。首次GEO成功的650/700ms展示规则保持。清除配对一次清完confirmed/pending/identity/name/UUID。

用户重新复制后取得实际00:37轮次，证据为 `evidence/gps-pairing-recovery-20261107/device-diagnostic-0037-cancelled.txt`：00:37:55收到ID ACK并打开系统窗口；00:38:00返回 `EABluetoothAccessoryPickerErrorDomain/2`，随后App停止，没有pending身份。不是应用30秒超时。用户明确反馈 **“点了相机，窗口自己关闭”**，因此不能把系统枚举名 `resultCancelled` 直接解释为用户主动点了取消。系统为什么关闭尚无底层证据；现有停止分支仍未解决，不能标记GPS成功，也不能把所有取消直接改成已配对。

用户质疑此前“iOS必须手动选设备”的说法。重新核对公开资料与本机SDK后，纠正如下：

1. CoreBluetooth允许App按广播服务发现并直接连接已识别的BLE设备，不要求经过设备选择列表。访问需要加密的GATT特征可触发系统配对确认；列表选择与确认配对是不同环节。[Apple WWDC22：What's new in Nearby Interaction，23:23–24:03](https://developer.apple.com/videos/play/wwdc2022/10008/)。该资料说明一般机制，不证明Nikon暴露了可用于此流程的受保护特征。
2. Apple公开CTKD跨传输密钥派生及 `CBConnectPeripheralOptionEnableTransportBridgingKey`：支持CTKD的设备可由BLE配对派生经典蓝牙密钥，并联动经典蓝牙连接。[Apple WWDC19：What's New in Core Bluetooth，dual-mode部分](https://developer.apple.com/videos/play/wwdc2019/901/)。本机SDK header也确认bridging选项是启动经典传输profile，不是Android `createBond` 的无条件等价物。尚无证据确认用户Z50 II的此项能力，不应只加一个选项就宣称修复。
3. 重新阅读[Nikon当前SnapBridge配对帮助](https://nikonimglib.com/snbr/onlinehelp/en/bluetooth_pairing_4.html)：`Nikon Z Mount Mirrorless Cameras`与`Other Cameras`为不同分节；明确“Select an accessory”的旧iOS步骤在后者。不能将该步骤直接推广为所有Z机型的硬性要求。[Z50 II说明书](https://onlinemanual.nikonimglib.com/z50II/en/24-02.html)要求首次双方核对配对码，后续已配对设备可以直接连接，但未说明底层CTKD支持。
4. 本地Android `NikonGpsBleClient.startClassicPairing/startClassicBond`确实自行发现匹配相机并调用`createBond`；`setPairingConfirmation(true)`只在系统允许时静默确认，失败仍回退系统提示。因此“安卓不选设备”不能推导为iOS必须增加列表，也不能推导iOS可代用户确认系统弹框。
5. 搜到的[photools iOS GPS项目](https://github.com/vincentchyu/photools#-practical-guide-pairing-key-extraction--bluetooth-automatic-sync)所谓免配对依赖先由SnapBridge配对、从抓包提取已有身份，不是首次配对的免列表方案。仅阅读公开说明作为排除依据，未复制其代码、未提取其他App凭证。

## 用户要求免设备选择：直接 BLE 实验

用户明确要求“尝试无需手机选设备这一步骤是否可行，而不是让我重新测一下”。此前清除旧 bond/重测选择器的请求被本次实验替代，不再以该请求未执行为阻塞。Android 基准仍为 eafc461d：ID ACK → 自动发现 Classic 相机/createBond → 同身份 BLE 重连 → 实际 GEO ACK。本台相机的系统历史报告过 Non CTKD，因此不把 transport bridging 参数当作已验证方案。
